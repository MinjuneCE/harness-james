# 공통 규칙

모든 코드에 적용한다. 층 구조는 `README.md`에 있다.

## 0. 적용 방식

- 적용 대상은 제품 코드다. 개인 도구 코드(에이전트 하네스, 스킬, 훅, 작업용 스크립트)는 대상이 아니다.
- 규칙은 새로 쓰거나 고치는 코드와 그 커밋에 적용한다. 문서를 설치한 곳에만 두므로 다른 사람이 쓴 코드와 커밋은 대상이 아니다.
- 컨벤션은 앞으로 하는 개발의 기준이다. 이미 있는 코드와 커밋은 그대로 둔다. 규칙에 맞추려고 기존 코드를 따로 정리하지 않는다.
- 기존 코드에 규칙과 다른 모습이 있어도 베끼지 않는다.
- 규칙은 구조, 타입, 자동 검사, 테스트, 문서 순서로 지키게 한다. 검사로 바꿀 수 있는 규칙은 검사로 바꾸고, 문서에는 검사로 바꿀 수 없는 것만 남긴다.
- 기존 위반은 기준선으로 묶어 둔다. 위반이 새로 늘 때만 검사가 실패하고, 정리한 뒤에는 기준선을 다시 조인다.

## 1. 구조와 경계

- **S1. 의존은 한 방향으로만 간다.** 입출력과 프레임워크 코드가 유스케이스 코드를, 유스케이스 코드가 판단 코드를 부른다. 거꾸로 가는 참조는 금지한다. 격리할 모듈은 폴더로 나누고, 폴더 사이의 import를 검사로 막는다. 계층이 없는 스택은 스택 문서가 이 규칙에 해당하는 방향을 정한다.
- **S2. 업무 판단은 프레임워크와 화면 없이 돌 수 있는 코드 한곳에 둔다.** 그 한곳은 스택에 따라 도메인 클래스나 순수 함수다. 화면을 그리는 코드와 입출력 코드에는 판단을 두지 않는다. 프레임워크를 띄우지 않고도 판단을 읽고 테스트할 수 있어야 한다.
- **S3. 갈아 끼우는 자리는 쓰는 곳이 둘 이상이거나 진짜 경계일 때만 만든다.** 갈아 끼우는 자리는 인터페이스, 주입하는 인자, 이벤트 같은 것이다. 진짜 경계는 외부 API, DB, 시계, 다른 팀의 시스템처럼 우리가 바꿀 수 없거나 테스트에서 갈아 끼워야 하는 것이다. 구현이 하나뿐인 간접층은 읽는 사람이 따라갈 층만 늘린다.
- **S4. 경계의 이름은 공급자 이름이 아니라 업무 말로 짓는다.** 우리가 고르는 이름에 적용한다. 이름을 공급자가 정해 주는 자리, 그 공급자를 다루는 것 자체가 업무인 자리는 프로젝트 문서에 예외로 적는다.
- **S5. 외부 응답과 오류는 경계에서 우리가 정한 모양의 값으로 바꿔 넘긴다.** 외부 시스템의 응답 형식, 상태 문자열, 오류 코드, 예외는 경계 코드 밖으로 나가지 않는다.
- **S6. 같은 일을 하는 방법은 하나만 둔다.** 새 방식을 정하면 같은 변경 안에서 호출하는 쪽을 옮기고 옛 방식을 지운다. 둘이 남아 있으면 사람도 에이전트도 둘 다 베낀다. 같은 목록이나 같은 화면을 복사해 여러 벌 두는 것도 여기에 든다.
- **S7. 상태는 한곳에서 정한다.** 그 한곳은 상태를 가진 타입의 메서드나 순수 함수 하나다. 다른 코드는 정해진 상태를 읽기만 한다. 흩어진 boolean과 if로 상태를 표현하지 않는다.
- **S8. 모르는 값과 실패는 안전한 쪽으로 떨어진다.** 모르는 외부 값, 빠진 설정, 실패한 외부 조회를 만나면 기능을 숨기거나 호출하지 않는 쪽으로 간다. 일부만 받은 값으로 업무 판단을 하지 않는다. 어느 쪽이 안전한지는 S5의 변환 한곳에 적는다.
- **S9. 오용하기 쉬운 기능은 감싼 한곳에서만 쓴다.** 잘못 쓰기 쉽거나 쓴 곳마다 같은 실수가 되풀이되는 기능은 제품 코드에서 직접 쓰지 않는다. 한곳에서 감싸 안전한 API로 내놓고, 나머지 코드는 그 API만 쓴다. 무엇이 해당하는지는 스택 문서의 "직접 쓰지 않는 것" 표에 적고, 검사로 막는다.
- **S10. 기다려서 순서를 맞추지 않는다.** 다른 코드가 준비되기를 기다리려고 타이머나 sleep을 쓰지 않는다. 테스트도 같다. 그런 기다림이 필요해 보이면 순서를 보장하는 방법(이벤트, 콜백, 반환값)으로 원인을 고친다. 제한 시간(X1), 정책이 정한 간격(폴링, 재시도), 입력 묶기에 쓰는 타이머는 허용하고, 이름 붙은 한곳에 둔다(S9).
- **S11. 다른 시스템이 최종 판정하는 규칙을 복제할 때는 원본보다 넓게 허용하지 않는다.** 화면이 서버의 판정을 미리 흉내 내는 경우가 대표적이다. 복제한 규칙이 원본보다 넓지 않음을 테스트로 고정하고, 원본이 무엇인지는 그 테스트의 이름에 밝힌다(K2).

## 2. 값

하드코딩된 값은 성격에 따라 둘 곳이 다르다.

| 종류 | 예 | 둘 곳 |
|---|---|---|
| 운영·정책 값: 환경마다 다르거나 코드를 고치지 않고 바꿔야 하는 값 | 시간, 간격, 재시도 횟수, 배치 크기, 국가 목록, 정책상 허용·차단 목록 | 그 스택의 설정 수단. 환경별 값과 시크릿은 환경 변수 |
| 업무 상태와 사유 코드 | 요청됨, 처리 중, 거절 사유 | 코드의 닫힌 값 목록 한곳 |
| 외부 계약 값 | 외부 API의 상태 문자열, 오류 코드 | 그 외부를 다루는 경계 코드의 매핑 한곳 |

- **V1. 운영·정책 값은 코드에 리터럴로 두지 않는다.** 설정으로 받는다. 없으면 안 되는 값은 시작할 때나 배포 전 검사에서 걸러, 값이 없거나 틀리면 뜨지 않게 한다. 없어도 되는 값은 없을 때의 동작(S8)을 한곳에 적는다.
- **V2. 기본값은 한 곳에만 둔다.** 코드 상수, 설정 파일, 예시 환경 파일에 같은 기본값을 나눠 두지 않는다. 시크릿은 기본값 없이 환경 변수로만 받고, 코드와 저장소에 넣지 않는다.
- **V3. 업무 상태와 사유 코드는 닫힌 값 목록으로 둔다.** 흩어진 문자열로 두지 않고, 설정으로 빼지도 않는다. 이 값은 저장되고 분기가 기대고 있어서 환경마다 달라지면 데이터와 코드가 어긋난다. 빠뜨린 경우는 검사가 잡게 한다. 그 검사는 스택에 따라 컴파일러, 타입 검사, 목록 전체를 도는 테스트다.
- **V4. 외부 계약 값은 경계 안에만 둔다(S5).** 판단 코드와 유스케이스 코드에는 외부 시스템의 문자열이 나오지 않는다.
- **V5. 바깥에 남는 값과 관측용 라벨을 나눈다.** 저장되거나 분기가 기대는 값은 판단 코드 쪽에 둔다. 메트릭 태그나 로그 라벨처럼 관측에만 쓰는 값은 그 값을 쓰는 계층에 둔다. DB 값, API 응답 값, 브라우저 저장소 키, 분석 이벤트 이름, 메트릭 태그처럼 바깥에 남는 문자열은 한곳에 고정해, 코드 쪽 이름을 바꿔도 바깥 문자열이 변하지 않게 한다.
- **V6. 정책은 상태와 업무 사실로 분기한다.** "이미 요청을 보냈다" 같은 업무 사실은 상태나 필드로 둔다. 코드 위치를 뜻하는 것(단계 이름, 페이지 경로, 파일 이름)으로 정책을 가르지 않는다. 그렇게 가르면 코드를 옮기는 것만으로 정책이 바뀐다.

## 3. 테스트

- **T1. 구현할 때는 실패하는 테스트를 먼저 쓴다.** 기능과 버그 수정 모두 해당한다.
- **T2. 커밋은 테스트 커밋, 구현 커밋 순서로 남긴다.** 테스트를 먼저 썼는지 이력에서 보이게 하려는 것이다. 브랜치의 마지막 커밋은 항상 테스트가 통과하는 상태여야 한다. 테스트를 나중에 몰아 넣는 커밋은 만들지 않는다. 테스트를 저장소에 둘 수 없는 프로젝트는 T1은 그대로 지키고, 이 규칙만 프로젝트 문서에 예외로 적는다.
- **T3. 테스트는 동작을 단언한다.** 기준은 "동작을 깨면 실패하고, 내부만 바꾸면 통과하는가"다.
  - 동작: 바깥으로 보낸 요청, 저장된 데이터와 상태, 응답, 오류 종류, 외부 경계와의 순서, 사용자에게 보이는 문구.
  - 동작이 아닌 것: 내부 협력 객체를 불렀는지와 그 순서, 로그와 내부 예외의 문구.
- **T4. 경계 자리에는 가짜를 먼저 쓴다.** 가짜는 스택에 따라 메모리용 구현이나 주입한 함수다. 목은 외부 경계에만 쓴다. 내부 객체를 목으로 바꾸면 테스트가 구현을 따라가게 된다.
- **T5. 기본 테스트 실행은 실제 외부 시스템을 부르지 않는다.** 실제로 부르는 테스트는 표시를 달아 별도 실행으로 분리한다.
- **T6. 테스트 이름은 영어로 행위를 서술한다.** 테스트 안의 설명은 단언 메시지에 쓴다(K2). 이미 있는 다른 언어의 이름은 그대로 둔다.
- **T7. 코드가 읽는 선언 파일과 코드의 짝을 테스트로 묶는다.** 설정 스키마, 번역 파일, 매니페스트가 해당한다. 한쪽만 바뀌면 테스트가 깨져야 한다.

## 4. 주석

- **K1. 주석은 쓰지 않는다.** 주석은 코드와 함께 검사되지 않아서 낡고, 문제를 고치는 대신 설명하고 넘어가는 자리로 쓰인다. 코드가 무엇을 하는지는 이름과 함수 추출로 드러낸다.
- **K2. 이유는 검사되는 자리나 변경에 붙는 자리에 적는다.**

  | 적고 싶은 것 | 적는 자리 |
  |---|---|
  | 외부 때문에 이상해 보이는 코드의 이유 | 그 동작을 고정하는 테스트의 이름과 단언 메시지 |
  | 여러 구현이 지켜야 하는 계약 | 진짜 구현과 가짜 구현에 똑같이 돌리는 계약 테스트 |
  | 이슈·문서 링크, 변경의 배경 | 커밋 메시지 |
  | 나중에 할 일 | 이슈나 작업 목록 |

- **K3. 이상해 보이는 코드를 남겨야 하면 그 동작을 고정하는 테스트를 둔다.** 누가 그 코드를 고치면 테스트가 깨지면서 이유를 알려 준다. 테스트 없이 남은 이상한 코드는 고칠 대상이다.
- **K4. 예외는 도구가 읽고 검사하는 주석뿐이다.** 타입 표기(JSDoc 타입 등), lint를 끄는 지시문과 거기에 붙이는 이유, 라이선스 머리말이 해당한다.
- 테스트를 저장소에 둘 수 없는 스택은 스택 문서가 예외를 정한다.
- 팀이 열 수 없는 번호(개인 작업 공간의 설계 문서 번호, 작업 메모의 항목 번호)는 코드와 테스트 이름에 쓰지 않는다.
- 이 규칙은 검사로 지킨다. 새로 추가된 줄에 K4 밖의 주석이 있으면 실패하게 한다.

## 5. 커밋과 변경 단위

- **C1. 커밋 하나에는 목적 하나만 담는다.** 문제를 푸는 가장 작은 diff를 낸다.
- **C2. 테스트 커밋, 구현 커밋 순서를 지킨다(T2).**
- **C3. 옮기기와 옛것 지우기는 한 변경에서 한다(S6).**

## 6. 외부 호출과 보안

- **X1. 모든 외부 호출에 제한 시간을 둔다.** 시간 초과는 다른 실패와 나눠 다룬다. 시간 초과는 요청이 처리됐는지 모르는 상태이기 때문이다.
- **X2. 개인정보와 비밀값은 로그, 예외 메시지, 브라우저 저장소, 분석 이벤트에 그대로 남기지 않는다.** 사람을 가리켜야 하면 해시 같은 되돌릴 수 없는 값으로 남긴다.
- **X3. 바깥에서 온 값을 다른 언어의 코드에 넣을 때는 그 언어용 인코딩을 거친다.** HTML, 스크립트, SQL, 셸 명령이 해당한다. 문자열을 이어 붙여 넣지 않는다.

## 7. 리뷰 질문

검사로 바꿀 수 없어서 리뷰에서 사람이 판단하는 것이다.

- 두 번 실행되거나 중간에 죽어도 같은 끝 상태가 되는가? 스케줄러, 재시도, 웹훅 처리에서 특히 확인한다. 화면 코드는 같은 스크립트가 두 번 실려도 한 번만 동작하는지 본다.
- 결과를 모르는 쓰기 요청(시간 초과, 서버 오류)을 실패나 성공으로 단정하지 않고, 다시 조회해 끝 상태를 정하는가?
- 이 catch나 가드가 다루는 상태가 정당한가, 아니면 버그를 숨기는가? 로그만 남기고 계속 가는 코드라면 이유를 한 줄로 밝힌다.
- 흩어진 boolean과 if를 상태 머신이나 타입으로 모아야 하지 않는가?
