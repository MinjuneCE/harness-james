# decision-log

```bash
node ${CLAUDE_SKILL_DIR}/bin/decision-check.mjs <기능 폴더>                # 기록과 문서를 맞춰 본다
node ${CLAUDE_SKILL_DIR}/bin/decision-check.mjs <기능 폴더> --current      # 지금 유효한 결정만 한 줄씩, 끝에 다음 번호를 보인다
node ${CLAUDE_SKILL_DIR}/bin/decision-check.mjs <기능 폴더> --sync-table   # decisions.md의 "지금 유효한 결정" 표를 기록에서 다시 만든다
```

검사와 `--current`는 읽기만 한다. `--sync-table`만 파일을 고치는데, 기록 파일이 프로젝트 폴더(`CLAUDE_PROJECT_DIR`, 없으면 명령을 부른 현재 폴더) 밖에 있거나 같은 번호가 두 번 나오면 고치지 않고 종료 코드 2로 끝낸다. 프로젝트 루트에서 부르면 된다.

Node 18 이상에서 돈다. 의존성 없음(외부 패키지와 외부 CLI를 쓰지 않는다).

## 이 문서 묶음이 도는 방식

- **결정의 원본은 `decisions.md` 하나다.** spec·plan에는 지금 유효한 결과만 적고 근거는 `(D12)`처럼 번호로 가리킨다. 이유와 버린 안을 두 곳에 적으면 한쪽만 고쳐져 어긋난다.
- **기록은 덧붙이기만 한다.** 지난 묶음은 고치지 않는다. 뒤집힌 결정은 새 항목의 `대체:` 줄로 표시한다. 그래야 그때 왜 그렇게 정했는지가 남는다.
- **D 번호는 사용자가 정한 것에만 붙인다.** 에이전트가 구현·조사 중에 본 것은 `P`(제안)로 적고 사용자 답을 받는다. 구현이 결정과 다르게 됐다는 사실은 근거일 뿐 결정이 아니다.
- **기록을 어느 저장소에 둘지는 프로젝트가 정한다.** 여럿이 쓰는 저장소에 개인 작업 기록을 넣지 않으려면 개인 작업 공간의 문서 폴더에 기능 폴더를 둔다. 검사기는 어느 쪽이든 프로젝트 폴더 밖의 파일은 고치지 않는다.

## 언제 무엇을 하나

| 상황 | 하는 일 |
|---|---|
| 기능 폴더에 기록이 아직 없다 | 양식 `${CLAUDE_SKILL_DIR}/templates/decisions.md`를 그 폴더에 `decisions.md`로 복사하고 자리표시를 채운다. spec-kit 스킬의 `feature` 명령으로 만든 폴더에는 처음부터 있다 |
| 사용자가 무엇을 정했다 | `## 기록` 바로 아래에 새 묶음을 넣는다(최신이 위). 번호는 `--current` 끝 줄의 "다음 번호"부터 쓴다. 끝나면 `--sync-table` |
| spec·plan을 고치려 한다 | `--current`로 지금 유효한 결정을 읽는다. 고친 뒤 그 줄에 `(D번호)`를 달고 머리 줄 번호를 올린다 |
| 구현·조사 중에 결정과 어긋나는 것을 봤다 | 그 방향으로 더 나아가기 전에 `P` 항목으로 적고 사용자에게 묻는다. 답이 오면 `D` 항목을 쓰고 `제안: P번호`로 닫는다 |
| 작업 묶음을 끝냈다 | 검사를 한 번 돌려 WARN·FAIL을 본다 |

머리 줄 번호를 올린다는 것은 "그 번호까지의 결정을 이 문서에 비춰 봤다"는 뜻이다. 결정이 이 문서와 상관없어도, 확인했으면 올린다.

## 항목 형식

양식 전문은 `${CLAUDE_SKILL_DIR}/templates/decisions.md`에 있다. 묶음 하나는 사용자가 한 번에 답한 자리다.

```markdown
### 2026-11-24 10:12 (사용자, 구현 세션 — 보관 기간)

원자료: `<대화 기록 경로>` 1234줄 "기간은 한 달로 가자"

- D12 내보낸 파일의 보관 기간은 30일이다.
  - 이유: 다시 받는 요청은 대부분 한 달 안에 온다
  - 버린 안: 90일(분기 대비) — 저장 공간이 빨리 찬다
  - 대체: D7
  - 반영: plan.md, spec.md
- P3 기간이 지난 파일을 지울 때 알릴 곳이 정해지지 않았다
  - 근거: plan.md 판정 5
  - 추천: 기존 알림 채널
```

검사기가 읽는 것은 다음뿐이다. 나머지 줄(이유, 버린 안, 원자료, 근거)은 자유롭게 쓴다.

| 줄 | 뜻 |
|---|---|
| `- D<번호> …` (들여쓰지 않은 목록 줄) | 결정 하나. 뒤의 글이 표에 들어가는 한 줄이다 |
| `- P<번호> …` | 사용자 답을 기다리는 제안 |
| `  - 대체: D7` | 이 결정이 D7을 통째로 대신한다. D7은 유효한 결정에서 빠진다 |
| `  - 일부 대체: D7 (…)` | D7의 일부만 바꾼다. D7은 유효하게 남는다 |
| `  - 반영: plan.md, spec.md` | 이 결정이 들어가야 하는 문서(기능 폴더 기준 경로) |
| `  - 제안: P3` | 이 결정으로 P3가 닫힌다(채택이든 기각이든) |
| `이전 기록: … (D1~D40)` | 앞선 번호가 다른 파일에 있다. 번호는 그 다음부터 잇는다 |

문서 쪽에는 앞 40줄 안에 머리 줄을 하나 둔다.

```markdown
**반영한 결정**: ~D12 ([decisions.md](decisions.md))
```

아직 반영한 것이 없으면 `**반영한 결정**: 없음`이다. spec.md와 plan.md는 머리 줄이 없으면 WARN이 나오고, 그 밖의 문서는 머리 줄을 둔 것만 본다.

## 결과 읽기

항목마다 한 줄(`PASS|FAIL|WARN|INFO  ID  [문서]  요약`)이 나오고 상세가 아래에 붙는다. 종료 코드는 0 = FAIL 없음, 1 = FAIL 있음, 2 = 인자 오류, 기록 파일 없음, `--sync-table` 거절이다.

| ID | 무엇 | 수준 |
|---|---|---|
| ledger | 결정 수, 최신 번호, 대체된 수. 같은 번호가 두 번 나오면 FAIL | PASS/FAIL |
| table | "지금 유효한 결정" 표가 기록과 다르다 → `--sync-table` | WARN |
| supersede-ref | `대체:`가 가리키는 번호가 기록에 없거나 자신보다 뒤다 | WARN |
| proposal | 닫히지 않은 제안 목록 | INFO |
| header | 문서 머리 줄이 기록보다 뒤처짐(몇 건 뒤인지, 이 문서를 반영 위치로 적은 결정) | WARN |
| header | 머리 줄 번호가 기록의 최신보다 크다 | FAIL |
| reflect | `반영:`에 적힌 파일이 없거나, 문서에 그 번호 인용이 없다 | WARN |
| stale-cite | 대체된 결정만 가리키는 줄(`파일:줄`). 같은 줄에 대체한 번호가 함께 있으면 넘어간다 | WARN |
| unknown-cite | 기록에 없는 번호를 가리킨다 | WARN |

검사기는 번호가 인용됐는지만 본다. 내용이 결정대로 반영됐는지는 사람과 에이전트가 읽어야 안다.

## 번호 읽는 규칙

- `D12`, `D33~D43`, `D1-D9`를 인용으로 읽는다. 범위는 `reflect` 확인에는 인정하고 `stale-cite`에서는 넘어간다.
- `D-05`(spec-kit research.md의 설계 항목 번호 같은 것)와 `회의록 D6`처럼 앞에 "회의록"이 붙은 번호는 다른 체계라 세지 않는다. 다른 문서의 D 번호를 옮겨 적을 때는 이렇게 출처를 앞에 붙인다.
- 코드 블록과 HTML 주석 안은 읽지 않는다.

## 옛 기록과 잇기

결정 기록이 이미 다른 파일(예: 기능 폴더 README의 "결정 기록" 절)에 쌓여 있으면 옮기지 않는다. 새 `decisions.md` 머리에 `이전 기록: [README.md](README.md#결정-기록) (D1~D40)` 한 줄을 두고 D41부터 잇는다. 검사기는 그 범위의 번호를 아는 번호로 치고, 대체 여부는 새 파일에 적힌 것만 안다.
