# 구조 목록을 정하는 기준

구조를 처음 나눌 때, 중요도·문턱을 매길 때, dependents를 걸 때 읽는다. 산식의 뜻은 /pr-verify의 `framework.md`(평가 폴더에 있으면 그것, 없으면 pr-verify 스킬의 `evaluation/framework.md`) 4.4장(구조 영향도), 5장(판정 규칙), 7장(피크 시즌)에 있다.

## 구조 나누기

구조는 "이 부분이 바뀌면 사람이 직접 봐야 하는가"를 가르는 단위다. 폴더 구조를 그대로 옮기지 않고, 틀렸을 때 생기는 일이 같은 파일끼리 묶는다.

- 먼저 진입점을 찾는다. 서버는 컨트롤러·스케줄러·이벤트(웹훅·큐) 수신, 화면은 앱·확장의 진입 컴포넌트와 서버 호출 코드, 템플릿 기반 사이트는 공통 레이아웃과 구매·가입 같은 주 흐름 페이지다. 진입점에서 호출을 따라가며 묶는다.
- 한 구조는 한 문장으로 "왜 중요한지"를 말할 수 있어야 한다. `why`에는 틀리면 생기는 일을 적는다(예: "틀리면 다른 고객의 구독 상태가 보인다"). 파일 설명만 있는 `why`는 중요도를 정할 근거가 못 된다.
- 레포 하나에 5–13개가 보통이다. 파일 서너 개짜리 레포 설정 구조도 괜찮다. 구조가 20개를 넘으면 검토 패킷이 잘게 쪼개진다.
- 경로는 되도록 폴더 glob으로 적는다(`…/infrastructure/mailer/**`). 새 파일이 생겨도 구조에 들어온다. 한 폴더에 성격이 다른 파일이 섞였으면 파일 이름이나 이름 패턴(`*Port.java`)으로 적는다.
- glob 뜻: `*`는 `/`를 넘지 않고, `**/`는 폴더 0개 이상, `?`는 한 글자다. `exclude`로 일부를 뺄 수 있다.
- 한 파일이 두 구조에 걸려도 된다. 예: 응답 상태 enum이 "판정"과 "API 계약" 양쪽에 든다.
- 템플릿에서 시작한 레포는 첫 커밋 그대로인 파일이 많다(inventory의 "첫 커밋 그대로인 파일 수"). 그 파일들도 구조에 넣되 중요도는 그 코드가 하는 일로 정한다. 첫 검증에서 그 구조의 바뀐 파일이 0으로 나오는 것은 정상이다.
- 설정 클래스(값 묶음, 예: `…Properties`)는 그 값을 읽는 기능의 구조에 넣는다. 값이 그 기능의 동작을 바꾸기 때문이다. 여러 기능이 함께 쓰는 검증 도우미와 공용 설정은 런타임 설정 구조에 넣는다.
- id는 `<레포 접두어>.<이름>`으로 짓고 등록 뒤에는 바꾸지 않는다. 리포트·보정 기록과 기능 문서 메타(`feature_map`이 있을 때)가 id를 가리킨다.

## 중요도 (criticality, 0–100)

프로필끼리 같은 눈금을 쓰도록 정한 줄이다. 새 구조는 이 줄에 맞춰 놓는다.

| 값 | 어떤 구조 | 예 |
|---|---|---|
| 95 | 돈이 실제로 움직이는 실행 경로, 인증·인가 경계 | 결제·환불 실행, 호출자 인증·소유자 검증, 결제 요청 화면과 API 호출 |
| 90 | 되돌리기 어려운 외부 쓰기, 중복 실행을 막는 경로, 매출이 지나가는 화면, 운영 배포·권한 | 멱등 키·재시도 안전망, 주문 상태 머신, 장바구니 |
| 85 | 외부에서 들어오는 진입점, DB 마이그레이션, 앱·확장의 권한·네트워크 설정, 모든 페이지에 실리는 코드 | 웹훅 수신, 마이그레이션, 앱 권한 설정, 공통 레이아웃 |
| 75–80 | API 계약, 외부 연동 기반, 개인정보·동의 표시 | 공개 API, 외부 서비스 클라이언트, 마케팅 수신 동의 |
| 70 | 운영 알림, 런타임 설정·의존성, 고객 안내 문구 | 운영 알림, 런타임 설정, 환불 정책 안내 |
| 50–60 | 번역, 미리보기, 생성 코드, 실사용이 끝난 시험용 API | 현지화, 앱 생성 코드 |

- 눈금은 파일 이름이 아니라 틀렸을 때 생기는 일로 고른다. 예와 이름이 같아도 생기는 일이 다르면 그 일에 맞는 줄을 고른다.
- 딱 맞는 줄이 없으면(예: 실패해도 주 흐름의 결과가 안 바뀌는 부가 외부 쓰기, 외부 쓰기를 열어 주는 판정 로직) 가까운 두 줄 사이에서 정한다.
- 눈금을 벗어났거나 망설인 값은 보고의 "판단이 갈린 곳"에 적는다. 사용자가 표에서 바로 고칠 수 있다.

## 검토 문턱 (review_threshold)

구조 영향도가 문턱 이상이면 사람이 직접 본다. 영향도 = 중요도 × 변경 규모(1–10줄 0.6, 11–50줄 0.8, 51줄 이상 1.0) + 중간 이상 지적이 있으면 20.

- 기본은 60이다. 중요도 75–85에서는 11줄 이상, 60–70에서는 51줄 이상 바뀔 때 걸린다. 중요도가 60 미만이면 문턱 60에서는 줄 수만으로 걸리지 않는다(중간 이상 지적이 같이 나와야 한다).
- 한 줄만 바뀌어도 사람이 봐야 하는 구조는 50으로 내린다(중요도 85 이상에서 통한다). 돈 경로·인증·마이그레이션에 흔히 50을 쓴다.
- 피크 시즌에는 문턱이 0.8배가 되어 더 적은 변경에 걸린다(중요도 80·문턱 60은 한 줄부터). 중요도 85 이상 구조는 문턱과 상관없이 동작 변경이 한 줄만 있어도 걸린다(표의 "시즌 변경 동결").
- 숫자를 손으로 계산하지 않는다. `table`이 구조마다 "몇 줄 바뀌면 사람이 보는지"를 계산해 준다. 그 문장이 의도와 다르면 값을 고친다.

## coverage_ignore

구조에 넣지 않는 파일이다. 여기 있는 파일은 "구조 밖 파일" 경고에서 빠진다.

- 넣는 것: 시험 코드, lock 파일, 빌드 래퍼, README, git 설정, 개발 도구 설정. skeleton이 넣어 준다. 도구가 만들어 커밋한 생성 파일(타입 선언 등)도 넣는다. 빌드 도구 버전을 정하는 파일(wrapper properties 등)은 설정 구조에 넣어도 된다.
- 판단할 것: 린트·서식 설정, CHANGELOG, `docs/` 같은 설명 문서, 이미지 같은 정적 자산, 루트의 타입 선언. 동작에 영향이 없으면 넣는다. 배포 절차서처럼 운영 작업의 기준이 되는 문서는 그 구조에 둔다. `.dockerignore`, `tsconfig.json`, 배포 스크립트의 시험처럼 빌드·배포 결과를 바꾸는 파일은 설정·배포 구조에 넣는다.
- 구조와 coverage_ignore에 모두 걸리면 구조가 이긴다.

## dependents (다른 레포와의 대조)

이 레포의 파일(`source`)이 바뀌면 /pr-verify가 상대 레포의 파일(`replicas`)을 실행 폴더에 가져와 판정 에이전트가 함께 본다.

- 계약이 있는 곳에만 건다: 서버 응답 DTO·오류 처리기·상태 enum과 그것을 해석하는 화면 코드, 화면이 부르는 경로·상태 코드와 그것을 정하는 컨트롤러. 양쪽 코드에서 같은 필드 이름·상태 값·상태 코드를 확인하고 건다(`git grep`).
- `repo`는 상대 프로필의 `repo.key`다. 상대 프로필이 아직 없으면 두 초안을 같은 폴더에 두고 함께 등록한다(check가 초안끼리 짝을 맞춰 본다).
- `ref`는 `origin/<브랜치>`로 적는다. /pr-verify는 이름을 로컬 브랜치에서 먼저 찾는데, 로컬 브랜치는 origin보다 뒤처져 있을 수 있다. `ref`를 빼면 상대의 default_base와 대조한다. 둘 다 되고, 고르기 어려우면 `origin/<상대 default 브랜치>`를 적는다. 기능 브랜치를 적었으면 머지된 뒤 고쳐야 한다(check가 `dependent-ref … stale`로 알린다).
- 설정 수준의 계약(앱 client_id와 토큰 검증, 권한 범위)과 양쪽에 따로 적힌 같은 상수(대기 시간 등)도 후보다. 한쪽이 바뀌어도 다른 쪽이 깨지지 않는 느슨한 관계는 걸지 않는다.
- `note`에는 무엇이 무엇의 거울인지 적는다(예: "응답 필드 이름을 카드가 그대로 읽는다").
- 양쪽 프로필에 서로를 건다. 서버가 바뀔 때는 화면을, 화면이 바뀔 때는 서버를 본다.

## 차원 가중치

skeleton의 출발값은 같은 성격의 등록 프로필 값이다. 레포의 위험이 다르면 옮기고 합을 1.0으로 맞춘다(check가 본다).

- 개인정보·비밀 키를 다루면 SEC를, 외부 호출 결과가 고객 상태를 바꾸면 REL을, 배포·인프라 파일이 레포에 있으면 OPS를 올린다.
- 트래픽이 작거나 요청당 외부 호출이 적으면 PERF를, 구조가 단순하면 ARCH를 내린다.
- A11Y는 traits에 client가 있을 때만 둔다. traits는 레포에 그 성격의 코드가 있으면 둔다(지금 호스팅하지 않는 템플릿 서버 코드도 server).
- 한 번에 0.05씩 옮기고 TEST는 0.10–0.15에 둔다.
- 같은 성격의 등록 프로필이 없어 skeleton이 가중치를 비워 뒀으면 pr-verify 스킬의 `examples/profile.example.json`(서버 레포 예) 값에서 시작한다. client 레포면 A11Y를 0.10 안팎으로 더하고 다른 차원에서 같은 만큼 덜어 합을 1.0으로 맞춘다.
- 바꾼 값과 이유를 보고에 적는다. 가중치는 등록 뒤에도 보정으로 고친다.

## 그 밖의 칸

- `feature_map`: 기능 문서 폴더와 그것을 점검하는 도구(`VERIFY_FM_BIN`)가 있는 프로젝트에서만 넣는다. 없으면 빼 둔다.
- `specs`: 판정 에이전트와 검토 패킷이 참고할 문서(설계·스펙) 경로 목록이다. 구조와 맞는 문서가 없으면 `[]`.
- `long_lived_branches`, `ledgers`: 장기 브랜치와 대체 장부가 있을 때만 넣는다. `ledgers`는 diff 밖 신호 도구(`VERIFY_SIGNAL_BIN`)가 있어야 쓰인다.
- `tools`: 프로젝트 도구 모듈(kind `module`, 평가 폴더 기준 경로) 목록이다. 프로젝트가 린터·플랫폼 검사 모듈을 준비했을 때만 넣고, 그 밖에는 `[]`. 모양은 pr-verify 스킬의 `references/profile-guide.md` "프로젝트 도구" 절에 있다.
- `rules`: 결정적 자동 신호 규칙이다. 이 스킬은 새로 짓지 않는다. 사용자가 요청한 규칙만 넣고 check로 모양을 본다.
- `parameters`: 판정 에이전트가 참고할 미확정 값이다. 모르면 null로 둔다.
- `floors`, `criteria`, `secret_scan`, `ignore_line_patterns`: skeleton이 준 값을 그대로 둔다. 차단선과 기준별 문턱은 보정 기록(평가 폴더의 `calibration/`)을 보고 고치는 값이라 이 스킬에서 정하지 않는다.
