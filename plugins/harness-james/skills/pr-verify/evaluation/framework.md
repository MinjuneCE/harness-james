# PR 검증 프레임워크

- 버전: 2.1.0 (2026-10-23)
- 대상: 모든 레포. 레포마다 프로파일 하나를 둔다. 레포 성격(`repo.traits`: `server`·`client`)과 차원 가중치가 어떤 차원·기준을 적용할지 정한다
- 수치 파라미터: [`config/scoring.json`](config/scoring.json) · 기준 본문: [`rubrics/`](rubrics/) · 레포별 설정: 프로젝트 평가 폴더의 `profiles/`(기본 `docs/evaluation/profiles/`, 작성 안내 [`../references/profile-guide.md`](../references/profile-guide.md))
- 실행: `/pr-verify` 스킬 (harness-james 플러그인 `skills/pr-verify/`)

이 문서는 PR 검증이 **무엇을, 어떤 규칙으로, 몇 점으로** 판정하는지 정한다. 판정 에이전트(LLM)는 근거가 달린 finding만 만든다. 점수와 판정은 스크립트(`score.mjs`)가 이 문서의 산식대로 계산한다. finding이 같으면 점수도 항상 같다.

---

## 1. 판정 구조 한눈에 보기

```
PR diff ─┬─ 자동 신호 (프로파일 도구, 비밀값 스캔)                  ─┐
         └─ 판정 에이전트 7개 차원 (Opus 5.5 max, 필요 시 탐색 에이전트) ─┤
                                                                    ▼
                                High 이상 finding → 반증 에이전트 (Opus 5.5 max)
                                                                    ▼
                         score.mjs: 기준 위험도 → 차원 품질 → 종합 품질 → 구조 영향도
                                                                    ▼
                    판정: BLOCK / REVIEW_REQUIRED / PASS  +  트리거별 검토 패킷
```

두 축으로 판정한다.

| 축 | 값 | 방향 | 쓰임 |
|---|---|---|---|
| **품질 점수** | 차원별 0–100, 종합 0–100 | 높을수록 좋음 | 차단선 미만이면 **BLOCK** (PR 전에 수정) |
| **위험 트리거** | 기준별 위험도 0–100, 구조별 영향도 0–100 | 높을수록 위험 | 기준치 이상이면 **REVIEW_REQUIRED** (사람이 해당 구조를 직접 검토) |

## 2. 평가 차원

| 코드 | 차원 | 서버 | 클라이언트 | 보는 것 | 보지 않는 것 (소관 차원) |
|---|:-:|:-:|:-:|---|---|
| `SEC` | 보안·프라이버시 | ● | ● | 인증·인가(IDOR), 입력 검증·출력 인코딩(XSS·인젝션), 비밀정보, 공급망(서드파티 스크립트·의존성 고정), 개인정보·동의(GDPR/CCPA, 동의 전 트래킹), 남용 방지(레이트 리밋·CORS·봇), 로그·오류를 통한 민감정보 노출 | 로그 형식(OPS), 레이트 리밋의 용량 측면(PERF) |
| `PERF` | 성능·확장성 (피크 트래픽) | ● | ● | 클라이언트: 로딩(LCP/INP/CLS, 렌더 차단, 자산 크기, 이미지), 서버 렌더 비용, 클라이언트 요청 수. 서버: 요청 스레드 안의 동기 외부 호출, 스레드·커넥션 풀, DB 쿼리·인덱스·락, 외부 API 호출 예산(호출 수·쿼리 비용·스로틀), 캐싱, 백프레셔·큐잉 | 타임아웃·재시도 정책 자체(REL) |
| `ARCH` | 아키텍처 | ● | ● | 계층·의존 방향, 경계 번역, 도메인 모델이 상태를 소유하는지, 응집·결합·중복, 설정 설계, 레포의 설계 원칙·스펙 문서 정합. 클라이언트: 벤더가 배포하는 코드 불가침, 지역·마켓 맥락 우선, 데이터 주도 콘텐츠, 생성 코드 불가침, 템플릿 명명·위생, 컴포넌트 중복 | 런타임 실패 처리(REL) |
| `REL` | 신뢰성·데이터 정합성 | ● | ● | 멱등성, 상태 전이의 런타임 안전성, 외부 호출 실패 처리(불확실 결과 재실행 금지, 타임아웃·재시도·백오프), 트랜잭션 경계, 동시성 제어, 마이그레이션 안전성, 복구·재처리 경로. 클라이언트: 구매 흐름 무결성, 서드파티 장애 시 우아한 저하, 설정 스키마·저장된 템플릿 호환성 | 용량(PERF) |
| `OPS` | 관측성·운영 | ● | ● | 로그 구조·컨텍스트, 메트릭·헬스체크·알림, 필수 설정 검증·설정 예시 파일 동기화, 배포·롤백 준비, 운영자 수동 처리 경로. 클라이언트: 미리보기 검증·운영 환경 동기화, 서드파티 임베드 변경 추적, 변경 추적성 | 민감정보 노출(SEC) |
| `TEST` | 테스트 적정성 | ● | ● | 바뀐 로직에 맞는 테스트, 실패 경로·경계값, 테스트 계층(단위·슬라이스·통합), 외부 의존 통합 테스트 분리, 시간 제어, 결정성. 클라이언트: 정적 검사 도구 통과, PR에 수동 QA 시나리오 기술 | — |
| `A11Y` | 접근성·i18n·마켓 | — | ● | WCAG 2.2 AA(대체 텍스트, 키보드, 포커스, aria, 대비, 헤딩, `lang`), 번역 리소스 경유, 언어 키 동기화, 국가·통화 하드코딩, 마켓별 가격·프로모션·약관 노출 정확성 | 마켓 분기 구조 설계(ARCH) |

- ●는 그 성격의 레포에 이 차원 기준이 있다는 뜻이다. 실제 적용 차원은 프로파일 `dimensions`(가중치)가 정한다.
- 기준 단위 적용은 rubric 기준 목록의 "적용" 열(`공통`·`서버`·`클라이언트`)과 프로파일 `repo.traits`로 고른다. `공통`은 항상, `서버`·`클라이언트`는 traits에 그 값이 있을 때만 적용한다.

**중복 금지**: 한 문제는 가장 구체적인 기준 하나에만 올린다. 다른 차원에도 영향이 있으면 `also_affects`에 적는다(점수에는 반영하지 않음).

## 3. Finding 모델

### 3.1 필드

```json
{
  "id": "F-REL-003",
  "criterion": "REL-02",
  "title": "결과 불명 상태에서 외부 결제 호출 재실행",
  "severity": "critical",
  "confidence": "confirmed",
  "origin": "introduced",
  "evidence": [
    {"side": "head", "file": "src/payment/retry.ts", "line": 88, "end_line": 97}
  ],
  "failure_scenario": "요청 ID 없이 처리 중인 건을 재시도 작업이 다시 집으면 결제 요청을 또 보냄 → 첫 호출이 실제로 성공했던 건은 두 번 청구됨",
  "rationale": "결과 불명인 비멱등 외부 호출은 재실행하지 않고 조회로만 확정해야 함",
  "recommendation": "요청 ID가 없으면 결제사 조회로 처리 여부를 확인하고, 확인 전에는 재호출하지 않음",
  "structures": ["api.payment"],
  "also_affects": ["ARCH"],
  "source": "judge"
}
```

| 필드 | 필수 | 설명 |
|---|:-:|---|
| `criterion` | ● | rubric의 기준 ID (`SEC-01` 등). 해당 레포에 적용되는 기준만 허용 |
| `severity` | ● | `critical` `high` `medium` `low` `info` (3.2) |
| `confidence` | ● | `confirmed` `likely` `possible` (3.3) |
| `origin` | ● | `introduced` `worsened` `pre-existing` `fixed` (3.4) |
| `evidence` | ● | 1개 이상. `side`(`head`=PR 이후 코드, `base`=PR 이전 코드), 레포 루트 기준 `file`, `line`(`end_line` 선택) |
| `failure_scenario` | ● | "입력·상태 → 결과" 형식의 구체적 시나리오. PERF는 트래픽 가정을 포함(예: "피크 시 분당 요청 N건") |
| `structures` | | 관련 핵심 구조 ID (프로파일의 `structures`) |
| `source` | ● | `judge`(판정 에이전트) `tool`(프로파일 도구·비밀값 스캔) `rule`(규칙 엔진, 현재 규칙 없음) |

### 3.2 심각도 앵커 (모든 차원 공통)

| 심각도 | 점수 | 정의 | 예 |
|---|---:|---|---|
| `critical` | 60 | 운영에서 **금전 손실·개인정보 유출·핵심 사용자 흐름(구매·취소 등) 전면 장애**가 현실적인 시나리오로 발생. 또는 레포가 타협 불가로 정한 원칙 위반 | 남의 주문을 취소할 수 있음(IDOR) · 불확실한 결과에 비멱등 외부 호출 재실행 → 이중 환불 · 피크에 외부 API 한도 초과로 핵심 흐름 전면 실패 · 저장형 XSS · 장바구니 추가 불능 · 키보드·스크린리더 사용자가 상품·장바구니 화면에서 구매 불가(접근성 측면의 핵심 흐름 전면 장애) |
| `high` | 30 | 특정 조건에서 critical 수준 피해, 레포 설계 원칙의 **MUST** 위반, 피크 트래픽에서 체감 가능한 성능 저하 | 외부 호출 타임아웃 없음 · 이미 적용된 마이그레이션 수정 · 렌더 차단 외부 스크립트 추가 · 토큰 로그 출력 |
| `medium` | 12 | 제한적 피해, 성능·운영 부담 증가, **SHOULD** 위반 | 인덱스 없는 신규 조회 · 번역 안 거친 문자열 · 실패 경로 테스트 누락 |
| `low` | 4 | 개선 권장 | 로그 컨텍스트 키 일부 누락 |
| `info` | 0 | 참고. 점수 영향 없음 | — |

각 rubric은 기준마다 이 앵커를 그 기준의 언어로 구체화한다(rubric의 "심각도 앵커").

### 3.3 신뢰도

| 값 | 계수 | 조건 |
|---|---:|---|
| `confirmed` | 1.0 | 코드 근거만으로 실패 경로를 끝까지 보일 수 있음 |
| `likely` | 0.7 | 근거는 있지만 설정값·데이터·트래픽 같은 런타임 조건에 달려 있음 |
| `possible` | 0.4 | 의심 수준. 확인이 필요함 |

### 3.4 출처 (origin)와 감점

| 값 | 의미 | 감점 |
|---|---|:-:|
| `introduced` | 이 PR이 새로 만든 문제 | ● |
| `worsened` | 기존 문제를 이 PR이 악화(새 호출 경로 추가, 방어 코드 제거 등) | ● |
| `pre-existing` | base 트리에 이미 있던 문제 (기존 부채) | — (리포트 '참고'에 표시) |
| `fixed` | 이 PR이 해결한 문제 | — (리포트 '개선'에 표시) |

**출처 검증(결정적)**: `introduced`·`worsened` finding은 근거 중 하나 이상이 diff 변경 범위(±`origin_line_tolerance`줄, 기본 5) 안에 있어야 한다. `head` 근거는 추가된 줄, `base` 근거는 삭제된 줄 기준이다. 조건을 못 맞추면 `score.mjs`가 `pre-existing`으로 재분류하고 리포트에 기록한다. 기존 부채 때문에 PR이 감점되는 일을 막는 장치다.

**기존 부채 판단**: 부채 목록을 따로 두지 않는다. 판정 에이전트가 base 트리(PR 이전 코드)를 직접 읽어 같은 문제가 이미 있었는지 확인한다. 있었으면 `pre-existing`, PR이 그 문제를 넓히거나 방어를 걷어냈으면 `worsened`로 분류한다. 근거에는 base 쪽 위치를 함께 단다.

### 3.5 자동 신호 (도구·비밀값 스캔)

판정 에이전트와 별도로 `prepare.mjs`가 diff에서 결정적으로 finding을 만든다. 자동 신호도 같은 산식으로 점수에 들어간다. rubric에는 자동 규칙을 두지 않는다. 규칙 엔진 코드는 남아 있지만 rubric·프로파일에 규칙이 없으므로 `source: rule` finding은 생기지 않는다.

| 출처 | 내용 | 묶는 단위 |
|---|---|---|
| 비밀값 스캔 | 추가된 줄의 비밀값 패턴(`config/scoring.json` `secret_patterns`, 프로파일 `secret_scan`) | **패턴 하나 = finding 하나**. 여러 파일에서 걸려도 근거를 모아 하나로 만든다(한 원인, 한 finding) |
| 도구 (`source: tool`) | 프로파일 `tools`에 정한 정적 검사 도구(base 대비 변경 파일에서 새로 생긴 오프펜스만, 도구별 매핑으로 기준·심각도 지정)와 템플릿 무결성 검사(설정 스키마 항목 삭제·이름·타입 변경과 그 값을 쓰는 템플릿 수, 참조 대상 존재 여부 등) | 체크(또는 심각도) 하나 = finding 하나 |

- 줄바꿈·들여쓰기만 바뀐 hunk(공백·주석을 빼면 같은 코드)는 동작 변경으로 세지 않는다.
- `info` 자동 신호는 0점이다. 판정 에이전트는 해당 기준의 `note`에 무엇을 확인했는지 적는다.
- 판정 입력에는 diff 외에 커밋 메시지(`context.commits`)와 PR 본문(`target.pr.body`, PR 대상일 때)이 들어간다.
- 브랜치 대상 실행(`target.pr`가 null)에는 PR 본문이 아직 없다. PR 본문에 적는 기록이 없다는 이유로는 감점하지 않고 `info` finding으로 확인 질문을 남긴다. 미리보기 근거·QA 시나리오·배포 메모가 여기에 해당한다(TEST-08, OPS-05).

### 3.6 중복 병합

같은 기준에서 근거 위치가 겹치는(같은 파일·같은 side, ±`origin_line_tolerance`줄) 감점 finding이 여럿이면 **점수가 가장 높은 하나만** 감점한다. 동점이면 판정 > 도구 > 규칙 순으로 남긴다. 나머지는 리포트 "중복 병합"에 표시한다. 다른 기준끼리는 병합하지 않는다. 한 문제를 여러 기준에 올리지 않는 것은 판정 에이전트의 책임이다(2장).

### 3.7 diff 밖 결정적 신호와 검증 범위

diff만 보면 "이 변경 때문에 바뀌었어야 하는데 diff 밖에 남은 것"이 보이지 않는다(부르는 곳이 사라진 정의, 설계가 지운다고 한 기호, 다른 레포 복제본, 문서 줄 참조). `prepare.mjs`는 갈림점 기준으로 결정적 도구를 돌려 그 사실을 판정 자료로 붙인다.

- **갈림점**: PR base(PR 대상) 또는 프로파일 `default_base`와 head의 merge-base.
- **두 모드**
  - 증분(기본): 판정은 `--base`부터의 diff를 본다. 신호는 갈림점 기준으로 한 번 더 돌고 리포트 "증분 범위 밖 누적 신호"에 둔다.
  - 전체(`--full`): base가 갈림점이다. 신호는 리포트 "결정적 신호"에 둔다. `--merge-ref`를 주면 머지 결과와의 비교도 돈다.
- **도구**: 도달성(갈림점에서 불렸는데 head에서 호출 0이 된 정의, 던지는 곳 없는 예외의 핸들러, 시험만 부르는 public), 대체 장부(프로파일 `ledgers`: 지운다·남긴다·이름 바꾼다 행과 문서 줄 참조), 복제본(프로파일 `dependents`: 원천이 바뀌었는데 복제본이 그대로), 피처맵(프로파일 `feature_map`: 기능 문서가 코드보다 낡음). 결과는 `RUN_DIR/signals/`(도구별 JSON과 `summary.md`)에 둔다. diff가 원천을 건드리면 복제본 사본을 `RUN_DIR/replicas/`에 둔다.
  - 이 도구들은 프로젝트가 준비한다(플러그인에 들어 있지 않다). 위치는 환경 변수로 준다: `VERIFY_SIGNAL_BIN`(`reach.mjs`·`ledger-check.mjs`·`co-change.mjs`가 있는 폴더), `VERIFY_FM_BIN`(`fm-check.mjs`가 있는 폴더). 도구마다 신호 JSON v1(`{version: 1, tool, status, note, items[]}`, 항목은 `severity`·`kind`·`symbol`·`message`·`head`·`base`·`docs`)을 `--json <파일>`에 쓴다.
  - 도달성은 Gradle 레포(head 트리에 `build.gradle`·`gradlew`)에서만, 대체 장부·복제본·피처맵은 프로파일에 그 필드가 있을 때만 돈다. 그 밖이면 `skipped`다.
- **점수**: 신호는 점수에 들어가지 않고 판정 범위도 줄이지 않는다. 판정 에이전트가 신호를 코드로 확인해 finding으로 쓰면 그 finding만 3.4의 출처 규칙대로 센다. base 쪽 근거(지워진 호출 줄)는 diff의 삭제 줄이라 `introduced`로 셀 수 있다.
- **도구 실패·미설정**: 실행을 멈추지 않는다. 돌아야 하는 도구가 실패하거나 위치가 설정되지 않았거나 파일이 없으면 `status: error`와 경고로 남고, 그 신호 없이 판정한다.
- **프로파일 점검**: 시작할 때 head 트리에서 아무 파일도 잡지 않는 구조와, 어느 구조에도 안 걸린 동작 변경 파일(프로파일 `coverage_ignore` 제외)을 경고로 남긴다.
- **검증 범위 장부**: 리포트 index에 실행마다 `mode`·`base_sha`(diff의 merge-base)·`fork_point`를, 레포마다 `ranges[]`(`base`·`head`·`run_id`·`mode`)를 쌓는다. PR 게이트는 이것으로 두 가지를 본다.
  - 프로파일 `long_lived_branches`의 브랜치에서 여는 PR은 head SHA에 `mode: full`이고 `base_sha` = merge-base(origin/<PR base>, head)인 리포트가 있어야 지금 규칙(PASS면 통과)으로 넘어간다.
  - 모든 PR의 승인 사유에 PR base..head 중 어느 범위에도 안 든 커밋 수를 적는다(rebase로 SHA가 바뀐 커밋은 patch-id로 맞춘다).
- **이어 돌리기**: 전체 모드는 크다. 한도 등으로 멈추면 `--resume <run_id>`가 같은 실행 폴더를 세션에 다시 등록하고, 끝난 단계는 건너뛴다.

## 4. 점수 산식

기호: finding *f*의 점수 `pts(f)` = 심각도 점수 × 신뢰도 계수. **감점 대상 finding**은 `introduced`·`worsened`이면서 반증에서 기각되지 않은 것이다. 반증으로 심각도가 바뀌었으면 바뀐 심각도를 쓴다.

### 4.1 기준 위험도 (0–100, 높을수록 위험)

```
R(c) = min(100, Σ pts(f))      f ∈ 기준 c의 감점 대상 finding
```

예: confirmed high 1건 = 30 · likely critical 1건 = 42 · confirmed high 2건 = 60

### 4.2 차원 품질 (0–100, 높을수록 좋음)

```
Q(d) = max(0, 100 − Σ w(c) × R(c))      c ∈ 차원 d의 기준, w(c) = 프로파일의 기준 가중치 (기본 1.0)
```

### 4.3 종합 품질

```
Q = Σ W(d) × Q(d) / Σ W(d)      d ∈ 레포에 적용되는 차원, W(d) = 프로파일의 차원 가중치
```

### 4.4 구조 영향도 (0–100, 높을수록 위험)

프로파일의 `structures`는 핵심 구조(예: 결제·취소 실행 경로, 장바구니 UI)를 경로 glob과 중요도(`criticality`, 0–100)로 정의한다.

```
I(s) = min(100, round(criticality(s) × m(s)) + 20 × [구조 s에 medium 이상 감점 finding 존재])

m(s) = 0    구조 s 파일의 동작 변경 줄 수 = 0 (공백·주석만 바뀜)
       0.6  1–10줄
       0.8  11–50줄
       1.0  51줄 이상
```

동작 변경 줄 = 추가·삭제된 줄 중 공백, 주석 전용 줄(프로파일 `comment_syntax`), 프로파일 `ignore_line_patterns`에 맞는 줄(예: import 문)을 뺀 것.

## 5. 판정 규칙

순서대로 적용한다. 기본값은 `config/scoring.json`, 레포·기준·구조별 값은 프로파일이 덮어쓴다(기준별 `weight`·`review_threshold`·`season_review_threshold`, 차원별 `floor`).

| 판정 | 조건 (하나라도 해당) |
|---|---|
| **BLOCK** | ① 감점 대상 `critical`이 `confirmed` 또는 `likely` ② 어떤 차원이든 `Q(d) < 차원 차단선`(기본 60) ③ `Q < 종합 차단선`(기본 70) ④ 평가 불완전(5.1) |
| **REVIEW_REQUIRED** | ① 어떤 기준이든 `R(c) ≥ 기준 검토 임계값`(기본 50, 프로파일에서 기준별 지정) ② 어떤 구조든 `I(s) ≥ 구조 검토 임계값`(기본 60) ③ 반증 결과가 `uncertain`인 high 이상 finding |
| **PASS** | 위 어느 것도 아님 |

BLOCK이어도 리포트는 검토 트리거를 함께 보여 준다(수정 후 무엇을 볼지 미리 알 수 있게).

### 5.1 평가 완전성 (fail-closed)

다음 중 하나라도 해당하면 점수를 내지 않고 **BLOCK(평가 불완전)**으로 끝낸다.

- 적용 대상 차원의 판정 결과 파일이 없거나 스키마가 깨짐
- 판정 결과에 적용 대상 기준 중 상태(`evaluated` / `not-touched`)가 빠진 기준이 있음
- high 이상 finding 중 반증 결과가 없는 것이 있음
- 판정·반증 결과의 `model`이 `claude-opus-5-5`가 아님 (모델 정책, 8장)

## 6. 직접 검토 트리거와 검토 패킷

REVIEW_REQUIRED가 되면 트리거마다 **검토 패킷**을 만든다. 사람이 그 구조만 집중해서 보도록 하는 자료다.

| 항목 | 내용 |
|---|---|
| 트리거 | 기준 위험도 또는 구조 영향도, 임계값, 점수 구성(어느 finding이 몇 점) |
| 구조 요약 | 이 구조가 무슨 일을 하는지, PR이 무엇을 바꿨는지 (3–5줄) |
| 읽는 순서 | `file:line` 목록. 진입점 → 바뀐 핵심 → 영향받는 호출처 순 |
| 흐름도 | 바뀐 흐름의 mermaid 시퀀스/플로 다이어그램 |
| 확인 질문 | 사람이 판단해야 할 질문 3–5개 (정책 결정, 트래픽 가정, 운영값 등) |
| 승인 시 남는 위험 | 이대로 머지하면 감수하게 되는 것 |

PR 생성(`gh pr create`) 시 훅이 현재 HEAD의 리포트를 확인한다. PASS가 아니거나 리포트가 없으면 승인 요청에서 멈춘다(플러그인 `hooks/require-verify-before-pr.mjs`).

## 7. 피크 시즌 모드

`config/scoring.json`의 `season.windows` 기간(연중 최대 트래픽 시즌. 기간은 설정 값)이거나 `/pr-verify --season on`으로 실행하면 적용한다. 변경 동결에 가까운 기간에 검토 문턱을 낮추고 성능·신뢰성 비중을 높이는 모드다.

| 항목 | 평시 | 시즌 |
|---|---|---|
| 기준·구조 검토 임계값 | 프로파일 값 | × 0.8 (기준에 `season_review_threshold`가 있으면 그 값. 예: SEC-04 공급망 20) |
| 차원·종합 차단선 | 프로파일 값 | + 10 |
| 중요도 85 이상 구조 | 영향도 기준 | 동작 변경이 있으면 REVIEW_REQUIRED (변경 동결 성격) |
| 도구별 시즌 보정 | 도구의 평시 값 | 도구에 시즌 값이 있으면 그 값 (예: 설정 스키마 참조 high 기준 템플릿 수를 낮춤) |
| PERF·REL 차원 가중치 | 프로파일 값 | × 1.5 (종합 점수 계산 시) |

## 8. 검증 파이프라인과 모델 정책

| 단계 | 수행자 | 산출물 |
|---|---|---|
| 0. 사전 점검 | `prepare.mjs` | 모델·effort를 덮어쓰는 환경변수(`CLAUDE_CODE_EFFORT_LEVEL`, `CLAUDE_CODE_SUBAGENT_MODEL(+_FORCE)`, `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`)가 정책과 다르면 중단 |
| 1. 준비 | `prepare.mjs` | 대상 해석(브랜치/SHA/PR), base·head 트리 추출(`git archive`, 소스 레포 작업트리는 건드리지 않음), diff, 구조 매핑, 자동 신호, 갈림점 기준 diff 밖 결정적 신호(3.7) |
| 2. 탐색 (필요 시) | `verify-explorer` | 호출 관계, 관련 스펙·설계 원칙 조항, 영향 범위, base 트리의 기존 상태 |
| 3. 판정 | `verify-judge` × 적용 차원 수 | 차원별 finding JSON + 기준별 평가 상태 |
| 4. 반증 | `verify-refuter` | high 이상 finding의 판정: `upheld` / `downgraded` / `rejected` / `uncertain` |
| 5. 채점 | `score.mjs` | 점수, 판정, 트리거 |
| 6. 검토 패킷 | `verify-orchestrator` | 트리거별 패킷 |
| 7. 리포트 | `report.mjs` | `reports/<repo>/<날짜>-<브랜치>-<sha7>.md` + `.json`, `reports/<repo>/index.json`(실행별 모드·base·갈림점, 검증 범위 `ranges[]`) |

**모델 정책**: 2–4, 6단계와 이를 지휘하는 오케스트레이터는 모두 `claude-opus-5-5`, effort `max`로 실행한다. 에이전트 정의 파일(플러그인 `agents/verify-*.md`)에서 모델과 effort를 고정한다. 각 에이전트는 결과에 자기 모델 ID를 기록하고, `score.mjs`는 이 값이 다르면 평가 불완전으로 처리한다. 메인 세션은 스킬을 호출만 하고 판정에 관여하지 않는다.

**테스트 실행 금지**: 검증 파이프라인은 테스트·빌드·애플리케이션을 실행하지 않는다. 테스트가 실제 외부 시스템(운영 스토어·결제 API 등)을 호출할 수 있기 때문이다. 판정은 코드를 읽어서만 한다.

## 9. 재현성과 변경 관리

- 리포트에는 대상·base SHA, merge-base, rubric 내용 해시, 프로파일·scoring 버전, 단계별 모델 ID, 시즌 모드 여부를 기록한다.
- rubric·임계값을 바꾸면 이 문서와 해당 파일의 버전을 올리고, `calibration/`의 보정 케이스를 다시 돌려 탐지율·오탐률 변화를 기록한다.
- 버전 규칙: 기준 삭제·재정의나 산식 변경은 MAJOR, 기준 추가는 MINOR, 문구·예시 수정은 PATCH.
- **역할 분리**: rubric(`rubrics/*.md`)과 이 문서는 레포와 무관한 일반 원칙만 담는다. 파일 경로·레포 이름·벤더 고유 사실·예산 수치 같은 레포 지식은 두지 않는다. 레포 고유 설정(traits, 차원 가중치, 차단선, 핵심 구조, 기준별 가중치·임계값, 도구, 비밀값 스캔, 예산 파라미터)은 레포 프로파일(`profiles/*.json`)에만 둔다. 판정 에이전트는 원칙을 들고 코드를 직접 읽어 판단한다.
