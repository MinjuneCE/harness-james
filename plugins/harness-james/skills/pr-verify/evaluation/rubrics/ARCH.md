# ARCH — 아키텍처

- 버전: 2.0.0 (2026-10-13)
- 적용: 모든 레포 (차원·기준 적용은 레포 프로파일의 traits(server·client)와 dimensions가 정한다)
- 보는 것: 계층·의존 방향, 외부 모델의 경계 번역, 도메인이 상태를 소유하는지, 응집·결합·중복, 설정 설계, 프로젝트 설계 원칙·스펙 정합, 벤더·생성 코드 불가침. 클라이언트는 지역·시장별 분기 **구조**, 데이터 주도 콘텐츠, 명명·위생, 컴포넌트 중복도 본다.
- 보지 않는 것:
  - 런타임 실패 처리(재시도·타임아웃·트랜잭션·동시성·복구), 마이그레이션 안전성, 템플릿·컴포넌트 설정 스키마 호환성 → **REL**
  - 사용자에게 보이는 지역별 가격·프로모션·약관 노출의 **정확성**, 하드코딩 문자열 번역 → **A11Y** (ARCH는 분기 방식만 본다)
  - 환경 변수 예시 동기화·필수 설정 기동 검증·로그 형식 → **OPS** (ARCH는 설정 키를 어떤 타입·위치로 설계했는지만 본다)
  - 서드파티 스크립트 버전 고정·무결성 검증, 렌더 차단 자원 → **SEC**(공급망)/**PERF**
  - 동기 호출 구조의 용량 영향 → **PERF**
  - 테스트 계층·태그 → **TEST**

## ARCH-01 계층·의존 방향

- **적용**: 서버
- **왜 중요한가**: 핵심 업무 규칙이 외부 API·DB 구현을 직접 알면 규칙이 인프라 세부사항과 엉킨다. 외부 API 버전 업그레이드나 복구 로직 추가 때 규칙이 같이 흔들리고, 외부 자원을 대역으로 바꾼 단위 테스트도 어려워진다.
- **판정 기준은 레포가 채택한 구조다.** 헥사고날·클린·레이어드 등 레포가 이미 따르는 계층 구조와 의존 규칙을 코드(패키지 구성, 기존 의존 방향)에서 먼저 확인하고, PR이 그 규칙을 깨는지 본다. 레포에 정해진 구조가 없으면 아래 "핵심 규칙 → 인프라 의존 금지" 원칙만 적용하고, 특정 스타일(포트·use case 인터페이스 등)을 요구하지 않는다.
- **판정 질문**
  - 이 PR이 추가·변경한 핵심 업무 코드가 인프라 구현이나 프레임워크의 영속성·웹·HTTP 타입·예외에 직접 의존하는가?
  - 새 외부 자원 접근(외부 API 조회·DB·시계·분산 잠금)이 레포가 정한 경계(포트·리포지토리 인터페이스·게이트웨이 등)를 거치는가?
  - 새 진입점(컨트롤러·스케줄러·메시지 리스너)이 레포의 기존 진입점과 같은 경로로 업무 로직을 호출하는가?

**체크포인트**
- 도메인·애플리케이션 계층의 import 목록. 허용: 같은 경계의 도메인·애플리케이션, 언어 표준 라이브러리, 로깅 파사드, 빈 등록용 최소 어노테이션.
- 어댑터가 프레임워크 예외(유니크 위반 등)를 애플리케이션 예외로 바꿔 올리는지. 애플리케이션이 프레임워크 예외를 직접 catch하면 위반.
- 스케줄러·워커를 추가하는 PR: 트리거는 진입점 계층에 두고, 대상 선정 쿼리와 외부 상태 조회는 레포의 경계를 거친다. 외부 응답 타입·쿼리 문자열은 인프라 계층 안에서만 쓴다.
- 시계: 현재 시각이 업무 판단(만료·주기 계산)에 쓰이면 주입된 시계로 접근해야 한다. 도메인·애플리케이션에 새 시스템 시계 직접 호출이 생기는지 본다.
- 영속성 매핑 어노테이션이 이미 도메인 엔터티에 붙어 있는 레포라면(실용적 타협), 기존 엔터티에 매핑 필드를 더하는 것은 감점하지 않는다. 새 도메인 타입을 처음부터 영속성 엔터티로 만들면 low.
- 서비스 간 결합: 새 서비스가 기존 서비스의 내부 흐름을 복붙하면 의존 방향이 아니라 중복으로 보고 low~medium. 업무 실행 규칙이 두 벌이 되면 `also_affects: ["REL"]`.

**심각도 앵커**
- critical: (해당 없음. 의존 위반이 이중 실행·금전 손실로 이어지면 그 실패는 REL에 올린다)
- high: 도메인·애플리케이션이 어댑터 구현(외부 API 클라이언트, 리포지토리 구현, 외부 DTO)을 import·호출. 애플리케이션이 새 프레임워크 예외를 catch해 분기
- medium: 새 진입점이 레포가 정한 경계(예: 레포가 use case 인터페이스를 쓰면 그것)를 우회. 핵심 업무 코드에 새 시스템 시계 직접 호출. 경계를 만들지 않고 인프라 구현 메서드를 열어 직접 호출
- low: 계층·컴포넌트 이름이 레포 관례와 다름. 테스트를 구 패키지 구조에 추가

**피크 트래픽 관점**: 피크 대비로 큐·비동기 실행(접수 후 워커 처리)을 도입하는 PR이 나온다. 리스너·워커가 애플리케이션 서비스를 우회해 어댑터·리포지토리를 직접 호출하면 선영속화·직전 재조회 같은 안전 검증을 건너뛴 두 번째 실행 경로가 생긴다. 모든 진입점은 같은 업무 로직 경로를 호출해야 한다.

**근거**: Dependency Inversion Principle, Clean Architecture 의존 규칙(Robert C. Martin), Hexagonal Architecture(Alistair Cockburn) — 특정 스타일은 레포가 채택했을 때만 기준이 된다

## ARCH-02 도메인의 상태 전이·생성 소유

- **적용**: 서버
- **왜 중요한가**: 엔터티의 전이 검증("초기 상태로 되돌리기 불가", "종료 상태 불변", "외부 작업 ID는 처리 중 상태에서만 기록")이 실행 안전을 지킨다. 이를 우회하면 처리 중·실패 건을 다시 실행 가능 상태로 만들 수 있고, 그 결과는 비가역 외부 작업(결제·환불·발송)의 재실행이다.
- **판정 질문**
  - 상태 필드를 엔터티 메서드가 아닌 방법(setter, 일괄 setter 생성 어노테이션, 리플렉션, 직접 UPDATE 쿼리, 생성자 오버로드, 공개 빌더)으로 바꾸는 코드가 추가되는가?
  - 새 상태·전이를 추가할 때 상태 열거·전이 검증·종료 판정을 함께 바꾸고, 종료 상태 정책을 바꾸면 스펙 근거가 있는가?
  - 새 엔터티·값 객체가 정적 팩토리로만 생성되고 초기 상태를 팩토리가 정하는가?

**체크포인트**
- 엔터티의 생성 경로 접근 수준(비공개 빌더, protected 기본 생성자, 초기 상태를 고정하는 팩토리)이 넓어지는지.
- 새 전이 메서드(재시도·만료·수동 검토 등)가 공통 전이 검증을 호출하는지. 검증 없이 필드를 대입하면 위반.
- 상태 외 진행 필드(마지막 확인 시각, 다음 확인 시각, 확인 횟수, 실패 코드)를 갱신하는 메서드도 도메인에 둔다. 서비스가 필드를 직접 다루면 위반.
- 영속성 우회: 리포지토리에 상태를 바꾸는 UPDATE 쿼리를 추가하면 위반. 잠금용 조회(행 잠금·건너뛰기 잠금) 자체는 REL 소관이다.
- 테스트 코드의 리플렉션 상태 주입은 운영 경로가 아니므로 이 기준 위반이 아니다. 운영 코드에 생기면 위반.
- 종료 상태 재개 같은 정책 변경은 도메인 메서드 + 스펙 갱신이 함께 오면 정상. 코드만 오면 ARCH-05와 함께 본다.
- 스타일(low 상한): 값 객체는 불변 타입, 엔터티는 비공개 빌더 + 정적 팩토리.

**심각도 앵커**
- critical: 우회 경로로 처리 중·종료 상태 건을 초기·대기 상태로 되돌릴 수 있고, 실행 경로(처리 서비스·복구 스케줄러)가 그 건을 다시 집어 비가역 외부 작업이 나갈 수 있음 (근거가 실행 경로까지 이어질 때만. 재실행 자체는 REL에도 별도 finding)
- high: 상태 필드 public setter·일괄 setter 생성·리플렉션·UPDATE 쿼리 추가. 스펙 근거 없이 종료 상태에서 전이를 허용하도록 검증 완화
- medium: 새 전이 메서드가 공통 검증을 거치지 않고 스스로 조건을 검사(규칙 분산). 새 엔터티를 public 생성자로 만듦
- low: 정적 팩토리 대신 공개 빌더, 불변으로 둘 값 객체를 가변 클래스로 만듦, 코드 생성 범위 확대(전체 인자 생성자 등)

**피크 트래픽 관점**: 피크 중 실패가 대량 발생하면 운영자가 일괄 재처리를 원한다. "DB에서 상태를 초기 상태로 UPDATE하는 관리 스크립트·엔드포인트"가 PR로 들어오기 쉽다. 외부 작업 ID가 있거나 결과 불명이었던 건까지 되살리면 이중 실행이 난다. critical 후보다.

**근거**: Domain-Driven Design의 Aggregate·불변식(Eric Evans), Tell-Don't-Ask, CWE-841(행위 흐름 강제 미흡)

## ARCH-03 외부 모델 경계 번역과 보수적 매핑

- **적용**: 서버
- **왜 중요한가**: 적격성 판단은 어댑터가 번역한 도메인 상태만 본다. 어댑터가 모르는 외부 값을 "허용" 쪽으로 매핑하면 이미 출고·처리된 건에 비가역 작업이 나간다. 외부 타입이 도메인으로 새어 들어오면 외부 API 변경이 업무 규칙을 직접 흔든다.
- **판정 질문**
  - 외부 API 응답 DTO나 원문 구조(맵·JSON 트리)가 어댑터 밖(포트 시그니처·애플리케이션·도메인·웹 응답)으로 나가는가?
  - 새 외부 값 매핑(상태 변환, 결과 분류)에서 모르는 값의 기본값이 "알 수 없음"이고, 그것이 불허·보류로 이어지는가?
  - 웹 요청·응답 DTO가 애플리케이션·도메인으로 들어가거나, 도메인 엔터티가 그대로 응답 직렬화되는가?

**체크포인트**
- 외부 상태 → 도메인 상태 매핑의 기본 분기가 "알 수 없음"으로 유지되는지. 새 매핑(부분 처리·승인만 된 결제 등 중간 상태)은 스펙 결정이 있어야 한다.
- 적격성 판정 순서에서 "알 수 없음"이 허용 결과에 도달하지 않는지.
- 실행 결과 분류: 응답 누락·작업 ID 누락은 "결과 불명"이어야 한다. 새 분기가 이를 성공·실패로 낙관 분류하면 위반. 결과를 덜 낙관적으로 바꾸는 것(오류 필드를 더 읽어 거부 처리)은 개선.
- 포트 시그니처가 도메인 타입·원시 타입만 쓰는지. 외부 API 전용 예외·HTTP 상태 타입이 포트 밖으로 던져지지 않는지.
- 외부 오류 메시지 원문 문자열을 결과 객체에 담는 정도는 DTO 누출로 보지 않는다.
- 웹 경계: 엔터티 → 응답 DTO 변환 계층을 유지. 새 조회 API가 엔터티를 그대로 반환하거나 내부 식별자를 노출하면 ARCH low + `also_affects: ["SEC"]`.

**심각도 앵커**
- critical: 모르는·중간 상태를 허용 쪽으로 매핑해 실행 가능 판정에 도달하는데 스펙 결정이 없음. 결과 불명을 성공·실패로 낙관 분류해 확인 조회를 건너뜀
- high: 외부 DTO·원문 구조가 포트 시그니처·애플리케이션·도메인으로 나감. 외부 상태 문자열 비교가 애플리케이션·도메인에 생김
- medium: 어댑터 전용 예외를 애플리케이션이 catch해 분기. 웹 DTO가 애플리케이션 메서드 파라미터로 들어감. 새 열거 값을 추가하면서 "알 수 없음" 기본 처리 누락
- low: 엔터티를 그대로 응답 직렬화, 변환 메서드 이름·위치가 레포 관례와 다름

**피크 트래픽 관점**: 피크 직후 부분 처리·보류·분할 결제 건 비율이 늘어난다. "불가 응답이 많다"는 운영 압력으로 매핑을 완화하는 핫픽스가 피크 중에 들어오기 쉽다. 이 기준은 그런 PR을 스펙 결정 없이는 critical로 막는 것이 목적이다.

**근거**: Anti-Corruption Layer(Domain-Driven Design), Fail-safe defaults(Saltzer & Schroeder), OWASP ASVS V1 아키텍처, CWE-636(Not Failing Securely)

## ARCH-04 설정·의존성 설계

- **적용**: 서버
- **왜 중요한가**: 업무 정책(환불·재고·알림 여부 등)이 설정값인 경우가 많다. 설정을 어떤 타입·바인딩으로 설계하느냐가 "미설정이면 실제 처리 0건" 같은 운영 사고를 좌우한다. 외부 API 버전·엔드포인트를 코드에 박으면 외부 버전 수명 주기마다 배포가 필요하다.
- **판정 질문**
  - 새 설정을 타입 있는 설정 묶음(+ 필요 시 검증)으로 묶었는가, 개별 주입·환경 직접 조회·하드코딩 상수로 흩뿌렸는가?
  - 업무 **정책값**을 코드 상수나 코드 기본값으로 넣었는가(설정으로 외부화해야 함)?
  - 외부 API 버전·엔드포인트·호스트·자격증명 경로가 코드에 하드코딩되는가? 새 런타임 의존성에 설계 문서·PR 본문 근거가 있는가?

**체크포인트**
- 새 설정 묶음은 기존 설정 묶음과 같은 위치·형식으로 둔다.
- 정책 기본값을 코드에 박으면 운영값 결정을 코드가 대신한다 → medium(값 자체의 영향은 REL).
- 미설정 처리 방식(기동 실패 vs 런타임 실패 기록)은 정책 결정이다. 어느 쪽이든 스펙 근거가 있으면 정상.
- 외부 클라이언트를 새로 만들 때 API 버전을 설정에서 받는지. 버전 리터럴이 보이면 위반.
- 새 HTTP 클라이언트 인스턴스를 직접 생성하면 공통 타임아웃·관측 설정을 걸 수 없다. 프레임워크가 구성한 빌더·팩토리를 주입받는지 본다(타임아웃 부재 자체는 REL).
- 설정 로딩 방식과 키 형식이 맞는지(예: 환경 변수 형식 키를 속성 파일처럼 읽어 바인딩이 안 되는 경우). 의심되면 `possible`로 적는다.
- 의존성: 회복성·분산 잠금·보안·큐 라이브러리 등 새 런타임 의존성은 근거를 남겨야 한다. 근거가 레포 밖에 있어 확인할 수 없으면 `possible`.
- 버전 관리: 의존성 BOM·버전 카탈로그가 관리하는 라이브러리 버전을 직접 덮어쓰면 low.

**심각도 앵커**
- critical: (해당 없음)
- high: 외부 API 버전·호스트·자격증명 경로를 코드에 하드코딩. 업무 정책값을 설정 없이 코드 상수로 고정
- medium: 묶음 설계 없이 개별 설정 주입, 정책값에 코드 기본값 부여, 근거 없는 새 런타임 의존성
- low: 설정 prefix·키 이름이 레포 관례와 다름, BOM 관리 라이브러리 버전 직접 지정

**피크 트래픽 관점**: 피크 대비로 타임아웃·재시도·풀 크기 설정이 추가된다. 값이 코드 상수면 피크 중 조정에 재배포가 필요하다. 설정으로 외부화했는지를 본다(값의 적정성은 REL·PERF). 레포 프로파일 `parameters`에 기준값이 있으면 그것과 비교하고, 없으면 가정을 시나리오에 적고 confidence를 likely 이하로 둔다.

**근거**: The Twelve-Factor App III(Config)·II(Dependencies), OWASP ASVS V14 구성, CWE-798(하드코딩된 자격증명)

## ARCH-05 설계 원칙·스펙 정합

- **적용**: 공통
- **왜 중요한가**: 레포에 설계 원칙 문서(아키텍처 결정, 헌장)와 기능 스펙이 있으면, 원칙 위반은 이유를 남겨야 하고 스펙과 다른 동작은 다음 기능의 잘못된 전제가 된다. 미결 정책을 코드가 조용히 결정하면 아무도 그 결정을 추적할 수 없다.
- **판정 질문**
  - PR이 구현하는 기능의 스펙 요구사항·수용 시나리오와 어긋나는 동작이 있는가? 미결로 남은 정책을 코드가 임의로 결정하는가?
  - 레포 설계 원칙의 필수(MUST) 위반이 들어오는데 PR 본문·설계 문서에 정당화가 없는가?
  - 레포가 스펙 → 설계 → 작업 순서를 요구하는데 새 기능을 그 없이 구현하는가?

**체크포인트**
- 레포에 스펙·원칙 문서가 없으면 PR 본문·연결된 이슈와의 정합만 본다.
- 미결 정책의 대표 유형: 실패·거부 건 재요청 허용, 이미 처리된 상태 처리, 정책 기본값, 미설정 기동 실패, 대기 최대 시간, 장기 처리 중 건 종료, **결과 불명 건 재전송 조건**, 다중 인스턴스 잠금.
- 결정이 스펙에 반영됐는지(같은 PR 또는 링크된 문서 변경) 확인. 스펙이 레포 밖에 있으면 PR 본문의 결정 기록("결정: …")을 인정한다.
- 원칙 위반 자체는 해당 기준(ARCH-01·02·03, REL, OPS)에 올린다. 이 기준에는 "정당화 없이 들어온 위반"이나 "스펙과 다른 동작"만 올린다(중복 금지).
- 정의만 있고 아무도 쓰지 않는 예외·핸들러처럼 미결 결정의 흔적이 있으면, 그것을 활성화하는 PR은 결정 근거를 함께 요구한다.
- 기존 위반이 많아도 새 위반은 정당화하지 않는다.
- 커밋 메시지·브랜치 규칙은 **OPS**(변경 추적성) 소관이다.

**심각도 앵커**
- critical: (해당 없음. 스펙과 다른 동작이 금전 손실·전면 장애를 만들면 REL에 올린다)
- high: 미결인 **돈·종료 정책**을 근거 없이 코드로 결정. 구현 동작이 스펙의 필수 요구와 반대
- medium: 원칙 필수 위반을 정당화 없이 도입(정당화 누락이 별개 문제일 때만). 스펙 없이 새 기능(엔드포인트·스케줄러) 구현. 돈과 무관한 정책(응답 코드, 사유 노출)을 근거 없이 결정
- low: 구현과 스펙의 용어·이름 불일치, 요구사항 추적표를 갱신하지 않음

**피크 트래픽 관점**: 시즌 중에는 "일단 막고 나중에 스펙 정리" 핫픽스가 늘어난다. 핫픽스라도 결정한 정책(예: 대기 만료 시간)을 PR 본문에 남기면 medium 이하로 본다. 남기지 않으면 시즌 후 아무도 그 결정을 추적할 수 없다.

**근거**: Architecture Decision Records(Michael Nygard), ISO/IEC/IEEE 29148 요구사항 추적성

## ARCH-06 벤더·생성 코드 불가침

- **적용**: 공통
- **왜 중요한가**: 벤더가 배포하는 코드(테마·프레임워크 코어 번들, vendored 라이브러리)를 직접 고치면 업스트림 업데이트를 머지할 수 없고 수정이 조용히 사라진다. 도구·앱이 생성하는 파일은 다음 생성 때 덮어써진다. 수동 사본으로 관리되는 파일 쌍은 한쪽만 바꾸면 일부 화면만 다르게 동작한다.
- **판정 질문**
  - 벤더 코어 번들, vendored 코드, 도구·앱 생성 파일을 이 PR이 추가·수정·삭제하는가?
  - 수동 사본으로 유지되는 파일 쌍(같은 레이아웃의 변형 등)이 있으면, 한쪽 변경이 다른 쪽에도 같은 의미로 반영됐는가?
  - 커스텀 동작·스타일이 레포가 정한 확장 위치에 들어갔는가? 서드파티 위젯 내부 DOM·클래스·이벤트를 레포 코드로 덮어쓰거나 재사용하는가?

**체크포인트**
- 벤더 코드 diff는 거의 항상 위반이다. 예외: 공식 버전 업그레이드 PR(버전 표기 변경 동반). 이때는 info로 두고 REL·PERF 영향을 본다.
- 생성 파일 diff의 출처 판별: 봇·동기화 커밋(자동 작성자, 동기화 메시지)이면 사람이 고친 게 아니다. 반증에서 rejected 또는 info로 낮춘다. 생성물에 없는 로직·주석 추가, 일부 줄만 수정 같은 수작업 흔적이면 유지한다.
- 생성 파일 여부가 이름 패턴만으로 추정되면 confidence는 `possible`.
- 사본 파일 쌍은 전역 자원·스크립트·렌더 목록이 같은지 diff로 비교한다. 한쪽 전용 차이만 고친 경우는 info.
- 벤더 코어 파일이 아닌 벤더 제공 컴포넌트에 커스텀 로직을 직접 넣는 것은 이 기준이 아니라 ARCH-09 관점이다.
- 벤더가 제공하는 확장 패턴(커스텀 엘리먼트, 부분 렌더링 엔드포인트, 플러그인 훅)이 있으면 그것을 확장한다. 별도 경로를 새로 만들면 ARCH-09.
- 서드파티 내부 클래스를 강제 우선순위 스타일로 덮어쓰거나, 다른 서드파티의 이벤트 이름을 재사용해 결합하면 medium.

**심각도 앵커**
- critical: (해당 없음. 벤더 코드 수정으로 핵심 구매·실행 흐름이 실제로 깨지면 그 동작 결함은 REL에 별도 finding)
- high: 벤더 코어 코드 직접 수정. 생성 파일 수동 수정·삭제. 레이아웃 쌍 중 한쪽에 전역 스크립트·자원·노출 차단 로직을 추가하고 다른 쪽 미반영
- medium: 커스텀 코드를 지정된 확장 위치 밖(새 전역 자원, 벤더 번들 끝에 덧붙임 등)에 둠. 서드파티 DOM 강제 오버라이드·이벤트 재사용 신규. 사본 쌍의 비기능 변경(주석·접근성 보정) 미반영
- low: 커스텀 코드에 출처·이유 주석 없음

**피크 트래픽 관점**: 피크 직전 서드파티 설정 변경과 핫픽스가 겹친다. 벤더·생성 코드를 손으로 고치면 피크 중 재생성·벤더 패치 때 수정이 사라진다. 레포 프로파일이 해당 구조의 중요도를 높게 두면 시즌 모드에서는 건드리기만 해도 REVIEW_REQUIRED다.

**근거**: Open-Closed Principle, 생성 코드 직접 수정 금지 관행, OWASP Top 10 A06(취약하고 오래된 구성요소)

## ARCH-07 지역·시장별 분기 구조 (선언적 설정 우선)

- **적용**: 클라이언트
- **왜 중요한가**: 지역·시장별 차이를 표현하는 방식이 여러 가지(선언적 설정 상속, 코드 내 국가 비교, 접미사 파일 복제, 콘텐츠 데이터) 섞이면 "이 지역에 무엇이 보이는가"를 한 곳에서 답할 수 없다. 새 분기가 또 다른 방식으로 들어오면 지역별 프로모션 교체 때 누락이 생긴다.
- **판정 질문**
  - 지역별 차이를 플랫폼의 선언적 지역 설정·상속으로 표현했는가?
  - 템플릿 코드에 새 국가·지역 코드 비교나 국가 목록을 추가했는가? 꼭 필요하면 목록을 한 곳(공용 조각·콘텐츠 데이터)에 모았는가?
  - 지역 접미사를 붙인 컴포넌트·템플릿을 새로 복제했는가?

**체크포인트**
- 새 지역 설정 파일: 상속 대상이 실제로 존재하는지(렌더 영향은 REL). 지역 식별자가 레포의 지역 목록에 있는지(없으면 고아 파일 → ARCH-08).
- 국가 비교: 국가 코드를 직접 비교하거나 변수로 받아 비교하는 줄. 같은 국가 목록을 컴포넌트마다 하드코딩하는 패턴이 퍼지는지.
- 파일 복제: 새 지역 접미사 파일이 기존 세트를 복사한 것인지. 차이가 문구·금액뿐이면 콘텐츠 데이터 + 지역 설정으로 표현 가능하다(ARCH-08 연계).
- 배열 인덱스로 지역을 매핑하면 순서 계약이 주석·문서로 명시돼 있는지.
- 공통 노출 차단 로직이 있으면 재사용하는지, 컴포넌트마다 새로 만드는지.
- 지역 식별자를 캠페인 이름처럼 쓰는 패턴(지역 ≠ 캠페인)을 새로 만들지 않는지.
- 범위 밖: 표시되는 금액·통화·약관이 지역에 맞는지 → A11Y.

**심각도 앵커**
- critical: (해당 없음)
- high: 레이아웃·전역 컴포넌트(헤더, 카트, 상품 상세)에 국가 하드코딩 분기를 추가해 모든 페이지·구매 흐름 동작이 국가별로 갈림(선언적 설정으로 표현 가능한데 코드로 분기)
- medium: 새 국가 비교·국가 목록 하드코딩. 새 지역 접미사 복제 세트. 인덱스 매핑 순서 계약 누락(피해가 국소적이라 medium)
- low: 기존 복제 세트에 같은 패턴으로 지역 하나를 추가하면서 PR 본문에 사유 기재

**피크 트래픽 관점**: 시즌 프로모션은 지역마다 시작·종료 시각과 할인율이 다르다. 하드코딩·복제로 들어온 시즌 컴포넌트는 전환·종료 때 파일 여러 개를 동시에 고쳐야 하고, 하나라도 빠지면 특정 지역에 지난 프로모션이 남는다. 같은 캠페인 PR의 지역 복제 파일은 한 finding으로 묶어 medium을 유지한다(파일마다 따로 올리지 않는다).

**근거**: W3C Internationalization Best Practices, Single Source of Truth, DRY(The Pragmatic Programmer)

## ARCH-08 데이터 주도 콘텐츠·명명·위생

- **적용**: 클라이언트
- **왜 중요한가**: 같은 페이지의 날짜별 사본과 같은 의미의 구·신 데이터 필드가 섞이면, 템플릿을 복제할수록 스키마 변경 영향 범위(REL)와 시즌 캠페인 교체 작업량이 늘어난다. 명명 규칙을 어기면 지역·날짜 기준 정리·검색이 불가능해진다.
- **판정 질문**
  - 새 상품·프로모션 텍스트·미디어를 구조화된 콘텐츠 데이터로 주입했는가, 템플릿 설정값·코드 하드코딩으로 넣었는가?
  - 새 데이터 참조가 레거시 네임스페이스·필드를 쓰는가(현행 대체가 있는데)?
  - 새 템플릿·파일 이름이 레포 명명 규칙(소문자·숫자·하이픈, 유형·슬러그·지역·날짜 순서)을 따르는가? 테스트용 템플릿, 공백·대문자 이름, 지역 목록에 없는 지역 파일을 추가하는가?

**체크포인트**
- 새 템플릿이 기존 템플릿의 날짜 사본인지: 같은 슬러그의 다른 날짜 사본이 이미 있는지 확인. 차이가 데이터로 표현 가능한 텍스트·이미지뿐이면 medium(복제는 최후 수단).
- 레거시 데이터 참조: 코드의 신규 참조와, 편집기가 재직렬화한 설정 파일의 참조를 구분한다. 설정 파일은 base에 같은 참조가 있었는지 비교해 새 참조만 올린다.
- 가격·정가·할인 배지를 텍스트 설정으로 입력받는 컴포넌트는 데이터 주도 위반(ARCH) + 가격 정확성(A11Y)으로 나눠 올린다.
- 특정 상품·컬렉션 식별자를 코드에 하드코딩하는 신규 추가.
- 절대 URL: 사이트 내부 링크에 운영 도메인·플랫폼 기본 도메인을 박으면 지역·언어 경로가 깨진다. 라우팅 헬퍼·상대 경로를 쓴다. 생성 파일은 제외(ARCH-06).
- 레거시 정리 PR은 개선이다(`fixed`). 삭제 대상의 참조 확인은 REL.

**심각도 앵커**
- critical: (해당 없음)
- high: (해당 없음. 명명·데이터 주도 위반은 단독으로 구매 흐름을 깨지 않는다)
- medium: 데이터로 표현 가능한 차이를 날짜 사본으로 복제. 코드에 새 레거시 필드 참조. 텍스트·가격을 설정에 하드코딩하는 새 컴포넌트 스키마. 테스트 템플릿 커밋. 지역 목록에 없는 지역 파일 추가
- low: 공백·대문자 파일명, 슬러그 축약이 관례와 다름, 편집기 성격의 설정 파일에 새 레거시 참조, 내부 절대 URL

**피크 트래픽 관점**: 시즌 캠페인 템플릿은 매년 새 날짜 사본으로 만들어지기 쉽다. 지난 시즌을 복제하는 대신 콘텐츠 데이터로 시즌 값을 바꾸는 구조인지 본다. 피크 직전 "복제 후 수정" PR은 low~medium으로 남기되, 이전 시즌 사본 정리 계획을 적으면 low.

**근거**: Separation of Content and Presentation, DRY(The Pragmatic Programmer), W3C Cool URIs don't change

## ARCH-09 컴포넌트 중복·재사용

- **적용**: 클라이언트
- **왜 중요한가**: 같은 역할의 컴포넌트(상품 카드, 목록 섹션, 위젯 UI)가 여러 벌 있으면 버그 수정·접근성 보정·동작 변경을 사본마다 따로 해야 하고, 화면마다 같은 동작(담기·추가)이 다르게 구현된다. 사본이 늘수록 핫픽스 누락 확률이 커진다.
- **판정 질문**
  - 기존 컴포넌트를 복사해 접미사(버전·시즌·new·old)를 붙인 새 파일을 만드는가? 기존 것을 설정·블록·파라미터로 확장할 수 있었는가?
  - 템플릿 언어의 deprecated 포함 방식(암묵적 변수 공유)을 새로 쓰는가? 명시적 파라미터 전달 방식으로 바꿀 수 있는가?
  - 카트·빠른 추가·업셀 갱신에 기존 공통 패턴(부분 렌더링·공용 컴포넌트) 대신 새 fetch·DOM 조립 경로를 만드는가?

**체크포인트**
- 새 파일이 기존 같은 역할 컴포넌트와 얼마나 같은지 diff로 비교한다. 대부분 같으면 복제로 본다(비율은 판단, evidence에 비교 결과를 적는다).
- 시즌 변형은 기존 컴포넌트에 설정·블록으로 배지·가격 표시를 추가하는 방식이 가능한지 본다.
- 신·구 구성 파일이 같은 역할로 공존하는지(구 버전을 지우지 않고 새 버전 추가).
- deprecated 포함 방식: 정적 분석 도구 finding이 있으면 이 기준에 따로 올리지 않는다(중복 금지). 동적 포함 대상 누락 위험은 REL.
- 부분 렌더링 API에 요청당 한도가 있으면, 새 경로가 한도를 피하려 요청을 쪼개는 것은 PERF.
- 반대 방향(사본 통합·삭제)은 `fixed`로 기록한다. 참조 확인은 REL.

**심각도 앵커**
- critical: (해당 없음)
- high: (해당 없음. 복제본의 동작이 원본과 달라 핵심 흐름이 깨지면 REL)
- medium: 이미 중복된 컴포넌트 가족에 새 사본 추가. 카트·빠른 추가에 공통 패턴을 우회하는 새 fetch·렌더 경로
- low: 새 deprecated 포함(도구 finding이 없을 때만), 같은 마크업 블록을 두 곳에 복붙, 주석 처리된 이전 구현을 남김

**피크 트래픽 관점**: 시즌 카드·시즌 목록 섹션은 시즌 후 미사용으로 남기 쉽다. 같은 패턴의 새 시즌 사본이 들어오면 medium으로 올리고 recommendation에 "시즌 설정으로 통합"을 적는다.

**근거**: DRY(The Pragmatic Programmer), Composition over Inheritance, Martin Fowler "Refactoring"(Duplicated Code)
