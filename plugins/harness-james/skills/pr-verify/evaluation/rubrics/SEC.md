# SEC — 보안·프라이버시

- 버전: 2.0.0 (2026-10-13)
- 적용: 모든 레포 (차원·기준 적용은 레포 프로파일의 traits(server·client)와 dimensions가 정한다)
- 보는 것: 누가 어떤 리소스·데이터에 손댈 수 있는가(인증·인가·IDOR), 신뢰할 수 없는 입력이 쿼리·HTML·URL로 흘러가는가(인젝션·XSS·오픈 리다이렉트), 비밀정보와 개인정보가 코드·로그·응답·서드파티 스크립트로 새는가, 클라이언트에 새 코드가 어떤 경로로 들어오는가(공급망·운영자가 넣는 임의 코드·서드파티 통합), 동의 전 트래킹, 남용 방지(호출량 제한·CORS·관리 엔드포인트·서명 검증).
- 보지 않는 것:
  - 로그 **형식**(구조화 여부, 메시지 언어, 컨텍스트 키 누락) → OPS. 로그·예외·응답에 **무엇이 담기는지**(토큰·응답 본문·PII)는 SEC-07.
  - 호출량 제한·스로틀의 **용량**(외부 API 쿼터, 커넥션 풀, 피크 처리량) → PERF. 제한이 **남용 방지 장치로 존재하는지**는 SEC-08.
  - 외부 스크립트의 **로딩 비용**(렌더 차단, 비동기 로드, 자산 크기) → PERF. 버전 고정·무결성 검증·출처·데이터 접근 범위는 SEC-04.
  - 인증 실패·소유자 불일치 **메트릭·알림** → OPS. 실패 경로 테스트 유무 → TEST.
  - 멱등 응답·상태 전이의 정합성 → REL. 다만 멱등 응답이 **다른 사용자의 요청 정보를 돌려주는 것**은 SEC-01.
  - 접근성 속성, 번역 경유 → A11Y. 벤더가 배포하는 코드를 직접 수정하는 것 자체 → ARCH. 그 수정이 스크립트를 주입하면 SEC-04에도 `also_affects`.
  - 환경변수 예시 파일의 키 동기화 → OPS. 예시 파일에 **실제 값**이 들어가는 것은 SEC-05.

- **SEC-01 = 1.5 / 30**: 인가 결함 1건이 곧 금전 손실(남의 주문·결제·환불 조작)이나 대량 개인정보 노출이다. confirmed high 1건(30점)만 나와도 사람이 보도록 30. 가중치 1.5면 high 1건으로 차원 품질이 55가 되어 차단선(60) 아래로 내려간다. 인증 경로에 손대는 PR은 사람 검토를 거치게 하려는 의도다.
- **SEC-03 = 1.5 / 30**: 클라이언트 XSS는 모든 방문자에게 영향을 준다(세션 기반 요청 위조, 계정 페이지 접근, 결제 전 피싱 오버레이). confirmed high 1건에서 검토.

- 나머지는 기본값(1.0 / 50).

## SEC-01 호출자 인증과 리소스 소유자 인가

- **적용**: 서버
- **왜 중요한가**: 돈이 움직이거나 개인정보를 돌려주는 API를 "식별자만 알면 누구나" 호출할 수 있으면 곧 IDOR이다. 순차 숫자처럼 추측 가능한 식별자라면 대량 악용도 쉽다. 새 엔드포인트나 조회 API가 같은 구멍을 넓히면 금전 손실과 개인정보 노출이 생긴다.
- **판정 질문**:
  1. 이 PR이 추가·변경한 엔드포인트(라우팅, 필터·미들웨어, 인증 예외 경로 포함)는 **외부 조회·저장·부수효과 전에** 호출자를 인증하는가?
  2. 사용자 대리 호출이면 **인증된 사용자 ID와 리소스 소유자 ID를 대조**하는가? 기존 요청을 돌려주는 멱등 경로에서도 대조하는가?
  3. 플랫폼·외부 시스템이 서명하는 요청(웹훅, 프록시 경유 요청)이면 서명을 원문 기준으로 검증하는가?

**호출자 유형별 요구사항 (조건부 판정)**

PR이 도입하는 호출자 유형에 해당하는 행만 적용한다. 유형이 PR에서 드러나지 않으면 "호출자 유형 미정"을 `info` finding으로 남기고 공통 요구사항만 본다.

| 호출자 유형 | 필수 검증 | 위반 시 |
|---|---|---|
| **공통** | 인증 실패는 401, 외부 조회·저장 **이전**에 거부. 인증 우회 경로(전체 허용, 필터 제외)는 헬스체크 등 명시 목록으로만 | 인증 누락 → critical |
| **서명된 쿼리·프록시 요청** | ① 서명 파라미터를 뺀 나머지를 정해진 규칙(정렬·결합)대로 정규화해 공유 비밀로 HMAC 계산, **상수 시간 비교**. ② 로그인 사용자 식별 값이 비어 있으면 비로그인으로 보고 사용자 대리 작업 거부(정책 확정 전까지). ③ 그 사용자 식별 값과 리소스 소유자 대조. 서명은 변조만 막을 뿐 소유를 증명하지 않는다. ④ 타임스탬프 재전송 허용 범위 검사(권장) | ①③ 누락 → critical, ④ 누락 → medium |
| **세션 토큰·JWT** | 서명 검증(허용 알고리즘 고정, `none` 거부), `exp`/`nbf`, `aud`(이 앱), 발급 대상·테넌트 검증. `jti`로 재전송 방지(권장). 사용자 식별은 **토큰 클레임**만 신뢰하고 바디·쿼리의 사용자 ID는 무시. 브라우저 교차 출처 호출이면 SEC-08 출처 제한과 함께 본다 | 서명·주체 대조 누락 → critical, `aud`·테넌트 누락 → high |
| **서비스 간 호출 (서비스 토큰·API 키)** | 키는 환경변수로 주입(SEC-05), 상수 시간 비교, 호출자 식별자를 요청 기록에 저장. 서비스 호출자는 사용자 대리가 아니므로 소유자 대조 대신 **허용 테넌트·허용 작업 범위**를 제한 | 키 검증 누락 → critical, 하드코딩 키 → SEC-05 |
| **웹훅** | 서명 헤더를 **원문 바디(raw bytes)** 기준으로 검증. 역직렬화한 객체를 다시 직렬화해 검증하면 안 된다. 중복 전달은 전달 ID로 거름(REL과 공유) | 서명 미검증 → critical(위조 웹훅으로 상태 확정 가능), 재직렬화 검증 → high |

**체크포인트**
- 새 라우트·핸들러가 인증 정보(헤더·서명·토큰)를 받는지, 어디서 검증하는지(필터·미들웨어·인자 해석기).
- 서비스 계층이 **기존 건을 반환하기 전에** 소유자를 대조하는가. 기존 요청이 있어도 소유자 검증이 먼저다.
- 두 ID를 **같은 형식으로 정규화**해 비교하는가(전역 ID 문자열 vs 숫자). 형식이 달라 항상 불일치하는 것은 REL 소관이고, 한쪽이 null이면 통과하는 분기는 SEC critical이다.
- 소유자 없는 리소스(비회원 등)를 통과시키는 분기: 정책이 정해지기 전엔 거부가 기본.
- 소유자 불일치 응답이 리소스 존재 여부·상태·이름을 담으면 열거가 가능하다. 403/404 선택 자체는 정책 문제다.
- 관리·재처리·복구 API는 사용자 인증과 **분리된** 운영자 인증이 있는가. 네트워크 위치("내부망이라 괜찮다")만으로 보호하면 high.
- 스케줄러·메시지 리스너는 인증 대상이 아니지만, 외부에서 트리거하는 엔드포인트가 붙으면 위 규칙을 적용한다.
- 헬스체크 공개용 전체 허용, 무상태 토큰 API의 CSRF 보호 해제는 그 자체로 결함이 아니다. 허용 범위가 명시 목록을 넘는지, 쿠키 인증과 섞이는지를 본다.
- 인증이 아직 없는 기존 경로에 **새 엔드포인트**를 더하면, 새 엔드포인트 자체는 `worsened`가 아니라 `introduced`다.

**심각도 앵커**
- critical: 인증 없이 부수효과·조회가 가능한 새 경로, 소유자 대조 누락으로 사용자 A가 사용자 B의 리소스를 조작·조회, 서명 검증이 항상 통과하는 구현(비교 결과 무시, 예외를 삼키고 진행), 웹훅 서명 미검증.
- high: 멱등 경로(기존 건 반환)에서만 소유자 대조가 빠짐, 소유자 불일치 응답이 리소스 상태·이름을 노출, 토큰 `aud`·테넌트 미검증, 재직렬화 바디로 서명 계산, 관리 API를 네트워크 위치로만 보호.
- medium: 서명 비교가 상수 시간이 아님, 타임스탬프 재전송 검사 없음, 호출자 식별자를 요청 기록에 남기지 않음.
- low: 인증 실패 응답이 실패 원인(서명 불일치 vs 토큰 만료)을 구분해 알려 줌.

**피크 트래픽 관점**: 인증·인가가 약하면 트래픽 폭증기에 봇이 추측 가능한 식별자를 돌며 대량 부수효과(취소·환불 등)를 건다. 즉시 실행되는 금전 작업은 되돌리기 어렵고, 피크 기간 지원 인력이 감당하지 못한다. "피크 동안 성능 때문에" 서명 검증을 끄는 플래그를 추가하면 high 이상.

**근거**: OWASP Top 10 2025 A01 Broken Access Control, A07 Authentication Failures · ASVS 5.0 V6 Authentication, V8 Authorization, V9 Self-contained Tokens · CWE-639 (Authorization Bypass Through User-Controlled Key), CWE-345, CWE-208 (Observable Timing Discrepancy) · RFC 8725 JWT Best Current Practices

## SEC-02 입력 검증과 인젝션 방지

- **적용**: 서버
- **왜 중요한가**: 요청 값이 외부 API 쿼리 변수·DB 쿼리·다른 시스템의 메모 필드로 그대로 흘러간다. 쿼리 문자열 연결이 생기면 인젝션으로 다른 필드·다른 리소스에 대한 조작이 가능해진다.
- **판정 질문**:
  1. 새 쿼리(SQL·GraphQL·검색 DSL 등)가 **변수·파라미터 바인딩만** 쓰는가(문자열 연결·포맷 함수 없음)?
  2. 외부 입력(바디·경로·쿼리·헤더)에 형식·길이·허용값 검증이 있는가? 리소스 식별자는 기대하는 리소스 종류의 형식인가?
  3. 요청 DTO가 서버가 결정해야 할 필드를 받는가?

**체크포인트**
- 쿼리 문서는 상수 + 변수 바인딩. 쿼리 실행 함수에 넘기는 쿼리 인자가 런타임 조합 문자열이면 의심한다.
- 식별자 형식 검증: 여러 리소스 종류가 같은 식별자 체계를 쓰면(전역 ID 등) **다른 리소스 종류의 ID**가 통과하지 않는지. 숫자 ID와 전역 ID를 둘 다 받으면 변환 로직도 본다.
- 선택형 값은 허용 목록(enum). 자유 텍스트는 길이 제한, 그리고 외부 시스템 화면에 표시되는 필드로 그대로 보내도 되는지.
- 경로 변수로 구조화된 식별자를 받으면 URL 인코딩된 구분자(`%2F`) 처리와 검증 누락.
- 검증 트리거(프레임워크의 검증 활성화 표시)를 빼면 DTO 제약이 전부 무력화된다. 리팩터링으로 위치만 옮긴 것인지 확인한다.
- Mass assignment: 요청 DTO를 엔터티로 바로 바인딩하거나, DTO에 상태·소유자 ID·서버 생성 ID 같은 서버 결정 필드를 추가.

**심각도 앵커**
- critical: 쿼리에 요청 값을 문자열로 연결(다른 리소스·필드 조작 가능), 요청 바디로 소유자 ID·상태를 받아 그대로 신뢰(SEC-01과 겹치면 SEC-01에 올리고 `also_affects`).
- high: 핸들러에서 검증 트리거 제거, 식별자 형식 검증 없이 다른 리소스 종류의 ID가 부수효과 호출 변수로 들어갈 수 있는 경로.
- medium: 새 입력 필드에 길이 제한 없음(컬럼 길이 초과 시 500), 허용 목록 없이 임의 문자열을 외부 시스템으로 전달.
- low: 검증 메시지가 내부 필드명·정규식을 그대로 노출.

**근거**: OWASP Top 10 2025 A05 Injection · ASVS 5.0 V1 Encoding and Sanitization, V2 Validation and Business Logic · CWE-89, CWE-943 (Improper Neutralization in Data Query Logic), CWE-915 (Mass Assignment) · OWASP Input Validation Cheat Sheet

## SEC-03 클라이언트 출력 인코딩·DOM XSS·오픈 리다이렉트

- **적용**: 클라이언트
- **왜 중요한가**: 페이지에서 실행되는 스크립트는 같은 오리진의 세션·카트·계정 데이터에 접근한다. 반사형·DOM XSS는 캠페인 링크(UTM, 프로모 코드 파라미터)로 대량 유포가 쉽고, 저장형은 모든 방문자에게 영향을 준다.
- **판정 질문**:
  1. 사용자가 조종할 수 있는 값(검색어, URL 파라미터, 주문 메모·속성, 사용자 프로필, 리뷰·UGC)을 HTML 속성·본문에 **문맥에 맞는 인코딩 없이** 출력하는가?
  2. 서버 템플릿 값을 `<script>` 안에 넣을 때 JSON 직렬화를 쓰는가(따옴표로 감싼 문자열 보간 금지)?
  3. JS가 `location.search/hash`, `fetch` 응답, `postMessage` 데이터를 `innerHTML`·`insertAdjacentHTML`·`document.write`·`eval`·`location` 대입으로 보내는가?

**체크포인트**
- 템플릿 출력: 속성 안 출력은 이스케이프가 기본. 엔진의 자동 이스케이프 여부가 문서로 확인되지 않으면 명시적 이스케이프를 정상으로 본다.
- "HTML 허용" 번역 키·문자열에 사용자 값을 보간하면 high.
- `<script>` 블록: 값은 JSON 직렬화로. 따옴표 안 보간은 `'`·`</script>`로 탈출 가능.
- `innerHTML`에 넣는 값이 같은 오리진 서버가 렌더한 HTML 조각인지, URL·사용자 입력인지 구분. 전자는 허용, 후자는 `textContent`로.
- 리다이렉트: 대상이 URL 파라미터에서 오면 **같은 오리진 상대 경로인지**(`/`로 시작하고 `//`·`\`로 시작하지 않음, 또는 `new URL(x, location.origin).origin === location.origin`) 확인. 고정 접두사 + 현재 pathname만 쓰는 리다이렉트는 오픈 리다이렉트가 아니다. `?return_to=`, `?redirect=` 값을 그대로 쓰는 것은 위반.
- `href`에 사용자 값: `javascript:` 스킴 차단 필요(HTML 이스케이프로는 막히지 않음).
- 계정·주문 페이지: 주소·이름 출력 이스케이프, 다른 사용자 데이터 참조 없음.
- 벤더가 배포하는 코드는 레포에서 고치지 않으므로 그 안의 기존 패턴은 판정 대상이 아니다. PR이 직접 고쳤다면 ARCH에 올리고, 고친 내용이 XSS면 여기서도 판정.

**심각도 앵커**
- critical: 저장형 XSS. 다른 사람이 보는 페이지에 사용자 입력(리뷰, UGC, 공유 데이터)을 이스케이프 없이 출력.
- high: 반사형·DOM XSS(URL 파라미터 → `innerHTML`/속성/스크립트), 오픈 리다이렉트, HTML 허용 번역 키에 사용자 값 보간, `<script>` 안 따옴표 보간에 사용자 값.
- medium: 자기 자신에게만 보이는 값(메모, 항목 속성)의 이스케이프 누락(self-XSS, 공유 링크로 확장 가능성), 자동 이스케이프가 확인되지 않은 사용자 값을 이스케이프 없이 새로 출력(`likely`).
- low: 상수·관리자 설정값을 이스케이프 없이 속성에 출력(관리자만 조작 가능), `target="_blank"`에 `rel="noopener"` 누락.

**피크 트래픽 관점**: 캠페인 직전에는 URL 파라미터로 프로모 코드·배너 문구·지역을 바꾸는 랜딩을 급히 만든다. 반사형 XSS 하나가 SNS·이메일 캠페인 링크와 섞여 대량 유포될 수 있다. 파라미터를 화면에 그대로 찍는 "프로모 코드 표시" 류 코드는 피크 직전 PR에서 특히 본다.

**근거**: OWASP Top 10 2025 A05 Injection · ASVS 5.0 V1 Encoding and Sanitization, V3 Web Frontend Security · CWE-79, CWE-601 (Open Redirect) · OWASP Cross Site Scripting Prevention / DOM based XSS Prevention Cheat Sheet

## SEC-04 코드 주입 경로와 공급망

- **적용**: 공통
- **왜 중요한가**: 클라이언트에 외부 스크립트 한 줄을 넣으면 그 CDN·벤더가 페이지 전체를 실행 권한으로 갖는다. 플로팅 버전은 상위 패키지가 바뀌는 순간 검토 없이 새 코드가 실행된다. 서버에서는 동적 의존성 버전·신뢰할 수 없는 저장소가 빌드 산출물을 바꾼다.
- **판정 질문**:
  1. 새 외부 스크립트·스타일이 **정확한 버전**으로 고정되어 있는가? 변경 불가능한 URL이면 SRI(`integrity` + `crossorigin`)가 있는가?
  2. 운영자가 관리 화면에서 임의 코드(HTML·스크립트·템플릿)를 넣는 경로를 새로 만들거나, 막혀 있던 출력을 다시 활성화하는가?
  3. 새 서드파티 통합(앱·위젯·플러그인)이 어떤 데이터(사용자·카트·주문)에 접근하는지 PR에 근거가 있는가?
  4. 새 의존성이 고정 버전·공식 저장소·알려진 취약점 확인을 거쳤는가?

**체크포인트**
- 외부 `<script src>`/`<link href>`: 버전 고정(`pkg@1.2.3`), HTTPS, 출처 도메인. `@latest`, `@N`, `@N.x.x`는 위반. 가능하면 자체 자산으로 내려받아 서빙.
- SRI: 레포에 SRI 관행이 없으면 버전 고정 URL의 SRI 누락은 low로만. **버전 미고정 + SRI 없음**은 medium 이상.
- 플랫폼이 주입하는 헤더·스크립트 블록을 변형·필터링해 제거·치환하는 것은 금지. 내용 포함 여부 검사만 허용.
- 관리자 임의 코드 경로: 새 설정 스키마에 HTML·코드 타입 추가, 비활성화된 출력의 재활성화. 재활성화는 이미 저장된 모든 값을 한꺼번에 렌더하므로 저장된 값의 범위를 근거로 판단한다.
- 서드파티 통합을 새로 켜면 PR에 이름, 접근 데이터 범위, 동의 연동 여부(SEC-06)를 적었는가.
- 같은 레이아웃·진입점이 여러 벌이면 외부 스크립트 변경이 모두에 반영됐는가(한쪽만 고정하면 다른 쪽에 플로팅 버전이 남음). 동기화 누락 자체는 ARCH.
- `eval`, `new Function`, `document.write` 추가.
- 결제 단계가 클라이언트 스크립트를 실행하지 않는 구조라면, 카드 스키밍보다 카트 조작·피싱 오버레이·사용자 정보 수집이 현실적인 피해다.
- 의존성 선언: 동적 버전(`+`, `latest`, 범위, 스냅샷)은 위반. BOM·플랫폼이 관리하는 버전 생략은 허용.
- 저장소: 로컬 저장소, HTTP 저장소, 승인된 미러 외 임의 URL 추가.
- 빌드 도구 래퍼·배포판 URL 변경 시 공식 출처인지, 체크섬이 있는지.
- 의존성 잠금·취약점 스캔이 없는 레포면 "알려진 취약점 확인 여부"는 PR 설명의 근거로만 판정한다.

**심각도 앵커**
- critical: 출처가 불명확하거나 개인 소유 도메인의 스크립트를 전 페이지(공통 레이아웃)에 추가, 플랫폼 주입 스크립트를 변형해 제거·치환.
- high: 플로팅 버전 외부 스크립트를 공통 레이아웃·전역 컴포넌트에 추가, 관리자 임의 코드 출력 재활성화, 전역에서 쓰이는 컴포넌트에 임의 코드 설정 추가, HTTP 스크립트, 동적 의존성 버전·신뢰할 수 없는 저장소.
- medium: 플로팅 버전을 특정 페이지 전용 컴포넌트에 추가, 사용자·카트 데이터에 접근하는 서드파티 통합을 근거 없이 활성화, `eval`/`new Function`/`document.write` 추가, 새 의존성의 취약점 확인 근거 없음.
- low: 버전 고정된 외부 스크립트에 SRI 없음, 외부 스타일시트 추가 시 출처 기술 부족.

**피크 트래픽 관점**: 피크 직전에는 카운트다운·스핀휠·팝업 같은 외부 위젯이 급히 붙는다. 플로팅 버전 CDN은 피크 중 상위 릴리스로 동작이 바뀌어도 변경 이력에 남지 않는다. 피크 중 외부 스크립트 변조는 최대 방문자에게 바로 노출되므로, 시즌 모드에서는 공통 레이아웃의 외부 스크립트 추가를 중요도 높은 구조 변경으로 본다.

**근거**: OWASP Top 10 2025 A03 Software Supply Chain Failures, A08 Software or Data Integrity Failures · ASVS 5.0 V3 Web Frontend Security, V15 Secure Coding and Architecture · CWE-829 (Inclusion of Functionality from Untrusted Control Sphere), CWE-494, CWE-1104 · W3C Subresource Integrity · SLSA

## SEC-05 비밀정보 관리

- **적용**: 공통
- **왜 중요한가**: 외부 플랫폼 client secret과 발급된 관리 토큰은 곧 주문·환불·데이터 변경 권한이다. 클라이언트로 배포되는 코드·설정은 사실상 공개 자산이므로 여기 들어간 키는 모두 공개된 것으로 봐야 한다.
- **판정 질문**:
  1. diff에 실제 비밀값(토큰, client secret, 비밀번호, 개인키, 비공개 API 키)이 있는가?
  2. 비밀값이 환경변수·버전 관리 제외 파일로만 들어오고, 설정 파일에 실제 값이 커밋되지 않는가?
  3. 비밀값을 담는 객체가 문자열 표현·직렬화·캐시·예외 메시지로 새지 않는가?

**체크포인트**
- 설정 파일: 환경변수 참조만 허용. 기본값 문법에 실제 값 금지.
- 환경 파일(예시 파일 제외) 추가, 무시 목록에서 환경 파일 제거.
- 예시 파일: 변수 이름과 자리표시자만.
- 로컬 개발용 컨테이너 설정의 평문 비밀번호: **새로 추가**하거나 같은 값을 운영·스테이징 설정에 재사용하면 위반. 환경변수 참조로 바꾸면 `fixed`.
- 비밀을 담는 값 객체: 언어·도구가 자동 생성하는 문자열 표현(record·data class·자동 toString)은 모든 필드를 포함한다. 이 객체를 로그·예외 메시지에 넣는 변경은 high. 문자열 표현을 마스킹으로 재정의하면 `fixed`.
- 토큰 캐시: 메모리 외 DB·파일·외부 캐시에 평문 저장을 추가하면 저장 위치의 접근 통제·암호화 근거가 있는가.
- 테스트의 명백한 가짜 값은 허용. 실제 발급 형식(벤더 접두사 + 고정 길이 값 등)은 위반.
- 서명 검증용 secret을 **코드 상수**로 두면 critical.
- 클라이언트 레포: 저장된 설정·스키마 기본값·컴포넌트에 API 키·토큰. 공개 키(지도 키, 공개 API 토큰)도 저장소 기본값은 비운다. 비공개·관리 토큰이 클라이언트에 들어가면 critical. 서드파티가 설정값을 요구해도 공개 키만 허용.
- 연결 문자열에서 전송 구간 암호화를 끄는 옵션(로컬 기준)을 운영 설정에 그대로 쓰면 medium.

**심각도 앵커**
- critical: 실제 관리 액세스 토큰·client secret·개인키·운영 DB 비밀번호 커밋, 비공개 토큰을 클라이언트(공개 자산)에 넣음, 서명 검증용 secret을 코드 상수로.
- high: 환경 파일 커밋(값 확인 불가여도), 비밀을 담은 객체를 로그·예외 메시지로 출력하는 경로 추가, 토큰을 평문으로 영속 저장, 무시 목록에서 환경 파일 제거.
- medium: 로컬 설정에 새 평문 비밀번호 추가, 공개 키를 클라이언트 저장소 기본값으로 커밋, 운영 연결에서 전송 암호화 해제.
- low: 테스트에 실제 형식처럼 보이는 가짜 값 사용(스캐너 오탐 유발).

**피크 트래픽 관점**: 피크 장애 대응 중 "급히" 토큰을 설정 파일에 박거나 디버깅용으로 토큰 로그를 켜는 핫픽스가 나온다. 시즌 중 이런 diff는 critical/high를 그대로 유지하고 완화하지 않는다.

**근거**: OWASP Top 10 2025 A02 Security Misconfiguration, A04 Cryptographic Failures · ASVS 5.0 V13 Configuration, V14 Data Protection · CWE-798 (Hard-coded Credentials), CWE-312, CWE-532 · 12-factor App III Config · OWASP Secrets Management Cheat Sheet

## SEC-06 개인정보 최소화와 동의 전 트래킹

- **적용**: 공통
- **왜 중요한가**: 동의가 필요한 지역(EU·UK 등) 방문자에게 분석·마케팅 쿠키나 식별자 전송을 동의 전에 하면 GDPR/UK GDPR(및 ePrivacy) 위반이다. 사용자 이메일·전화·주소를 분석 도구로 보내면 개인정보 유출로 본다. 서버는 사용자 ID·주문 정보·자유 텍스트를 다루므로 응답·저장 범위를 최소화해야 한다.
- **판정 질문**:
  1. 새 트래킹·분석·마케팅 스크립트(픽셀, 태그 매니저, 세션 리플레이, 이메일 마케팅 도구)가 **동의 확인 후에만** 로드·전송되는가?
  2. 사용자 식별자·PII를 제3자로 보내는가? 보낸다면 어떤 값인가(내부 ID vs 이메일·전화·이름·주소)?
  3. 새 응답·저장 필드·외부 조회에 필요 이상의 PII가 들어가는가?

**체크포인트**
- 동의 확인: 플랫폼·CMP의 동의 API로 분석·마케팅 목적을 **구분해** 확인하고, 동의 변경 이벤트에 반응한다. 레거시·단일 불리언 동의 API를 새 코드에서 쓰면 low.
- 동의 배너·동의 연동 컴포넌트를 제거·비활성화하는 변경은 대체 수단을 PR에 적었는가(관리 설정이라 저장소로 확인할 수 없으면 `possible`).
- 동의 연동이 내장된 이벤트·픽셀 샌드박스가 있으면 그것이 기본. 인라인 픽셀 추가는 동의 게이트가 있어야 한다.
- 식별자 판단 기준:
  - 내부 숫자 ID를 분석 도구 사용자 ID로 보내는 것은 **가명 식별자**다. 동의 게이트 없이 보내면 medium.
  - 이메일·전화·이름·주소를 분석·세션 리플레이·광고 도구로 보내면 high.
  - 해시한 이메일도 개인정보다. 광고 전환용 해시는 마케팅 동의 확인이 필수.
- 서드파티 통합의 자체 동의 연동 여부는 저장소로 확인할 수 없는 경우가 많다. 새로 켜는 PR은 연동 여부를 PR에 적었는지만 본다.
- 세션 리플레이가 계정·주소 페이지를 마스킹 없이 기록하는 설정 변경.
- 금전 가치가 있는 비밀 코드(기프트카드·쿠폰 코드)가 렌더되는 페이지에 새 서드파티 스크립트를 추가하면 high. 계정 페이지에 추가하면 medium 이상.
- 서버 응답에 사용자 ID·자유 텍스트·연락처를 추가하면 필요성 근거가 있는가.
- 외부 조회에 쓰지 않는 PII 필드를 추가하면 medium(접근 범위·권한도 늘어남).
- 새 PII 컬럼은 보존 기간·삭제 경로(삭제 요청·플랫폼 삭제 이벤트 대응) 근거가 있어야 한다. 없으면 medium.
- 사용자가 개인정보를 적을 수 있는 자유 텍스트를 외부 시스템·로그로 새로 보내면 medium.

**심각도 앵커**
- critical: 사용자 이메일·주소·전화를 대량으로 외부 도메인에 목적 외 전송, 다른 사용자 PII가 응답에 섞임(SEC-01과 겹치면 SEC-01).
- high: PII를 분석·광고 도구로 전송, 동의 게이트 없는 마케팅 픽셀을 공통 레이아웃에 추가, 동의 배너·연동 제거, 비밀 코드 페이지에 서드파티 스크립트 추가.
- medium: 가명 ID를 동의 게이트 없이 전송, 특정 페이지 한정 분석 스크립트를 동의 게이트 없이 추가, 쓰지 않는 PII 조회·저장, 보존·삭제 근거 없는 PII 컬럼.
- low: 레거시 동의 API 사용, 새 서드파티 통합의 동의 연동 여부 기술 누락.

**피크 트래픽 관점**: 캠페인 측정을 위해 광고 픽셀·전환 스크립트가 급히 추가되는 시기다. 동의 필요 지역 트래픽이 커질수록 동의 전 전송 건수도 비례해 늘어난다. 캠페인 PR에 "동의 확인 후 로드" 근거가 없으면 시즌 중에도 완화하지 않는다.

**근거**: GDPR Art. 5(1)(c) 데이터 최소화, Art. 6·7 동의 · ePrivacy Directive Art. 5(3) · CCPA/CPRA · OWASP Top 10 2025 A01(과다 노출) · ASVS 5.0 V14 Data Protection · CWE-359 (Exposure of Private Personal Information)

## SEC-07 오류·로그·응답을 통한 민감정보 노출

- **적용**: 서버
- **왜 중요한가**: 외부 API 오류 응답 본문, 토큰 발급 요청 바디(client secret 포함), 쿼리 변수(자유 텍스트)가 로그·예외 메시지·API 응답으로 새면 비밀정보와 PII가 로그 수집 시스템·호출 측 화면까지 퍼진다. 토큰·시크릿·PII를 로그에 남기지 않는 것은 기본 요구사항이다.
- **판정 질문**:
  1. 새 로그·예외 메시지·오류 응답 본문에 토큰, client secret, 외부 응답 본문, 요청 바디, 사용자 PII가 들어가는가?
  2. 처리하지 않은 예외가 기본 오류 응답으로 내부 정보(스택 트레이스, 예외 메시지, SQL)를 노출하는 경로를 추가하는가?
  3. HTTP 클라이언트 요청·응답 로깅(인터셉터, wire 수준 로그 레벨)을 켜서 인증 헤더·바디가 찍히는가?

**체크포인트**
- 외부 오류 본문 전체를 보관하는 예외: 그 본문을 로그·오류 응답·결과 객체·DB 컬럼에 넣으면 위반. 상태 코드·오류 코드만 기록하는 것이 기준.
- 예외 메시지 전달: 지금은 오류 코드만 찍더라도, PR이 예외 메시지를 로그·응답·DB에 쓰기 시작하면 외부 오류 문구와 HTTP 클라이언트 예외 메시지(요청 URL 포함 가능)가 그대로 나간다 → medium.
- HTTP 클라이언트 예외의 응답 본문 접근자·문자열 표현을 로그로 남기면 high. 토큰 발급 실패 예외에는 form 바디가 포함될 수 있다.
- 로그 레벨: HTTP 클라이언트·wire 로거를 DEBUG/TRACE로 올리는 설정은 high(헤더·바디 기록).
- 오류 응답 detail에 내부 예외 메시지(무결성 위반의 SQL 등)를 넣으면 medium. 호출자 본인 입력을 반사하는 것은 low.
- 프레임워크 오류 응답 옵션(스택 트레이스·메시지·예외 포함)을 항상 켜면 high.
- 사용자 PII 로그: 자유 텍스트, 이메일·이름·주소를 로그에 넣으면 high. 내부 사용자 ID를 PII로 볼지 정책이 없으면 medium으로 판정하고 확인 질문으로 남긴다. 호출자 식별자 기록이 요구사항이면 허용.

**심각도 앵커**
- critical: 관리 액세스 토큰·client secret이 로그·응답에 출력되는 경로(운영 로그 수집 시스템까지 퍼짐).
- high: 외부 응답 본문·HTTP 클라이언트 예외 본문을 로그로 출력, wire 로깅 활성화, 자유 텍스트·연락처를 로그로 출력, 오류 응답에 스택 트레이스 포함.
- medium: 예외 메시지를 API 응답·DB에 그대로 저장·반환, 내부 예외 메시지를 오류 응답으로 반환, 사용자 ID를 근거 없이 로그에 추가.
- low: 호출자 입력값을 오류 메시지에 그대로 반사.

**피크 트래픽 관점**: 피크 중 외부 API 429·5xx가 늘면 오류 경로 로그가 폭증한다. 응답 본문을 찍는 오류 로그는 평시엔 드물어도 피크엔 대량으로 쌓여 로그 저장소·외부 로그 서비스로 PII가 퍼진다(로그 양 자체는 OPS/PERF).

**근거**: OWASP Top 10 2025 A09 Security Logging and Alerting Failures, A10 Mishandling of Exceptional Conditions · ASVS 5.0 V14 Data Protection, V16 Security Logging and Error Handling · CWE-209 (Error Message Containing Sensitive Information), CWE-532 (Sensitive Information in Log File) · OWASP Logging Cheat Sheet

## SEC-08 남용 방지와 노출 표면 (호출량 제한·CORS·관리 엔드포인트)

- **적용**: 서버
- **왜 중요한가**: 요청 1건이 동기 외부 호출 여러 번으로 불어나는 API는 남용 방지가 없으면 봇이 반복 호출로 외부 API 예산을 소진시킨다. 잘못된 CORS는 다른 사이트에서 로그인한 사용자의 브라우저로 부수효과 요청을 보내게 만든다. 관리·진단 엔드포인트의 과다 노출은 환경변수(비밀)·힙 덤프를 내준다.
- **판정 질문**:
  1. 새 공개 엔드포인트에 호출자·IP·사용자 단위 호출량 제한이 있는가(또는 앞단 게이트웨이에서 처리한다는 근거가 있는가)?
  2. CORS 허용 출처가 명시 목록인가(`*` 금지, 자격증명 허용 시 와일드카드 금지)?
  3. 관리·진단 엔드포인트 노출 범위가 헬스·기본 정보를 넘는가? 상세 정보가 인증 없이 열리는가?

**체크포인트**
- 호출량 제한: 필터·미들웨어 또는 PR 설명의 게이트웨이 근거. 한도 값(처리량)은 PERF, **존재 여부와 키(사용자·IP·호출자)**는 여기서 본다. 공개 엔드포인트를 새로 열면서 제한도 근거도 없으면 medium.
- CORS: 인자 없는 허용 표시(= 모든 출처), 와일드카드 출처·패턴, 자격증명 허용 + 넓은 패턴. 허용 출처는 실제 클라이언트 도메인 목록만. 임베드 UI처럼 교차 출처로 오는 호출은 어디서든 올 수 있다고 가정하고 출처 제한과 SEC-01 토큰 검증을 함께 요구한다.
- CORS 설정이 아예 없으면 브라우저 교차 출처 호출이 막히므로 그 자체로 노출은 아니다.
- 같은 오리진 프록시를 경유하는 구조면 CORS가 필요 없다. 그 상태에서 CORS를 넓게 열면 우회 경로가 생긴다.
- 관리·진단 엔드포인트: 전체 노출, 환경·설정 덤프(비밀 노출), 힙·스레드 덤프, 런타임 로그 레벨 변경, 종료, 라우트·컴포넌트 목록. 헬스 상세 항상 공개. 별도 관리 포트 없이 공개 포트로 노출.
- 비용이 큰 경로(재처리 트리거, 대량 조회)를 공개 엔드포인트로 노출.
- 봇 대응: 사용자 대리 작업은 로그인 세션·토큰으로 묶는 것이 1차 방어다. 비로그인 작업을 열면 CAPTCHA·이메일 확인 같은 추가 방어가 필요하다.

**심각도 앵커**
- critical: 환경·설정 덤프·힙 덤프를 인증 없이 노출(비밀·토큰 유출), 자격증명 허용 + 와일드카드 CORS + 쿠키 기반 인증 조합(CSRF형 부수효과).
- high: 부수효과 API에 와일드카드 CORS, 관리 엔드포인트 전체 노출, 로그 레벨 변경 공개, 인증 없는 비용 큰 관리 엔드포인트.
- medium: 새 공개 엔드포인트에 호출량 제한도 근거도 없음, 헬스 상세 항상 공개, 비로그인 작업을 열면서 봇 방어 없음.
- low: CORS 허용 메서드·헤더가 필요 이상으로 넓음.

**피크 트래픽 관점**: 피크에는 정상 트래픽만으로도 외부 API 예산이 빠듯하다(용량은 PERF). 이때 호출량 제한 없는 공개 엔드포인트는 소수의 남용 클라이언트만으로 정상 사용자의 요청을 막을 수 있다. 피크 대비로 "제한을 일시 해제"하는 설정 플래그를 추가하면 medium 이상.

**근거**: OWASP Top 10 2025 A02 Security Misconfiguration, A06 Insecure Design · OWASP API Security Top 10 2023 API4 Unrestricted Resource Consumption · ASVS 5.0 V3 Web Frontend Security(CORS), V4 API and Web Service, V13 Configuration · CWE-770, CWE-942 (Permissive Cross-domain Policy), CWE-215
