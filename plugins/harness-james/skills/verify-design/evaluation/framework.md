# 설계 검증 프레임워크

- 버전: 0.2.1 (2026-10-16)
- 대상: 구현 전 설계 문서 묶음(명세·계획·데이터 모델·계약·작업·시나리오·결정 기록 등). 어떤 프로젝트·도메인에도 쓴다
- 기준 본문: [`rubrics/`](rubrics/) · traits: [`traits.md`](traits.md) · 프로파일 필드: [`profile-schema.md`](profile-schema.md) · 합성 예시: [`../test/fixtures/bundle-a/profile.json`](../test/fixtures/bundle-a/profile.json)
- 형제 시스템: PR 검증 `/verify`. 심각도·신뢰도 척도를 맞췄다

이 문서는 설계 검증이 **무엇을 보고, 무엇을 결함으로 올리고, 어떻게 판정하는지**를 정한다. 검증 절차·순서·에이전트 구성은 정하지 않는다. 그것은 실행(스킬) 쪽 몫이다.

---

## 1. 범위

### 1.1 보는 것

- 문서 사이의 일관성: 용어·ID·값·상태·결정이 묶음 전체에서 같은가
- 추적성과 필요성: 요구마다 설계·작업·검증이 있는가, 설계 요소마다 원 요구가 있는가
- 요구 품질: 측정 가능성, 미해결 자리표시, 실패 동작 명세
- 결정과 근거: 대안·결과·가역성, 결정 상태, 원칙 정합
- 근거와 가정: 출처 위계, 외부 동작 주장의 근거, 수치 근거, 환경 전제
- 행위 모델: 상태×이벤트, 불변식, 진행, 경합, 중복, 정리 작업, 충돌 지점, 요구 경로 실현 가능성
- 실패·복구 정책: 의존 실패, 결과 불명, 타임아웃·재시도, 오류 처리, 사람 개입
- 품질 속성·위협·출시·운영 감지의 **설계 수준 존재와 일관성**
- 묶음 위생: 정본, 기준 시점, 참조, ID 체계, 구현 가능성, 분량

### 1.2 보지 않는 것

- 코드. 코드가 설계대로인지는 `/verify`가 본다
- 외부 사실의 참·거짓 자체. 설계 검증은 "주장에 1차 출처가 붙었나, 없으면 미확인으로 표시됐나"까지만 판정한다. 참·거짓은 외부 조회(X) 또는 사람(H)이 정한다
- 문체·서식·맞춤법. 의미를 바꾸지 않는 것은 올리지 않는다
- 사업 판단(무엇을 만들지). 원 요구는 주어진 것으로 본다. 단, 원 요구에 없는 것을 설계가 더했는지는 본다(TRC-03·04)

### 1.3 `/verify`와의 경계

| 영역 | 설계 검증 | `/verify` |
|---|---|---|
| 문서 간 일관성·추적성·요구 품질 | 맡음 (CON·TRC·REQ·BND) | 안 봄 |
| 결정·가정·외부 사실 근거 | 맡음 (DEC·EVD) | ARCH가 코드와 스펙의 정합만 |
| 상태 기계 완전성·불변식·경합 | 설계 수준 (BEH) | REL이 코드의 런타임 안전성 |
| 타임아웃·재시도·멱등성 | 정책의 존재·일관성 (FLR·BEH-05) | 코드가 정책대로인지 (REL) |
| 위협 | 신뢰 경계·위협 범주·대응의 요구화 (THR) | 코드 수준 인가·입력 검증 (SEC) |
| 성능·용량 | 용량·한도 가정 (QAS) | 쿼리·자산·호출 비용 (PERF) |
| 운영 | 출시·호환·감지 신호 설계 (RUN) | 로그·메트릭·배포 준비 구현 (OPS) |
| 테스트 | 검증 방법의 존재와 판별력 (TRC-02·RUN-04) | 테스트 코드 적정성 (TEST) |
| 접근성·i18n | 사용자 화면 요구의 존재 (REQ) | 마크업·리소스 (A11Y) |

- 차원 코드는 `/verify`의 SEC·PERF·ARCH·REL·OPS·TEST·A11Y와 겹치지 않는다.
- 연결: 설계 검증을 통과한 불변식·상태표·정책 값은 `/verify` 판정 에이전트가 "스펙 정합" 근거로 읽을 수 있다.

## 2. 차원

| 코드 | 차원 | 기준 수 | 주로 켜는 traits |
|---|---|---:|---|
| `CON` | 문서 간 일관성 | 7 | multi-doc |
| `TRC` | 추적성·필요성 | 5 | 공통 |
| `REQ` | 요구 품질 | 5 | 공통 |
| `DEC` | 결정·근거 | 5 | 공통 |
| `EVD` | 근거·가정 | 6 | 공통, external-integration |
| `BEH` | 행위 모델 | 8 | state-machine, concurrent-actors, async-events |
| `FLR` | 실패·복구 | 5 | external-integration |
| `QAS` | 품질 속성 | 4 | 공통 |
| `THR` | 위협 | 4 | trust-boundary |
| `RUN` | 출시·운영 | 4 | 공통, data-migration, automation |
| `BND` | 묶음 위생 | 6 | multi-doc, agent-authored |

합계 59개. 기준 적용은 기준의 "적용"(`공통` 또는 traits)과 프로파일 `design.traits`로 고른다. `공통`은 항상, trait 기준은 프로파일에 그 trait가 켜졌을 때만 적용한다. 여러 trait가 적힌 기준은 하나라도 켜지면 적용한다.

**중복 금지**: 한 문제는 가장 구체적인 기준 하나에만 올린다. 다른 기준에도 걸리면 `also_affects`에 적는다.

## 3. 기준 필드

rubric의 각 기준은 아래 필드를 갖는다.

| 필드 | 뜻 |
|---|---|
| ID | `<차원>-NN`. 한 번 정하면 바꾸지 않는다 |
| 적용 | `공통` 또는 trait 목록 |
| 범위 | 다시 검증할 단위. `절`: 바뀐 절만 다시 본다. `문서`: 문서 하나가 바뀌면 그 문서 전체를 본다. `묶음`: 어느 문서든 바뀌면 묶음 전체를 본다 |
| 왜 중요한가 | 깨지면 생기는 일 (1–3줄) |
| 판정 질문 | 예/아니오로 답하는 질문 1–3개. "아니오"가 결함 후보다 |
| 체크포인트 | 개념 수준의 확인 항목 |
| 검사 방법 | `S` 스크립트(기계적 추출·대조) · `L` LLM 판단 · `X` 외부 조회 · `H` 사람만 가능. 주된 것을 앞에 |
| 스크립트 추출 대상 | `S`가 있으면 무엇을 뽑는지(ID, 참조, 수치, 용어, 중복 내용 등). LLM은 추출된 충돌·후보만 판단한다 |
| 심각도 앵커 | 4장 척도를 그 기준의 언어로 구체화 |
| 근거 요구 | 이 기준의 finding이 반드시 달아야 할 근거 |
| 잡는 결함 범주 | 결함 이력 범주 C01–C13 (README 커버리지표) |
| 근거 출처 | 외부 레퍼런스 키와 등급(A/B) |

## 4. 심각도와 신뢰도

### 4.1 심각도 (모든 차원 공통, `/verify` 3.2와 같은 점수)

| 심각도 | 점수 | 설계 단계 정의 | 예 |
|---|---:|---|---|
| `critical` | 60 | 이대로 구현하면 금전 손실·데이터 손상·개인정보 유출·핵심 사용자 흐름 전면 장애가 현실적 시나리오로 생긴다. 또는 프로젝트 원칙의 MUST 위반, 또는 되돌릴 수 없는 결정이 근거 없이 확정됨 | 결과 불명 시 비가역 호출을 다시 보내는 설계 · 비가역 부작용이 근거 없는 외부 동작 가정에 기댐 · 부작용 있는 (상태, 이벤트) 빈칸이 비가역 결과로 이어짐 |
| `high` | 30 | 특정 조건에서 critical 수준 피해. 구현자가 추측해야 하는 핵심 동작 빈칸. 문서끼리 상충하는 요구. 측정 불가한 보안·정합·성능 속성. 원 요구 없이 상태·경로·알림이 여러 문서로 퍼진 장치 | 문서마다 다른 타임아웃 값 · 폐기된 설계가 작업 목록에 남음 · 요구 원문 없는 예외 처리 경로 |
| `medium` | 12 | 제한적 피해, 구현·운영 부담 증가, 경계 사례 미명세, 용어 드리프트, 비기능 커버리지 누락 | 같은 개념의 동의어 혼용 · 미확인 항목에 영향 평가 없음 |
| `low` | 4 | 개선 권장. 의미에 닿지만 오해 가능성이 작음 | 낡은 참조 한 곳 · 번호 없는 결정 문단 |
| `info` | 0 | 참고. 확인 질문, 의도적 위험 수용의 재확인 | — |

각 rubric 기준의 "심각도 앵커"가 이 척도를 구체화한다. 앵커가 없는 심각도는 그 기준에서 쓰지 않는 것이 기본이다. 쓰면 이유를 `rationale`에 적는다.

### 4.2 신뢰도 (`/verify` 3.3과 같은 계수)

| 값 | 계수 | 설계 단계 조건 |
|---|---:|---|
| `confirmed` | 1.0 | 묶음 안의 인용만으로 결함이 끝까지 보인다(두 문서의 상충 문장, 빈칸이 표 전수로 확인됨 등) |
| `likely` | 0.7 | 근거는 있지만 외부 사실, 작성자 의도, 묶음 밖 문서에 달려 있다 |
| `possible` | 0.4 | 의심 수준. 확인 질문으로 남긴다 |

- 외부 사실에 기대는 finding(EVD-02 등)은 외부 출처 링크가 없으면 `possible` 이하다.
- 부재형 finding(빈칸·누락)은 찾아본 곳 목록이 묶음 전체를 덮을 때만 `confirmed`다.

### 4.3 변경 상태 (`scope_state`)

바뀐 곳만 다시 검증할 때 쓴다. `/verify`의 origin에 해당한다.

| 값 | 뜻 | 판정 반영 |
|---|---|:-:|
| `changed` | 이번 검증 대상 변경(새 버전·바뀐 절) 안에 근거가 있다 | ● |
| `carried` | 바뀌지 않은 곳에 이미 있던 결함이다 | ● (전체 검증일 때) / 참고 (증분 검증일 때) |
| `resolved` | 이전 검증의 finding이 이번 변경으로 해소됐다 | — (리포트 "해소") |

## 5. 근거 규칙

1. **위치 + 원문 인용**: finding마다 `문서 경로 + 절(제목) + 줄` 과 원문 인용을 단다. 인용은 문서에 실제로 있는 문자열이어야 한다. 인용을 못 찾으면 finding을 철회한다.
2. **부재형**: 빈칸·누락은 인용 대신 `searched`(찾아본 문서·절 목록, 쓴 검색어)와 `result: 없음`을 단다. 찾아본 곳이 좁으면 신뢰도를 낮춘다.
3. **상충형**: 두 문서가 어긋나면 양쪽 인용을 모두 단다. 어느 쪽이 정본인지(BND-01, 프로파일 `bundle`)를 함께 적는다.
4. **외부 사실**: 외부 시스템 동작에 대한 판정은 프로파일 `external_sources`에 맞는 1차 출처 위치를 단다. 없으면 `possible` 이하로 두고 "외부 확인 필요"로 표시한다.
5. **스크립트 추출 결과**: `S` 검사 결과를 근거로 쓰면 추출 결과의 해당 행(값·위치)을 그대로 인용한다. LLM은 추출된 충돌·후보만 판단하고, 추출 결과에 없는 값을 지어내지 않는다.
6. **요구 연결**: 모든 finding은 `touches`에 그 결함이 닿는 것을 적는다. 원 요구 ID·문장, 정확성 속성(불변식·안전 속성), 또는 원칙 MUST 중 하나다. 아무것에도 닿지 않으면 올리지 않는다(6장).

## 6. 과잉 지적 방지

- **닿는 것만 올린다**: 정확성(구현했을 때 틀린 동작·데이터)이나 명시 요구(원 요구·원칙·명시된 품질 목표)에 닿는 결함만 finding이다. 취향·대안 선호·"더 좋게 쓸 수 있음"은 올리지 않는다.
- **설계 확장을 권하지 않는다**: 권고는 결함을 없애는 최소 변경으로 쓴다. 새 장치·상태·알림을 더하라는 권고는, 그것 없이 원 요구 문장이 깨진다는 근거가 있을 때만 쓴다. 이 규칙은 TRC-03(필요성)과 같은 원칙이다. 검증이 과설계를 만들지 않게 한다.
- **의도적 수용은 다시 올리지 않는다**: 프로파일 `known_risks_accepted`에 있거나 문서가 "위험 수용·비목표·인지된 불일치"로 적은 것은 `info`로만 남긴다. 단, 수용 근거가 사라졌으면(조건 변경) 다시 올린다.
- **건수 상한**: 기본값은 아래와 같고 프로파일 `limits`가 덮어쓴다. 상한을 넘으면 심각도·신뢰도 순으로 남기고 나머지는 "요약" 절에 기준별 개수와 대표 위치만 적는다.

| 상한 | 기본 |
|---|---:|
| 전체 finding | 50 |
| 기준 하나당 | 5 |
| `low`·`info` 합계 | 10 |

- **같은 원인, 한 finding**: 한 원인이 여러 위치에 나타나면(예: 결정 하나가 다섯 문서에 미전파) finding 하나에 근거를 모은다.
- **결함 없음도 정상 결과**다. 기준별로 "평가함, 결함 없음"을 남긴다.

## 7. Finding 필드와 보고 형식

### 7.1 필드

```json
{
  "id": "F-CON-002",
  "criterion": "CON-05",
  "title": "대체된 결정이 시나리오 문서에 남음",
  "severity": "high",
  "confidence": "confirmed",
  "scope_state": "carried",
  "method": "S+L",
  "evidence": [
    {"doc": "<시나리오 문서>", "section": "<절 제목>", "line": 287, "quote": "<원문>"},
    {"doc": "<결정 기록>", "section": "<절 제목>", "line": 72, "quote": "<원문>"}
  ],
  "absence": null,
  "touches": ["<원 요구 ID 또는 불변식·원칙>"],
  "failure_scenario": "구현자가 시나리오 문서를 기준으로 사유 코드를 고르면 결정과 다른 값이 화면에 나간다",
  "rationale": "결정 기록이 정본이고 이후 결정이 이전 값을 대체했다",
  "recommendation": "시나리오의 해당 세 곳을 결정 값으로 맞춘다",
  "also_affects": ["BND-01"],
  "source": "judge",
  "refutation": null
}
```

| 필드 | 필수 | 설명 |
|---|:-:|---|
| `criterion` | ● | 적용 대상 기준 ID만 허용 |
| `severity` | ● | 4.1 |
| `confidence` | ● | 4.2 |
| `scope_state` | ● | 4.3 |
| `method` | ● | 이 finding을 만든 검사 방법(`S`·`L`·`X`·`H` 조합) |
| `evidence` | ●(부재형 제외) | 1개 이상. `doc`, `section`, `line`, `quote` |
| `absence` | 부재형 ● | `{"searched": [...], "queries": [...], "result": "없음"}` |
| `touches` | ● | 닿는 원 요구·정확성 속성·원칙 (5장 6) |
| `failure_scenario` | ● | "이대로 구현·운영하면 → 결과" 형식 |
| `recommendation` | ● | 최소 변경 (6장) |
| `source` | ● | `script`(스크립트 추출만으로 확정) · `judge`(판정) · `human`(사람 판단 기록) |
| `conflicts_with` | | 반대 방향 권고를 하는 다른 finding ID 목록(7.5) |
| `refutation` | high 이상 ● | `{"verdict": "upheld|downgraded|rejected|uncertain", "model": "...", "note": "..."}`. 반증은 결함을 찾은 모델과 다른 모델이 한다. 반증 상한(8.3) 밖이라 반증하지 않은 finding은 `{"verdict": "uncertain", "model": null, "note": "not-refuted: cap"}` |

### 7.2 보고 형식

- **finding 표**: `ID | 기준 | 심각도 | 신뢰도 | 위치(문서§) | 인용 | 실패 시나리오 | 권고`
- **커버리지 표**(TRC): `요구 ID | 설계 | 작업 | 검증 | 비고`
- **일관성 대조표**(CON·BND, 스크립트 추출): `항목 | 문서 A 값 | 문서 B 값 | 정본 | 판단`
- **외부 확인 목록**(EVD): `주장 | 위치 | 필요한 1차 출처 | 담당 | 틀렸을 때 영향`
- **구체 후보 처리표**(`standard`·`deep`, 7.4): `후보 ID | 기준 | 위치 | 처리(채택 → finding ID / 기각 → 이유)`
- **권고 충돌 표**(7.5): `finding A | finding B | 충돌 내용`
- **기준별 상태**: 적용 기준마다 `evaluated` / `not-applicable`(trait 꺼짐) / `disabled`(프로파일 사유) / `skipped-unchanged`(증분 검증에서 범위 밖)
- **제외 문서**: 프로파일 `bundle.exclude`에 걸리거나 `readable: false`인 문서 목록. 의도적 제외이며 미평가가 아니다(8.1).
- **지표**: 요구 커버리지 %, 기준별 finding 수, critical·high 수, 외부 확인 대기 수
- 리포트 머리에 묶음 문서 목록과 각 문서 버전·해시, 프로파일 버전, rubric 버전, level, 검사 방법별 수행 여부, 단계별 모델 ID를 적는다.
- 프로파일 traits에 `irreversible-effects` 또는 `data-migration`이 있고 level이 `deep`이 아니면 리포트 머리에 **"deep 권장"** 한 줄을 보인다. 정보일 뿐이고 level을 자동으로 바꾸지 않는다(8.2).

### 7.3 쓰기 주체 (읽기 전용 보장)

- 판정·반증 에이전트는 **읽기 도구만** 가진다. 검증 대상 묶음, 원 요구·원칙 문서, 스크립트 추출 결과를 읽고, finding·반증 결과를 **반환값으로만** 돌려준다.
- 보고서와 findings 파일은 **호출한 쪽**(스킬 본체·워크플로 오케스트레이터)이 쓴다. 쓰는 곳은 보고서 폴더뿐이다.
- 검증은 묶음 문서·프로파일·rubric을 고치지 않는다. 권고(`recommendation`)는 문장으로만 남긴다.
- 외부 조회(X)는 읽기다. 외부 시스템에 쓰거나 상태를 바꾸는 호출은 하지 않는다.

### 7.4 구체 후보 처리 (출력 요건)

- **구체 후보**: 스크립트 추출 결과 중 위치와 충돌 내용이 특정된 후보다(옛 이름·ID 잔존, 정의 없는 ID 참조, 번호 체계 혼용, 설정·파라미터 대조 불일치, 깨진 참조, 요약 대 본문 개수 불일치 등). 어느 후보가 구체인지는 추출 결과가 표시한다. 개수로만 집계되는 후보(시간 표현, 외부 주체 문장 등)는 구체 후보가 아니다.
- `standard`·`deep`의 판정 출력은 구체 후보마다 **채택**(그 후보를 담은 finding ID) 또는 **기각**(한 줄 이유)을 적는다. 여러 후보를 finding 하나에 모아도 된다(6장 "같은 원인, 한 finding").
- 이것은 출력에 무엇이 있어야 하는지의 요건이다. 후보를 언제·어떤 순서로 보는지는 정하지 않는다.
- 처리 기록이 없는 구체 후보가 있으면 **평가 불완전 경고**다(8.1).

### 7.5 반대 방향 권고 (출력 요건)

- 집계 결과는 서로 반대 방향을 권하는 finding 짝을 드러낸다. 예: 한 finding은 어떤 요소를 빼라고 하고(TRC-03), 다른 finding은 그 요소에 기대는 신호·장치가 없다고 한다(RUN-04).
- 짝은 권고 충돌 표에 보이고, 각 finding의 `conflicts_with`에 상대 ID를 적는다. 집계가 한쪽을 지우거나 고치지 않는다. 어느 쪽을 따를지는 사람 몫이다.

## 8. 판정 규칙

기호: `pts(f)` = 심각도 점수 × 신뢰도 계수. 판정 반영 대상은 `scope_state`가 판정에 들어가고(4.3) 반증에서 기각되지 않은 finding이다. 반증으로 심각도가 바뀌면 바뀐 값을 쓴다.

기준 위험도: `R(c) = min(100, w(c) × Σ pts(f))`. `w(c)`는 프로파일 기준 가중치(기본 1.0)다.

| 판정 | 조건 (하나라도 해당) | 뜻 |
|---|---|---|
| **REVISE** | ① `critical`이 `confirmed` 또는 `likely` ② 평가 불완전(8.1) | 구현 전에 설계를 고친다 |
| **REVIEW_REQUIRED** | ① 어떤 기준이든 `R(c) ≥ 검토 임계값`(기본 50, rubric 권장값 → 프로파일이 덮어씀) ② 반증 결과가 `uncertain`인 high 이상(반증 상한 밖이라 반증하지 못한 것 포함, 8.3) ③ `X`·`H` 확인이 필요한 high 이상이 열려 있음 ④ 원자료 미독(8.1) | 사람이 해당 항목을 결정·확인한 뒤 진행 |
| **PROCEED** | 위 어느 것도 아님 | 구현 진행. medium·low는 진행하며 정리 |

- REVISE여도 리포트는 검토 항목을 함께 보여 준다.
- **차원 품질 점수는 두지 않는다.** 판정은 기준 위험도 `R(c)`와 위 조건만 쓴다. 차원·종합 점수(`/verify` 4.2·4.3 같은 것)는 보정 시험 뒤 재검토한다.
- **BND-06(분량 비례)은 판정에 들어가지 않는다.** 심각도 상한은 `low`이고, `R(c)` 계산과 REVISE·REVIEW_REQUIRED 조건에서 뺀다. 리포트에는 참고로 보인다.
- 이 판정 규칙은 `standard`·`deep`에 적용한다. `light`는 판정을 내지 않는다(8.2).

### 8.1 평가 완전성 (fail-closed)

**REVISE(평가 불완전)**는 실제로 평가가 빠졌을 때만 쓴다. `standard`·`deep`에서 다음 중 하나면 이것으로 끝낸다.

- 적용 대상 기준 중 평가 상태가 빠진 기준이 있다(미평가)
- 관점 에이전트·판정 세션이 실패해 맡은 기준을 평가하지 못했다
- 프로파일 `bundle`의 **정본 문서**(역할이 `source-material`·`review-input`이 아닌 문서: 명세·계획·데이터 모델·계약·작업·검증·시나리오·결정 기록·원 요구 등) 중 판정 쪽 **어디에서도** 읽지 않은 문서가 있다. 재실행이 필요하다. 관점별로 나눠 읽을 때는 관점별 미독 목록을 더하지 않고, 어느 관점도 읽지 않은 문서만 센다
- 기준이 `S`를 요구하는데 스크립트 추출 결과가 없다(추출 실패는 `info`가 아니라 불완전이다)
- 반증을 시도한 high 이상 finding의 반증 결과가 없다(반증 에이전트 실패)

다음은 평가 불완전이 **아니다**.

- **의도적 제외**: 프로파일 `bundle.exclude`에 걸리거나 `readable: false`인 문서. 리포트에 "제외 문서"로만 적는다.
- **반증 상한 밖** high 이상: `uncertain`으로 두고 REVIEW_REQUIRED(사람 검토)로 간다(8.3).
- **원자료 미독**: 어느 관점도 읽지 않은 문서가 원자료(역할 `source-material`·`review-input`, 즉 원자료·입력 문서)뿐이면 REVISE가 아니라 **REVIEW_REQUIRED**로 보낸다. 리포트에 "원자료 미독"과 그 문서 목록을 적는다. 의도적 제외(`exclude`·`readable:false`)는 여기에도 들지 않는다("제외 문서").

**평가 불완전 경고** (판정은 바꾸지 않고 리포트 머리에 보인다):

- 처리 기록(채택·기각)이 없는 구체 후보가 있다(7.4). 경고에는 빠진 후보 ID를 적는다.

### 8.2 검증 단계 (`level`)

`level`은 비용 단계다. 같은 rubric을 얼마나 비싸게 적용하는지만 바꾼다. 기준 문장·심각도 척도는 단계와 무관하다.

| level | 무엇을 하나 | 판정 | 반증 | 쓰는 때 |
|---|---|---|---|---|
| `light` | 스크립트(S) 검사만. LLM 판단 없음. `S` 단독 기준은 finding을 낸다. `S+L` 등 판단이 필요한 기준은 추출된 충돌 후보만 보고하고 판정하지 않는다 | 없음. 결과는 후보 목록과 `S` 단독 finding(심각도는 참고값) | 없음 | **문서를 고칠 때마다** |
| `standard` | 적용 기준 전부를 Fable 5.1 한 세션이 1회 검증 | 8장 | high 이상은 찾은 모델과 다른 모델이 반증 | **설계 중간 확인**(기본) |
| `deep` | 적용 기준 전부를 Opus 5.5 워크플로가 관점별(구현자·운영자·공격자·검증자·결정 검토자)로 나눠 검증 | 8장 | high 이상은 찾은 모델과 다른 모델이 반증 | **구현 시작 직전·설계 확정 때** |

- **기본 level은 `standard`**다. 사용자가 시점에 맞춰 고른다. level은 자동으로 바뀌지 않는다.
- traits에 `irreversible-effects` 또는 `data-migration`이 있으면 리포트에 "deep 권장" 한 줄을 보인다(7.2). 정보일 뿐이다.
- 보정 시험(2026-10-16)에서 `deep`이 더 잡은 실제 결함은 대부분 운영자·공격자 관점(마이그레이션, 비가역 호출 멈춤, 출시 순서, 개인정보)이었다. 구현 직전에 `deep`을 쓰는 근거다.
- `light` 결과의 후보는 다음 `standard`·`deep` 검증의 입력이 되고, 구체 후보는 처리 기록이 필요하다(7.4).
- 단계 사이에 검토 임계값을 바꾸지 않는다(0.1.0의 `deep` × 0.8 규칙은 없앴다).

### 8.3 반증 상한과 순서

- 반증 대상은 **critical·high 전부**다. 한 번의 검증에서 반증하는 건수는 최대 **8건**이다. 프로파일 `limits.refute`가 덮어쓴다.
- 상한을 넘을 때의 순서:
  1. 심각도: critical 먼저, 그다음 high
  2. 같은 심각도 안에서는 확신이 낮은 것 먼저: `possible` → `likely` → `confirmed`
  3. 그래도 같으면 그 finding이 속한 기준의 위험도 `R(c)`가 높은 순
- 상한 밖 high 이상은 반증하지 않은 채 `refutation.verdict = uncertain`(`note: not-refuted: cap`)으로 둔다. 판정에서는 REVIEW_REQUIRED ②로 간다. 반증하지 않았으므로 기각·강등은 없고, `R(c)`에는 원래 심각도로 들어간다.
- 리포트는 반증한 것과 상한 때문에 반증하지 않은 것을 나눠 보인다.

### 8.4 비용 표기

리포트나 실행 안내가 비용을 적을 때는 **판정 비용과 반증 비용을 나눠** 적는다. 반증을 두 번 세지 않기 위해서다. 금액은 숫자 뒤에 "달러"로 적는다(달러 기호를 숫자 앞에 붙이지 않는다).

**판정 비용** (반증 몫을 뺀 계수, 범위 ±25%)

| level | 계수 |
|---|---|
| `standard` | 묶음 1k 토큰당 0.092달러 |
| `deep` | 묶음 1k 토큰당 0.104달러 |
| `light` | LLM 비용 없음 |

- 판정 예상 = 계수 × 묶음 토큰(천 단위). 범위는 그 값의 0.75–1.25배.

**반증 비용** (건수 × 모델별 단가)

| 반증 모델 | 1건 단가 |
|---|---|
| Opus 5.5 | 0.20달러 |
| Fable 5.1 | 1.23달러 |

- 반증 예상 범위 = 0건부터 상한(`limits.refute`)까지: 0달러 ~ 단가 × `limits.refute`. 실제 건수는 critical·high finding 수로 정해진다.
- 합계를 적을 때는 판정 범위와 반증 범위를 더한 범위로 적고, 두 항목을 따로 보인다.
- 계수는 보정 시험을 다시 하면 갱신한다.

## 9. 재현성과 변경 관리

- 리포트에 묶음 문서별 해시, rubric 버전, 프로파일 버전, 모델 ID를 남긴다. 증분 검증은 이전 리포트의 해시와 비교해 바뀐 문서·절을 고른다(기준의 "범위" 필드).
- 버전 규칙: 기준 삭제·재정의나 판정 규칙 변경은 MAJOR, 기준 추가는 MINOR, 문구·예시 수정은 PATCH. 기준 ID는 바꾸지 않는다.
- **역할 분리**: rubric과 이 문서는 도메인·벤더·레포·제품 이름이 없는 일반 원칙만 담는다. 문서 경로, 원 요구 위치, 외부 1차 출처, ID 형식, 용어집, 원칙 문서, 수치 파라미터, 수용한 위험은 프로파일에만 둔다.
- 보정: 이 rubric을 바꾸면 결함 이력의 미교정 항목(재현 가능한 것)으로 탐지율·오탐률을 다시 잰다. 보정 정답은 rubric에 쓰지 않는다(판정 모델에게 정답이 새지 않게).

### 변경 기록
