# BEH — 행위 모델

- 버전: 0.1.0 (2026-10-16)
- 적용: 상태·동시성·비동기 trait가 켜진 묶음
- 보는 것: 상태 모델이 완전하고(상태×이벤트), 지켜야 할 성질이 명시되고(불변식·진행), 끼어들기·중복·정리·크래시에서 안전하며, 요구 흐름이 상태·제약상 실현 가능한가. 설계 수준에서 본다.
- 보지 않는 것:
  - 상태 이름·전이가 문서마다 같은가 → **CON-04**
  - 외부 호출의 실패·재시도 정책 → **FLR**
  - 코드가 상태 전이를 안전하게 구현했는가 → `/pr-verify` REL
  - 상태별 동작의 문장 품질 → **REQ**

수기로 다룰 수 있는 범위: 작업자 둘·단계 수 개의 인터리빙, 상태×이벤트 표, 불변식 목록, 단계별 크래시 지점. 그보다 깊은 트레이스·진행 속성 증명·큰 상태 공간은 도구가 필요하다(BEH-04 체크포인트).

## BEH-01 상태×이벤트 전수

- **적용**: state-machine · **범위**: 묶음
- **왜 중요한가**: 정의되지 않은 (상태, 이벤트) 칸은 구현자가 추측한다. 예상 밖 전이가 부작용을 낸다.
- **판정 질문**
  - 모든 (상태, 이벤트) 쌍의 처리(전이·무시·거부)가 정의됐는가?
  - 상태에 따라 달라지는 동작이 "<상태> 동안 …" 형태로 상태별로 적혔는가?

**체크포인트**
- 이벤트: 사용자 요청, 외부 이벤트, 스케줄러 계기, 운영자 개입, 시간 경과.
- 종결 상태에서 이벤트가 오면(늦은 이벤트·재요청).
- 대기 상태에서 외부 상태가 부적격으로 바뀌면.
- 상태×이벤트 표가 문서에 없는 것 자체는 결함이 아니다. 빈칸이 결함이다. 빈칸 finding에는 그 근거가 된 표를 붙인다.

**검사 방법**: L

**심각도 앵커**
- critical: 빈칸이 비가역 부작용으로 이어짐(예: 처리 중 상태에 취소성 이벤트가 오면 동작 미정)
- high: 부작용 있는 이벤트의 빈칸
- medium: 부작용 없는 이벤트의 빈칸(무시가 자명하지 않음)

**근거 요구**: 상태 정의·이벤트 정의 위치 인용 + 빈칸 칸과 찾아본 절(부재형). 판정이 만든 상태×이벤트 표.

**잡는 결함 범주**: C11
**근거 출처**: NEWCOMBE(A), P(B), 1016(B) state dynamics, EARS(A) State-driven (refs REQ-05 흡수)

## BEH-02 불변식·안전 속성

- **적용**: state-machine, persistent-data · **범위**: 묶음
- **왜 중요한가**: 언제나 참이어야 하는 성질이 없으면 정합성을 판정할 기준이 없다. 동시 작업자가 있으면 특히 위험하다.
- **판정 질문**
  - 언제나 참이어야 하는 성질(불변식)과 일어나면 안 되는 일(안전 속성)이 명시됐는가?
  - 각 불변식을 무엇이 지키는가(저장 제약, 조건부 갱신, 순서)가 적혔는가?

**체크포인트**
- 대상당 활성 요청 수, 비가역 부작용 횟수(최대 한 번), 종결 상태 불변.
- 불변식과 저장 제약(유일성·외래키)의 대응.
- 불변식이 검증 항목(TRC-02)과 이어지는가.

**검사 방법**: L

**심각도 앵커**
- high: 동시 작업자가 있는데 불변식이 없음, 또는 불변식을 지키는 장치가 없음
- medium: 불변식은 있으나 지키는 장치가 적히지 않음
- low: 불변식이 검증과 이어지지 않음

**근거 요구**: 불변식 절 인용 또는 찾아본 곳(부재형) + 동시 작업자 근거.

**잡는 결함 범주**: C11, C12
**근거 출처**: NEWCOMBE(A) "먼저 정확성 속성 정의", SHARD(A)

## BEH-03 진행 속성(멈춤 없음)

- **적용**: state-machine, async-events · **범위**: 묶음
- **왜 중요한가**: 영원히 머무는 상태는 조용히 쌓인다. 진행 속성은 검사하지 않으면 못 찾는다.
- **판정 질문**
  - 모든 비종결 상태에서 종결로 가는 경로와 그 계기(시간·이벤트·사람)가 있는가?
  - 외부 응답·이벤트가 영영 오지 않으면 어떻게 끝나는가가 정해졌는가?

**체크포인트**
- 상한(시간·횟수)과 상한 도달 시 전이.
- 상한 검사를 누가 언제 하는가(스케줄러가 멈추면).
- 사람 계기로 끝나는 경로(FLR-05)가 있는 상태.

**검사 방법**: L

**심각도 앵커**
- high: 사용자 흐름이 멈춘 상태로 남을 수 있음
- medium: 내부 상태가 멈출 수 있으나 사용자 영향 없음

**근거 요구**: 비종결 상태 인용 + 종결 경로를 찾아본 절.

**잡는 결함 범주**: C11
**근거 출처**: NEWCOMBE(A) liveness 미검사로 놓친 사례

## BEH-04 경합·check-then-act

- **적용**: concurrent-actors, async-events · **범위**: 묶음
- **왜 중요한가**: 확인과 실행 사이에 다른 작업자가 끼어들면 낡은 판단으로 실행한다. 이중 처리, 상태 손상이 생긴다. 이런 버그는 설계·코드 리뷰·테스트를 다 통과하곤 한다.
- **판정 질문**
  - 같은 대상을 바꾸는 작업자(사용자 요청·이벤트 처리·스케줄러·운영자)가 모두 식별됐는가?
  - 확인과 실행 사이의 끼어들기에서 동작이 정의됐는가(조건부 갱신, 잠금, 실행 직전 재확인)?
  - 수기로 다룰 수 없는 깊이(많은 단계·작업자·진행 속성)의 부분이 표시되고, 도구 검증 또는 위험 수용이 결정됐는가?

**체크포인트**
- 작업자 둘·단계 수 개의 인터리빙에서 낡은 판단으로 실행하는 순서가 있는가(예: 스케줄러와 이벤트가 같은 건을 동시에 처리).
- 외부 상태를 읽고 그 판단으로 외부 호출을 하는 흐름의 재확인 시점.
- 자기 쓰기에 의한 이벤트(우리가 바꾼 결과가 이벤트로 돌아옴).
- 깊은 트레이스가 필요한 부분: 표시만 하면 통과. 표시 없이 복잡하면 medium.

**검사 방법**: L+H

**심각도 앵커**
- critical: 끼어들기로 비가역 부작용이 두 번 날 수 있음
- high: 끼어들기로 상태 손상(종결 상태 덮어쓰기 등)
- medium: 작업자 식별 누락, 도구 검증 필요 부분 표시 누락

**근거 요구**: 두 작업자의 흐름 위치 인용 + 끼어들기 순서(단계 목록)를 failure_scenario에.

**잡는 결함 범주**: C11
**근거 출처**: AWS-PES-2025(A), NEWCOMBE(A), SHARD(A), YUAN(A) 소범위 재현 (refs BEH-08 흡수)

## BEH-05 중복·순서 뒤바뀜

- **적용**: async-events, external-integration · **범위**: 문서
- **왜 중요한가**: 비동기 이벤트는 중복·지연·순서 뒤바뀜이 정상이다. 멱등하지 않으면 재전달마다 처리가 반복된다.
- **판정 질문**
  - 같은 이벤트·요청의 중복 도착에서 결과가 같도록(멱등) 설계됐는가?
  - 순서가 뒤바뀐 도착(늦은 옛 이벤트)을 구분하는 기준(버전·시각·현재 상태 재조회)이 있는가?

**체크포인트**
- 멱등 키(요청 ID·이벤트 ID)와 그 저장.
- 사용자 재요청과 기존 요청의 관계.
- 이벤트 내용을 믿는가, 이벤트를 계기로 현재 상태를 다시 읽는가.

**검사 방법**: L

**심각도 앵커**
- critical: 중복 시 비가역 부작용 반복
- high: 늦은 옛 이벤트가 최신 상태를 덮어씀
- medium: 중복 시 알림·기록이 반복

**근거 요구**: 이벤트·요청 처리 절 인용 + 멱등·순서 장치를 찾아본 곳.

**잡는 결함 범주**: C11
**근거 출처**: BL-IDEM(A)

## BEH-06 정리 작업 안전성

- **적용**: persistent-data, automation · **범위**: 문서
- **왜 중요한가**: 정리·만료·GC 작업이 아직 쓰이는 상태를 지우면 전면 장애가 된다.
- **판정 질문**
  - 정리·만료·삭제 작업이 아직 쓰이는 상태를 지울 수 없도록 조건이 명시됐는가?
  - 늦게 도착한 실행기(이전 판단으로 도는 작업)가 정리 뒤에 다시 쓰는 경우가 다뤄졌는가?

**체크포인트**
- 정리 대상 조건(종결 상태·나이)과 사용 중 판별.
- 정리와 다른 작업자의 경합(BEH-04와 겹치면 정리 쪽을 여기에).
- 외부에 남는 것(외부 잠금·예약)의 정리 주체.

**검사 방법**: L

**심각도 앵커**
- critical: 살아 있는 상태를 지워 핵심 흐름 전면 장애
- high: 살아 있는 상태 일부 삭제 가능
- medium: 정리 조건 불명확

**근거 요구**: 정리 작업 정의 인용 + 조건.

**잡는 결함 범주**: C11
**근거 출처**: AWS-PES-2025(A)

## BEH-07 충돌 지점

- **적용**: persistent-data, irreversible-effects · **범위**: 문서
- **왜 중요한가**: 단계 사이에서 프로세스가 죽으면 중간 상태가 남는다. 외부 부작용 뒤 기록 전에 죽으면 다시 실행된다.
- **판정 질문**
  - 각 단계 사이에서 프로세스가 죽었을 때 남는 중간 상태와 복구 방법이 정의됐는가?
  - 외부 부작용 전에 "진행 중"을 기록하고, 복구가 재실행이 아니라 조회로 확정하는가?

**체크포인트**
- 기록 → 외부 호출 → 결과 기록의 순서와 각 틈.
- 트랜잭션 경계와 외부 호출의 위치.
- 알림·메일의 발송과 상태 전이의 원자성(같이 기록되는가).

**검사 방법**: L

**심각도 앵커**
- critical: 외부 부작용 뒤 기록 전 크래시가 재실행으로 이어짐
- high: 크래시 후 중간 상태에 복구 경로 없음
- medium: 알림 중복·누락 가능

**근거 요구**: 흐름(시퀀스) 위치 인용 + 크래시 지점과 결과를 failure_scenario에.

**잡는 결함 범주**: C11
**근거 출처**: SHARD(A) crash consistency, BL-IDEM(A)

## BEH-08 요구 경로 실현 가능성

- **적용**: state-machine, persistent-data · **범위**: 묶음
- **왜 중요한가**: 요구는 있는데 그 요구를 만족하는 상태 경로가 없거나, 저장 제약(유일성 등)이 그 경로를 막으면 구현 단계에서야 드러난다. 제약끼리 충돌하기도 한다.
- **판정 질문**
  - 각 요구 흐름(재요청·재시도·인수·복구 포함)에 그것을 만족하는 상태 경로가 있는가?
  - 저장 제약·유일성·외래키가 그 경로를 막지 않는가?
  - 제약끼리, 또는 제약과 결정이 충돌하지 않는가?

**체크포인트**
- "같은 대상에 다시 요청"·"실패 뒤 재시도"·"남은 자원 인수" 같은 흐름과 유일성 제약.
- "기존 행 반환"과 "새 요청 허용"이 동시에 요구되는가.
- 실제 대상 시스템(현재 코드·스키마)의 제약과 설계 전제가 같은가(코드는 BND-02 기준 시점).

**검사 방법**: L

**심각도 앵커**
- high: 핵심 요구 흐름이 저장 제약에 막힘, 또는 두 제약이 충돌해 어느 구현도 둘을 지킬 수 없음
- medium: 부가 흐름이 막힘
- low: 경로는 있으나 문서에 적히지 않음

**근거 요구**: 요구 인용 + 막는 제약 인용(데이터 모델·현재 스키마 위치).

**잡는 결함 범주**: C11
**근거 출처**: SK-AN(B) C 미명세, NEWCOMBE(A), 29148(A·간접) Feasible
