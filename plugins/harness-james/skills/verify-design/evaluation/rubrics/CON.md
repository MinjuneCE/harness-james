# CON — 문서 간 일관성

- 버전: 0.1.0 (2026-10-16)
- 적용: 모든 설계 묶음 (기준 적용은 프로파일 `design.traits`가 정한다)
- 보는 것: 같은 개념·값·엔터티·상태·결정이 묶음 안의 모든 문서와 한 문서의 요약·본문에서 같은가. 시나리오가 명세된 동작만 쓰는가.
- 보지 않는 것:
  - 어느 문서가 정본인지 정해져 있는가, 사본이 있는가 → **BND-01** (사본 사이의 값이 실제로 다르면 CON)
  - 결정 기록에 상태·대체 표시가 있는가 → **DEC-04** (대체된 결정이 본문에 남았으면 CON-05)
  - 존재하지 않는 ID·절·파일 참조, 낡은 시간 표현 → **BND-03**
  - ID 형식·번호 체계 충돌 → **BND-04**
  - 값 자체의 근거 → **EVD-05**

스크립트 선추출이 이 차원의 기본 입력이다. LLM은 추출된 충돌 후보만 판단한다.

## CON-01 용어·식별자 일치

- **적용**: multi-doc · **범위**: 묶음
- **왜 중요한가**: 같은 것을 다른 이름으로 부르면 구현이 둘로 갈린다. 한 이름이 두 뜻이면 각 문서가 다른 동작을 기대한다.
- **판정 질문**
  - 같은 개념이 모든 문서에서 같은 이름·ID·철자로 쓰이는가?
  - 한 이름이 묶음 안에서 하나의 뜻으로만 쓰이는가?

**체크포인트**
- 상태 이름, 사유·오류 코드, 설정 키, 이벤트 이름, 역할 이름의 철자와 대소문자.
- 용어집(프로파일 `glossary`)이 있으면 금지 동의어 사용.
- 같은 단어가 서로 다른 정의·값 범위와 함께 나오는가(예: 어떤 신호 이름이 "외부가 쓰는 값 하나"와 "판정 신호 집합"을 모두 뜻함).
- 합치거나 개명한 이름이 일부 문서에만 반영됐는가(옛 이름 잔존은 CON-05와 겹치면 CON-05로).

**검사 방법**: S+L
- **스크립트 추출 대상**: 코드 서식·대문자 식별자, 따옴표 용어, 용어집 항목과 금지 동의어, 문서별 출현 위치. 편집 거리가 작은 쌍(철자 변형)과 같은 문맥에 쓰인 서로 다른 이름 쌍을 후보로 낸다.

**심각도 앵커**
- high: 두 이름(또는 두 뜻)이 서로 다른 동작·저장값으로 구현될 여지가 있음
- medium: 동의어 혼용으로 구현자가 같은 것인지 확인해야 함
- low: 철자·대소문자 차이뿐이고 문맥상 같음이 분명함

**근거 요구**: 서로 다른 이름(또는 뜻)이 쓰인 위치 둘 이상의 인용. 용어집이 있으면 정본 항목.

**잡는 결함 범주**: C13, C05
**근거 출처**: SK-AN(B) F 용어 드리프트, 42010(B, 미확인) 대응 규칙

## CON-02 값·수치 일치

- **적용**: multi-doc · **범위**: 묶음
- **왜 중요한가**: 타임아웃·한도·재시도 횟수·기간이 문서마다 다르면 구현자가 임의로 고른다. 결정이 바뀔 때 일부 문서만 고치는 일이 가장 흔하다.
- **판정 질문**
  - 같은 파라미터의 값이 모든 문서에서 같은가?
  - 파생 값(주기 + 지연 = 최대 지연 등)이 원 값과 맞게 계산돼 있는가?

**체크포인트**
- 시간(초·분·시간·ISO 기간 표기), 횟수, 크기, 백분율, 금액 한도.
- 같은 값이 설정 예시·계약·명세·검증 기대값에 모두 나오는가, 모두 같은가.
- 의도적으로 다른 값(인지된 불일치)은 문서에 이유가 적혔는지 본다. 적혔으면 `info`.
- 이력 맥락("이전 버전에서 폐기")의 옛 값은 결함이 아니다.

**검사 방법**: S+L
- **스크립트 추출 대상**: 숫자 + 단위, 기간 표기, 설정 키 = 값 쌍, 문서·줄 위치. 파라미터 이름(또는 주변 키워드)으로 묶어 문서별 값 표를 만든다.

**심각도 앵커**
- critical: 돈 이동·데이터 삭제 시점을 정하는 값이 문서마다 달라, 어느 쪽을 구현해도 다른 문서의 보장이 깨짐
- high: 사용자 약속·외부 계약·정합성에 닿는 값 불일치
- medium: 운영 주기·로그 보존 같은 내부 값 불일치
- low: 표기만 다르고 값은 같음이 계산으로 확인됨

**근거 요구**: 값이 다른 위치 둘 이상의 인용과 추출 표의 해당 행. 정본(BND-01)이 정해져 있으면 정본 값.

**잡는 결함 범주**: C05, C07
**근거 출처**: SK-AN(B) F

## CON-03 엔터티·필드 정합

- **적용**: multi-doc, persistent-data · **범위**: 묶음
- **왜 중요한가**: 계약·계획이 쓰는 필드가 데이터 모델에 없으면 구현 중에 임의로 생긴다. 모델에만 있는 필드는 아무도 채우지 않는다.
- **판정 질문**
  - 계획·계약·작업에 나오는 엔터티·필드가 데이터 모델에 정의돼 있는가?
  - 데이터 모델의 필드가 쓰는 곳(쓰기·읽기) 하나 이상을 갖는가?

**체크포인트**
- 필드 이름·타입·널 허용·유일성이 문서 사이에 같은가.
- 삭제한 필드가 계약·쿼리 예시·작업에 남았는가.
- 상태 값 열의 허용 값 목록이 상태 정의(CON-04)와 같은가.

**검사 방법**: S+L
- **스크립트 추출 대상**: 데이터 모델의 엔터티·필드 목록, 계약·쿼리·작업에 나오는 필드 식별자. 양방향 차집합.

**심각도 앵커**
- high: 계약·핵심 흐름이 쓰는 필드가 저장 모델에 없음, 또는 타입·유일성 정의가 문서마다 달라 저장 제약이 바뀜
- medium: 쓰는 곳 없는 필드, 보조 필드 타입 불일치
- low: 설명 문구만 다름

**근거 요구**: 필드가 나오는 위치 인용 + 데이터 모델에서 찾아본 절(부재형).

**잡는 결함 범주**: C05, C11
**근거 출처**: SK-AN(B) F 계획에만 있는 엔터티, BMAD(B)

## CON-04 상태·전이 정합

- **적용**: multi-doc, state-machine · **범위**: 묶음
- **왜 중요한가**: 문서마다 전이 그래프가 다르면 한 문서만 허용하는 전이가 구현되어 예상 밖 부작용을 낸다.
- **판정 질문**
  - 모든 문서의 상태 이름과 허용 전이가 하나의 정의(표·다이어그램)와 같은가?
  - 시나리오·시퀀스에 나오는 전이가 정의에 있는가?

**체크포인트**
- 상태 목록, 전이(출발 → 도착, 계기, 조건), 종결 상태 여부.
- 합쳐진 상태·없어진 상태가 다른 문서에 남았는가.
- 같은 전이의 계기·조건이 문서마다 다른가.

**검사 방법**: S+L
- **스크립트 추출 대상**: 상태 이름 목록(대문자 식별자, 상태 열 값), "A → B" 형태 전이, 문서별 위치. 정의 문서의 전이 집합과 다른 문서의 전이 집합 차이.

**심각도 앵커**
- critical: 정의에 없는 전이가 비가역 부작용을 일으킴
- high: 한 문서만 허용하는 전이가 부작용(외부 호출·알림·저장)을 일으킴, 또는 종결 여부가 문서마다 다름
- medium: 부작용 없는 전이의 계기·조건 표현 차이
- low: 다이어그램과 표의 표기 차이뿐

**근거 요구**: 정의 위치 인용 + 어긋나는 위치 인용.

**잡는 결함 범주**: C05, C11
**근거 출처**: 42010(B, 미확인), SK-AN(B) F, 1016(B) state dynamics

## CON-05 결정 전파

- **적용**: multi-doc · **범위**: 묶음
- **왜 중요한가**: 결정은 한 곳에서 바뀌고 본문 여러 곳에 반영돼야 한다. 반영이 빠지면 폐기된 설계가 작업·검증·시나리오로 살아남는다. 결정이 바뀔 때마다 비용이 문서 수만큼 곱해진다.
- **판정 질문**
  - 채택된 결정과 변경 기록의 각 행이 그 결정이 닿는 본문(명세·계획·데이터 모델·작업·검증·시나리오)에 반영됐는가?
  - 폐기·대체된 결정의 내용(이름·값·장치)이 본문에 살아 있는 설계로 남아 있지 않은가?

**체크포인트**
- 변경 기록이 "바뀐 문서·절"을 적었다면 그 절에 실제로 새 내용이 있는가.
- 삭제한 용어·장치·값의 잔존. 이력 맥락("삭제함", "이전 버전")은 제외한다.
- 묶음 경계(설계 → 시나리오, 설계 → 작업)에서 전파가 끊겼는가.
- 다른 문서의 상태를 서술한 문장("그 문서는 아직 ~로 적혀 있다")이 지금도 맞는가.
- 제안된 항목(새 시나리오·새 요구)이 채택·기각 기록 없이 사라졌는가.

**검사 방법**: S+L
- **스크립트 추출 대상**: 결정 ID별 값·상태(결정 기록·변경 기록에서), 문서별 결정 ID 인용 위치, 삭제·개명 용어 목록(변경 기록에서)과 그 잔존 위치. 이력 맥락 키워드가 붙은 줄은 따로 표시한다.

**심각도 앵커**
- critical: 폐기된 설계가 비가역 부작용을 일으키는 형태로 작업·계약에 남음
- high: 폐기된 장치·상태·값이 작업·검증·시나리오에 살아 있는 설계로 남음
- medium: 결정은 반영됐지만 보조 문서(시나리오·리서치 요약)의 서술이 옛 결정을 말함
- low: 다른 문서의 상태에 대한 낡은 서술 한 곳

**근거 요구**: 결정(또는 변경 기록 행) 인용 + 미반영 위치 인용. 미반영이 부재형이면 찾아본 절.

**잡는 결함 범주**: C05, C06
**근거 출처**: ADR(A) supersede, SK-AN(B) D·F

## CON-06 시나리오·명세 대응

- **적용**: multi-doc · **범위**: 묶음
- **왜 중요한가**: 시나리오가 명세 밖 동작을 전제하면 구현자는 시나리오와 명세 중 하나를 어긴다. 핵심 흐름 시나리오가 미정의 동작에 기대면 검증 기준도 성립하지 않는다.
- **판정 질문**
  - 시나리오·예시의 각 단계가 명세된 동작(요구·전이·정책)으로 설명되는가?
  - 시나리오의 기대 결과가 명세의 결과(상태·사유·안내)와 같은가?

**체크포인트**
- 시나리오가 쓰는 이벤트·상태·사유 코드가 명세에 있는가.
- 시나리오의 전제(외부 시스템 동작)가 명세의 가정 목록에 있는가(없으면 EVD-03과 함께).
- 검증 항목의 기대값이 시나리오·명세와 같은가.

**검사 방법**: L
- 보조로 S(시나리오에 나오는 식별자 중 명세에 없는 것 목록)를 쓸 수 있다.

**심각도 앵커**
- critical: 핵심 흐름 시나리오가 미정의 동작에 기대고, 그 동작이 비가역 부작용을 정함
- high: 핵심 흐름 시나리오의 기대 결과가 명세와 다름
- medium: 부가 시나리오가 명세 밖 동작을 전제함

**근거 요구**: 시나리오 단계 인용 + 명세에서 찾아본 절(부재형) 또는 어긋나는 명세 인용.

**잡는 결함 범주**: C05, C11
**근거 출처**: 1016(B), ATAM(A) 시나리오

## CON-07 문서 내부 정합

- **적용**: 공통 · **범위**: 문서
- **왜 중요한가**: 요약·표 머리만 읽는 독자(검토자·다른 세션)가 본문과 다른 결론을 가져간다. 한 문서 안의 두 진술이 맞지 않으면 어느 쪽도 믿을 수 없다.
- **판정 질문**
  - 요약·표 머리·목차의 수치·범위·상태 표시가 본문과 같은가?
  - 한 문서 안에서 같은 대상에 대한 두 진술이 서로 맞는가?

**체크포인트**
- 요약의 개수·범위(ID 범위, 항목 수)와 본문 실제 개수.
- 표 행 머리("변경됨")와 그 행 내용.
- 검증 기대값과 같은 문서의 설계 진술.
- 작성 시각·버전 표기가 문서 안에서 맞는가.

**검사 방법**: S+L
- **스크립트 추출 대상**: 요약 절의 숫자·ID 범위, 본문의 ID 목록과 개수 재계산, 머리말 버전·날짜와 변경 기록의 마지막 행.

**심각도 앵커**
- high: 요약이 본문과 다른 동작·결정을 말하고, 요약만 읽는 쪽이 그것으로 결정함
- medium: 같은 문서 안의 설계 진술과 검증 기대값이 다름
- low: 개수·날짜 오기
