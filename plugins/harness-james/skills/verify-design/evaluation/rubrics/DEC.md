# DEC — 결정·근거

- 버전: 0.1.0 (2026-10-16)
- 적용: 모든 설계 묶음
- 보는 것: 핵심 결정에 대안·결과·가역성이 적혔는가. 결정에 상태와 대체 관계가 있는가. 프로젝트 원칙과 충돌하지 않는가.
- 보지 않는 것:
  - 결정이 본문에 반영됐는가 → **CON-05**
  - 결정이 기대는 사실의 출처 → **EVD**
  - 품질 속성 사이의 트레이드오프 → **QAS-04**
  - 결정이 원 요구에 필요한가 → **TRC-03**

## DEC-01 대안·트레이드오프

- **적용**: 공통 · **범위**: 절
- **왜 중요한가**: 근거 없는 결정은 나중에 다시 논쟁되고 되돌려진다. "아무것도 하지 않는 안"을 검토하지 않으면 불필요한 장치가 들어온다.
- **판정 질문**
  - 핵심 결정마다 검토한 대안과 버린 이유가 적혔는가?
  - 대안에 "하지 않는다·기존대로 둔다"가 포함됐는가(해당할 때)?

**체크포인트**
- 핵심 결정: 상태 모델, 외부 연동 방식, 저장 구조, 실패 처리 정책, 사용자 약속.
- 대안 비교가 같은 기준(비용·위험·요구 충족)으로 됐는가.

**검사 방법**: L

**심각도 앵커**
- high: 되돌릴 수 없는 결정(DEC-03)에 대안이 없음
- medium: 핵심 결정에 대안·이유 없음
- low: 부가 결정에 이유 한 줄 없음

**근거 요구**: 결정 인용 + 대안을 찾아본 절(부재형).

**잡는 결함 범주**: C09
**근거 출처**: UBL(A) alternatives considered, RUST(B) rationale and alternatives, OXIDE(B)

## DEC-02 결과(부정 포함)

- **적용**: 공통 · **범위**: 절
- **왜 중요한가**: 긍정 결과만 적으면 숨은 비용(운영 부담·제약·지연)이 구현 뒤에 드러난다.
- **판정 질문**
  - 결정의 결과를 긍정·부정 모두 적었는가?
  - 결정이 남기는 예외(규칙이 맞지 않는 경우)를 적었는가?

**체크포인트**
- 운영 부담(수동 처리, 정리 작업), 사용자 영향(지연·안내), 다른 결정에 주는 제약.

**검사 방법**: L

**심각도 앵커**
- medium: 핵심 결정의 부정 결과·예외가 없음
- low: 부가 결정의 부정 결과 누락

**근거 요구**: 결정 인용 + 결과 절 인용 또는 부재 근거.

**잡는 결함 범주**: C09, C11
**근거 출처**: ADR(A) Consequences

## DEC-03 가역성 분류

- **적용**: 공통 (irreversible-effects·data-migration이 켜지면 앵커가 올라감) · **범위**: 절
- **왜 중요한가**: 되돌리기 어려운 결정(외부 계약, 데이터 형식, 사용자 약속, 돈 이동 규칙)을 가볍게 확정하면 고칠 수 없다. 반대로 가역 결정에 무거운 절차를 쓰면 진행이 막힌다.
- **판정 질문**
  - 되돌리기 어려운 결정을 표시했는가?
  - 그 결정에 더 깊은 근거와 승인(누가·언제)이 있는가?

**체크포인트**
- 외부에 노출되는 계약·식별자, 저장 형식, 사용자에게 한 약속, 비가역 부작용의 조건.
- 승인 기록(결정 기록의 승인자·날짜).

**검사 방법**: L+H

**심각도 앵커**
- critical: 비가역 결정이 근거·승인 없이 확정
- high: 비가역 결정에 승인은 있으나 근거(대안·사실)가 없음
- medium: 가역성 표시 없음
- low: 가역 결정에 과잉 절차(진행 지연)

**근거 요구**: 결정 인용 + 승인·근거를 찾아본 곳.

**잡는 결함 범주**: C01, C09
**근거 출처**: BEZOS(A) one-way/two-way door

## DEC-04 결정 상태·대체

- **적용**: multi-doc, agent-authored · **범위**: 문서
- **왜 중요한가**: 상태 없는 결정은 옛 결정이 살아 있는 것처럼 읽힌다. 여러 세션이 고친 문서에서 특히 흔하다.
- **판정 질문**
  - 결정마다 상태(제안·채택·폐기·대체)가 있는가?
  - 대체된 결정이 대체한 결정을 가리키고, 대체한 결정이 대체된 결정을 가리키는가?

**체크포인트**
- 결정 기록의 상태 열, 날짜, 승인자.
- 같은 번호의 결정이 버전마다 다른 내용인가(번호 재사용은 BND-04).
- "해석"으로 둔 결정이 나중에 확정됐다면 표시가 바뀌었는가.

**검사 방법**: S+L
- **스크립트 추출 대상**: 결정 ID, 상태 표지, 대체 관계 표기("대체됨", "→"), 날짜. 상태 없는 결정, 한쪽만 가리키는 대체 관계.

**심각도 앵커**
- high: 대체된 결정이 상태 표시 없이 남아 본문과 충돌
- medium: 결정 상태 없음
- low: 대체 관계가 한쪽만 표시됨

**근거 요구**: 결정 행 인용.

**잡는 결함 범주**: C05, C06
**근거 출처**: ADR(A) status·superseded, SK-CONST(B) 개정 이력, OXIDE(B) 상태

## DEC-05 원칙 정합

- **적용**: 공통 (프로파일 `principles`가 있을 때) · **범위**: 묶음
- **왜 중요한가**: 프로젝트 원칙의 MUST를 어기는 설계는 구현·리뷰 단계에서 반드시 막힌다. 설계에서 잡는 것이 가장 싸다.
- **판정 질문**
  - 프로젝트 원칙의 MUST와 충돌하는 결정이 없는가?
  - 원칙에서 벗어난 결정이 있다면 예외 근거와 승인이 적혔는가?

**체크포인트**
- 원칙 문서(프로파일 `principles`)의 MUST·SHOULD 조항별로 관련 결정.
- 원칙 개정이 필요한 결정은 원칙 개정 절차를 밟았는가.

**검사 방법**: L

**심각도 앵커**
- critical: MUST 위반이 예외 근거 없이 있음
- high: MUST 위반에 예외 근거는 있으나 승인 없음
- medium: SHOULD 위반에 이유 없음

**근거 요구**: 원칙 조항 인용 + 충돌하는 설계 위치 인용.

**잡는 결함 범주**: C11
**근거 출처**: SK-AN(B) D constitution 정합, SK-CONST(B) Complexity Tracking
