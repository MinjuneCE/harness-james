## THR-01 신뢰 경계·데이터 흐름

- **적용**: trust-boundary · **범위**: 문서
- **왜 중요한가**: 경계가 그려지지 않으면 어디서 검증해야 하는지 모른다.
- **판정 질문**
  - 신뢰 경계와 그것을 넘는 데이터 흐름(누가 → 무엇을 → 어디로)이 그려지거나 적혔는가?

**체크포인트**
- 외부 사용자·브라우저·제3자·외부 이벤트 발신자에서 들어오는 흐름.
- 경계마다 신원 확인 방법.

**검사 방법**: L

**심각도 앵커**
- high: 공개 진입점이 있는데 경계·흐름이 없음
- medium: 일부 흐름 누락

**근거 요구**: 진입점 인용 + 경계 서술을 찾아본 곳.

**잡는 결함 범주**: C11
**근거 출처**: OWASP-TM(A), TMM(A)

## THR-02 위협 범주 점검

- **적용**: trust-boundary · **범위**: 문서
- **왜 중요한가**: 범주별로 점검하지 않으면 인가 누락(남의 자원 조작) 같은 결함이 설계를 통과한다.
- **판정 질문**
  - 경계마다 위장·변조·부인·정보 노출·서비스 거부·권한 상승을 점검하고 대응이나 수용을 적었는가?
  - 요청자와 대상 자원의 소유자를 대조하는가?

**체크포인트**
- 자원 식별자를 요청자가 주는 흐름의 소유자 확인.
- 외부 이벤트·웹훅의 발신 검증.
- 남용(반복 요청)의 제한.

**검사 방법**: L

**심각도 앵커**
- critical: 남의 자원을 바꿀 수 있는 흐름에 대응 없음
- high: 위장·변조 대응 없는 진입점
- medium: 범주 점검 기록 없음

**근거 요구**: 흐름 인용 + 대응을 찾아본 곳.

**잡는 결함 범주**: C11
**근거 출처**: STRIDE(A), OWASP-TM(A)

## THR-03 대응의 요구화

- **적용**: trust-boundary · **범위**: 묶음
- **왜 중요한가**: 문서에만 있는 대응은 구현되지 않는다.
- **판정 질문**
  - 위협 대응이 검증 가능한 요구와 작업·검증 항목으로 옮겨졌는가?

**체크포인트**
- 위협 표의 대응 행 ↔ 요구 ID ↔ 작업·검증 ID.

**검사 방법**: S+L
- **스크립트 추출 대상**: 위협·대응 표의 행과 각 행이 인용하는 요구·작업·검증 ID.

**심각도 앵커**
- high: critical 위협의 대응이 요구·작업 없이 문서에만 있음
- medium: 그 외 대응의 요구화 누락

**근거 요구**: 대응 인용 + 요구·작업을 찾아본 결과.

**잡는 결함 범주**: C12
**근거 출처**: OWASP-TM(A) "완화는 요구가 된다"

## THR-04 민감 데이터 범위

- **적용**: trust-boundary, persistent-data · **범위**: 문서
- **왜 중요한가**: 설계가 저장·전송·기록하는 개인·민감 데이터를 모르면 보존·노출 범위를 정할 수 없다. 알림·로그로 흘러나간다.
- **판정 질문**
  - 설계가 저장·전송·로그·알림에 담는 개인·민감 데이터를 식별했는가?
  - 각 데이터의 최소화·보존 기간·노출 범위(누가 보는가)가 정해졌는가?

**체크포인트**
- 알림·운영 메시지·외부 채널로 나가는 필드.
- 저장 필드 중 개인정보, 보존 기간.

**검사 방법**: L

**심각도 앵커**
- high: 개인정보가 외부 채널·로그로 나가는 설계에 최소화·범위 결정 없음
- medium: 저장하는 개인정보의 보존 기간 미정

**근거 요구**: 필드·채널 정의 인용.

**잡는 결함 범주**: C11
**근거 출처**: 25010(A) 보안, UBL(A) cross-cutting(개인정보), OWASP-TM(A) 정보 노출
