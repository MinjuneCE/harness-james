# TRC — 추적성·필요성

- 버전: 0.1.0 (2026-10-16)
- 적용: 모든 설계 묶음 (기준 적용은 프로파일 `design.traits`가 정한다)
- 보는 것: 원 요구와 설계 요소가 양방향으로 이어지는가. 요구마다 설계·작업·검증이 있는가. 설계 요소마다 깨지면 안 되는 원 요구 문장이 있는가. 범위·소관이 지켜지는가.
- 보지 않는 것:
  - 요구 문장 자체의 품질(모호·측정 불가) → **REQ**
  - 요구 경로가 상태·제약상 실현 가능한가 → **BEH-08**
  - 결정의 대안·근거 → **DEC**
  - ID가 안정적인가, 번호 체계가 하나인가 → **BND-04**

원 요구가 어느 문서인지는 프로파일 `requirement_sources`가 정한다. 작성자가 스스로 만든 파생 요구(설계 문서 안의 FR·가정·해석)는 원 요구가 아니다.

## TRC-01 요구 → 설계 커버리지

- **적용**: 공통 · **범위**: 묶음
- **왜 중요한가**: 설계 없는 요구는 구현에서 빠지거나 즉흥으로 채워진다.
- **판정 질문**
  - 원 요구(프로파일 `requirement_sources`)의 각 문장·결정이 설계 요소(명세 요구·전이·정책·계약) 하나 이상에 대응하는가?

**체크포인트**
- 원 요구 문서의 결정·요구 ID(또는 번호 문장)마다 설계 쪽 대응 위치.
- 원 요구가 바뀐 뒤(새 결정) 대응이 새 내용으로 바뀌었는가(아니면 CON-05).
- 원 요구가 "하지 않는다"고 정한 것(비목표)도 대응으로 본다. 설계가 그것을 하지 않는지 확인한다.

**검사 방법**: S+L
- **스크립트 추출 대상**: 원 요구 문서의 ID·번호 목록, 설계 문서의 원 요구 ID 인용 위치. 인용 0건인 원 요구 목록.

**심각도 앵커**
- critical: 핵심 흐름의 원 요구가 설계 어디에도 없음
- high: 원 요구의 실패·예외 조항이 설계에 없음
- medium: 부가 요구의 대응 누락

**근거 요구**: 원 요구 인용 + 찾아본 설계 문서·절과 검색어(부재형).

**잡는 결함 범주**: C11
**근거 출처**: SK-AN(B) E 커버리지, BMAD(B) §1 요구 정합

## TRC-02 요구 → 작업·검증 커버리지

- **적용**: multi-doc · **범위**: 묶음
- **왜 중요한가**: 작업 없는 요구는 구현되지 않고, 검증 없는 요구는 구현됐는지 모른다. 비기능 성공 기준이 가장 자주 빠진다.
- **판정 질문**
  - 각 설계 요구가 작업 하나 이상과 검증 방법(테스트·확인 절차·지표) 하나 이상을 갖는가?
  - 검증 항목의 기대값이 그 요구를 실제로 판별하는가(요구가 깨져도 통과하지 않는가)?

**체크포인트**
- 요구 ID ↔ 작업 ID ↔ 검증 ID 대응표.
- 성능·보안·정합성 성공 기준의 측정 작업.
- 검증 전제(테스트 데이터·스텁)가 기대값을 만들 수 있는가(전제가 비면 기대값이 성립하지 않음).

**검사 방법**: S+L
- **스크립트 추출 대상**: 요구·작업·검증 ID 목록과 상호 인용. 작업·검증이 없는 요구 목록.

**심각도 앵커**
- high: 핵심 요구 또는 비기능 성공 기준에 검증이 없음, 또는 검증 전제가 기대값을 성립시킬 수 없음
- medium: 부가 요구의 작업·검증 누락
- low: 대응은 있으나 ID 인용 없이 문장으로만 이어짐

**근거 요구**: 요구 인용 + 찾아본 작업·검증 문서(부재형), 또는 기대값과 전제가 어긋나는 두 위치 인용.

**잡는 결함 범주**: C12, C11
**근거 출처**: SK-AN(B) E, TESSL(B) 요구 ↔ 테스트 링크

## TRC-03 필요성(제거 시험)

- **적용**: 공통 · **범위**: 묶음
- **왜 중요한가**: 원 요구 없이 더한 장치·상태·알림·절차는 상태·열·쿼리·알림·검증·작업으로 퍼진다. 넣을 때와 뺄 때 모두 문서 여러 개를 고친다. 이 범주는 리뷰에서 가장 비싸고, 사람만 잡아 왔다.
- **판정 질문**
  - 이 장치·상태·알림·절차를 빼면 원 요구의 어느 문장이 깨지는가? 그 문장을 인용할 수 있는가?
  - 그 요소가 묶인 요구가 원 요구인가, 작성자가 스스로 만든 파생 요구(해석·가정·"있으면 좋음")뿐인가?

**체크포인트**
- 대상 요소: 상태, 저장 필드, 외부 구독·호출, 알림·메일, 재시도·해제·보상 경로, 설정 키, 운영 절차, 검증 항목.
- 요소마다 "제거하면 깨지는 원 요구 문장"이 있으면 통과다. 파생 요구에만 묶이면 결함 후보다.
- 어떤 요구에도 묶이지 않은 작업·설계 요소(고아)는 같은 기준에서 본다. 고아는 기계적으로 뽑히는 하위 경우다.
- 드문 예외용 장치(드문 실패의 알림·자동 복구·대체 경로)는 특히 본다. 원 요구가 "운영이 직접 처리"를 허용하면 장치 대신 그쪽을 권한다.
- 이 기준은 장치를 더하라고 권하지 않는다. 결과는 "제거 후보"와 "근거 확인 질문"뿐이다.
- 문서가 이유를 적고 의도적으로 둔 요소(위험 수용, 원칙)는 그 이유가 원 요구·원칙에 닿는지 본다.

**검사 방법**: L+S+H
- **스크립트 추출 대상**: 설계 요소 목록(상태 이름, 필드, 알림·이벤트 종류, 설정 키, 작업 ID)과 각 요소가 인용하는 요구 ID. 요구 ID 인용이 없는 요소, 설계 문서 안 파생 요구에만 이어지는 요소를 후보로 낸다.
- 최종 범위 판단은 사람(H)이 한다. 판정은 후보와 근거 사슬을 제시한다.

**심각도 앵커**
- high: 원 요구 없는 요소가 상태·저장·외부 호출·알림 중 둘 이상으로 퍼져 있음(여러 문서·작업에 걸침)
- medium: 원 요구 없는 요소가 한 문서·한 작업에 국한됨
- low: 고아 작업·설명 절(동작에 영향 없음)
- info: 근거가 파생 요구뿐이지만 문서가 이유를 적고 위험을 수용함 → 사람 확인 질문

**근거 요구**: 요소의 정의 위치 인용 + 원 요구 문서에서 찾아본 절과 검색어(부재형) + 요소가 퍼진 위치 목록. 파생 요구에 묶였다면 그 파생 요구 인용.

**잡는 결함 범주**: C09
**근거 출처**: 29148(A·간접) Necessary, SK-AN(B) E 고아 산출물, UBL(A) "트레이드오프 없으면 쓰지 말 것", BOCKELER(A), CC-BP(A) 과잉 지적 경고
- refs TRC-03(고아 산출물)을 흡수했다. 차이: 고아 검사는 "요구 ID 인용이 있나"(기계)이고, 제거 시험은 "인용된 요구가 원 요구이고 제거 시 실제로 깨지나"(판단)다. 고아는 제거 시험의 하위 경우라 한 기준에 둔다.

## TRC-04 범위·비목표·소관

- **적용**: 공통 · **범위**: 문서
- **왜 중요한가**: 목표·비목표가 없으면 범위가 커진다. 다른 주체(운영·다른 팀·외부 시스템)의 일을 설계에 끌어오면 그 주체와 결정이 충돌한다.
- **판정 질문**
  - 목표와 비목표(하지 않을 것)가 명시됐는가?
  - 설계가 비목표나 다른 주체의 소관에 속한 일을 다루지 않는가(다루면 원 요구가 그것을 요구하는가)?

**체크포인트**
- 목표·비목표 절의 존재.
- 원 요구의 범위 문장(예: "지금 개발 중인 기능만")과 설계가 다루는 범위의 차이.
- 다른 주체의 진행 중 작업·결정을 이 설계의 결함·작업으로 세었는가.
- 범위 밖 항목이 "참고"로 분리돼 있는가.

**검사 방법**: L+H
- 범위 결정 자체는 사람(H) 몫이다. 판정은 범위 문장과 어긋나는 위치를 짚는다.

**심각도 앵커**
- high: 원 요구가 범위 밖으로 정한 일을 설계가 상태·작업으로 다룸
- medium: 목표·비목표 절이 없음, 또는 다른 주체의 소관을 결함·작업으로 셈
- low: 범위 밖 항목이 본문에 섞여 있으나 동작에 영향 없음

**근거 요구**: 원 요구의 범위 문장 인용 + 범위를 넘은 설계 위치 인용. 절 부재면 찾아본 곳.

**잡는 결함 범주**: C09
**근거 출처**: UBL(A) goals·non-goals, CC-BP(A) out of scope, SCP-01 (refs)

## TRC-05 작업 순서·의존

- **적용**: multi-doc · **범위**: 문서
- **왜 중요한가**: 선행 조건 없이 시작하는 작업은 되돌리거나 우회 구현을 만든다. 이전·배포 순서가 뒤집히면 운영 장애가 된다.
- **판정 질문**
  - 작업 순서가 의존 관계(데이터 모델 → 계약 → 구현 → 검증 등)와 모순되지 않는가?
  - 외부 확인이 필요한 항목에 기대는 작업이 그 확인 뒤에 놓였는가?

**체크포인트**
- 스키마 변경 전에 그 스키마를 쓰는 작업.
- 외부 확인(EVD-04 목록)에 기대는 작업의 위치.
- 병렬 표시된 작업이 같은 파일·같은 결정을 건드리는가.

**검사 방법**: L

**심각도 앵커**
- high: 이전·배포 순서 역전(옛 코드가 새 스키마를, 새 코드가 옛 데이터를 만남)
- medium: 선행 작업 없이 시작하는 작업, 미확인 사실에 기대는 작업이 확인 전에 놓임
- low: 순서 표기 누락

**근거 요구**: 두 작업의 위치 인용과 의존 근거(데이터 모델·계약 위치) 인용.

**잡는 결함 범주**: C11
**근거 출처**: SK-AN(B) F 작업 순서 모순, BMAD-PO(B) §6
