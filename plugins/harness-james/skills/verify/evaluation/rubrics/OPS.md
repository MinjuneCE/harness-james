# OPS — 관측성·운영

- 버전: 2.0.0 (2026-10-13)
- 적용: 모든 레포 (차원·기준 적용은 레포 프로파일의 traits(server·client)와 dimensions가 정한다)
- 보는 것: 이 PR이 머지·배포된 뒤 **운영자가 문제를 알아채고, 원인 건을 찾고, 멈추거나 되돌리고, 손으로 마무리할 수 있는지** 본다.
  - 서버: 로그 구조·컨텍스트, 메트릭·헬스체크·알림 연결점, 필수 설정 검증·설정 문서 동기화, 배포·롤백 준비, 킬 스위치, 운영자 수동 처리 경로.
  - 클라이언트: 검증 환경 확인 → 반영 → 기준 브랜치 동기화, 전역 설정·서드파티 연동 변경 추적, 운영 스위치(설정으로 끄기), 프런트 오류 가시성.
- 보지 않는 것:
  - 로그·오류 응답에 토큰·시크릿·개인정보가 나가는 문제 → `SEC`. OPS는 로그의 **형식과 컨텍스트 충분성**만 본다.
  - 자동 복구·재처리 로직의 **정확성**(재호출 금지, 상태 전이) → `REL`. OPS는 자동 복구가 포기한 건을 **사람이 찾고 처리할 경로**가 있는지만 본다.
  - 이미 적용된 마이그레이션 수정 금지·DDL의 데이터 안전성 → `REL`. 락·스캔 비용 → `PERF-04`. OPS는 **배포 순서와 롤백 가능성**(이전 앱 버전이 새 스키마에서 도는가)만 본다.
  - 설정 구조 설계(어떤 값을 설정으로 뺄지, 설정 객체 분리) → `ARCH`. OPS는 **필수 설정 누락이 기동 시점에 드러나는지**와 문서 동기화만 본다.
  - 테스트로 운영 경로를 검증했는지 → `TEST`. 메트릭·알림이 없어서 생기는 피크 용량 문제 → `PERF`(용량), 여기서는 **보이는지**만.
  - 서드파티 스크립트·임베드가 무거운지 → `PERF-06`. OPS는 **변경이 추적되고 되돌릴 수 있는지**만 본다.

## OPS-01 구조화 로그·상관관계

- **적용**: 서버
- **왜 중요한가**: 고객 문의가 오면 운영자는 업무 식별자 하나로 접수 → 판정 → 외부 호출 → 결과를 이어 봐야 한다. 로그에 업무 식별자·작업 식별자·오류 코드가 빠지거나 자유 문장에 섞이면, 피크에 수만 줄 사이에서 해당 건을 찾을 수 없다.
- **판정 질문**:
  1. 이 PR이 추가·변경한 상태 전이·외부 호출·예외 처리 지점에 로그가 있는가? 메시지 언어가 레포 관례와 같고, 컨텍스트는 검색 가능한 구조(`key=value` 또는 구조화 필드)인가?
  2. 새 진입점(스케줄러, 관리자 API, 큐 소비자)이 실행 단위 식별자(요청 ID, 실행 회차)를 남겨 한 건의 흐름을 이을 수 있는가?
  3. 로그 레벨이 의미에 맞는가? 결과 불명·방치는 warn, 실패는 warn/error, 정상 진행은 info. 피크에 폭주할 루프 안 info는 없는가?

**체크포인트**
- 레포에 이미 쓰는 로그 형식이 있으면 그것을 기준선으로 삼고 같은 형식인지 본다.
- 문자열 연결로 메시지를 만들지 않고 로거의 자리표시자·구조화 필드를 쓰는가.
- 새 상태 전이마다 **이전/새 상태**와 업무 식별자가 로그에 남는가.
- 배치·스케줄러: 실행 시작·종료에 처리 건수·성공·실패·소요 시간 요약 한 줄. 건별 info는 피크에 폭주하므로 debug 또는 상태 변경 시에만.
- 예외 처리기가 500 계열 경로를 로그 없이 삼키지 않는가.
- 기존 메서드의 로그 부재는 pre-existing이다. 그 메서드에 새 분기를 추가하면서 로그를 빼먹으면 새 분기의 introduced다.
- 로그 값이 응답 본문 전체·토큰이면 SEC로 보낸다(`also_affects: OPS`).

**심각도 앵커**
- critical: 해당 없음.
- high: 외부 상태를 바꾸는 경로(외부 쓰기 실행, 재처리, 수동 종결)를 추가했는데 결과 로그가 없다. 사후에 "외부 쓰기가 나갔는지"를 로그로 확인할 수 없다.
- medium: 새 실패·결과 불명 분기에 업무 식별자 없는 로그만 있다. 예외를 로그 없이 삼킨다. 루프 안 info 로그(피크 폭주).
- low: 컨텍스트 키 일부 누락. 레포 관례와 다른 메시지 언어. 레벨 부적절. 표준 출력 직접 사용.

**피크 트래픽 관점**: 평시에는 grep으로 찾던 건도 피크에는 로그량이 수십 배다. 키가 일관되지 않으면 로그 검색 쿼리가 맞지 않는다. 건별 info는 로그 비용과 디스크를 함께 키운다.

**근거**: [12-factor XI Logs](https://12factor.net/logs), [OpenTelemetry Logs data model](https://opentelemetry.io/docs/specs/otel/logs/data-model/), Google SRE Book 6장(Monitoring Distributed Systems).

## OPS-02 메트릭·헬스체크·알림 연결점

- **적용**: 서버
- **왜 중요한가**: 결과 불명·대기 건이 쌓이는 것은 로그만으로는 보이지 않는다. 체류 시간·상태별 건수·외부 API 실패/스로틀 비율이 지표로 나와야 알림을 걸 수 있다. readiness가 DB를 보지 않으면 DB가 끊긴 인스턴스에도 트래픽이 들어간다.
- **판정 질문**:
  1. 이 PR이 새 외부 호출·스케줄러·상태를 추가할 때, 그 결과(성공/HTTP 오류/응답 내 오류/스로틀/타임아웃)와 지연을 셀 수 있는 메트릭(counter/timer/gauge)이나 기존 메트릭 태그를 함께 추가하는가?
  2. 헬스·readiness 구성을 바꾼다면 DB·필수 의존성이 readiness에 반영되는가? 외부 API를 liveness에 넣어 외부 장애 때 인스턴스가 재시작 루프에 빠지지 않는가?
  3. 관리 엔드포인트 노출 범위를 바꾼다면 운영에 필요한 것(헬스, 메트릭)만 여는가? (과다 노출은 SEC)

**체크포인트**
- 메트릭 엔드포인트를 열면 그 수집에 필요한 의존성·설정이 함께 오는가.
- 권장 지표: 상태별 건수 gauge, 외부 호출 결과 counter(결과 분류 태그), 호출 지연 timer, 미종료 건 최장 체류 시간 gauge.
- 메트릭 태그에 업무 식별자 같은 **고유값**을 넣으면 카디널리티가 폭발한다 → medium.
- 프레임워크 기본값이 readiness에 DB를 포함하는지 확인한다. 포함하지 않는 경우가 흔하다.
- 스케줄러가 마지막 성공 실행 시각을 노출하는가(스케줄러가 조용히 멈추면 아무도 모른다).
- 알림 도구·채널은 레포 프로파일에 없으면 미확인으로 둔다. PR은 "어떤 지표에 어떤 임계로 알릴지"를 PR 설명이나 문서에 남기면 충분하다.

**심각도 앵커**
- critical: 해당 없음.
- high: 자동 복구·폴링 스케줄러를 추가하면서 진행 상황(처리 건수, 실패, 마지막 실행 시각)을 로그 외에 볼 수단이 전혀 없다. liveness에 외부 의존성을 넣는다.
- medium: 새 외부 호출 결과·지연 메트릭 없음. readiness에 DB 미포함 상태로 배포 probe를 추가한다. 고카디널리티 태그.
- low: 메트릭 이름·태그 규칙 불일치. 알림 임계값 문서화 누락.

**피크 트래픽 관점**: 피크에 가장 먼저 무너지는 신호는 외부 API 지연·스로틀 증가와 처리 중 체류 시간 증가다. 지표가 없으면 고객 문의가 첫 알림이 된다.

**근거**: Google SRE Book 6장(four golden signals), [Kubernetes liveness·readiness probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/), [Prometheus naming·label 관행](https://prometheus.io/docs/practices/naming/).

## OPS-03 필수 설정 검증·설정 문서 동기화

- **적용**: 서버
- **왜 중요한가**: 필수 설정이 없어도 서비스가 **정상 기동**하면, 런타임에 해당 요청이 전부 실패 종료 상태로 끝난다. 멱등성 키 때문에 재요청도 막히면 복구할 길이 없다. 설정 누락은 기동 시점에 실패해야 한다.
- **판정 질문**:
  1. 이 PR이 추가한 설정 키 중 운영에 반드시 필요한 값이 **기동 시 검증**(바인딩 + 필수·범위 제약)되는가? 아니면 런타임에 null을 확인하고 조용히 실패하는가?
  2. 새 환경변수가 환경변수 예시 파일·설정 문서에 이름·용도와 함께 추가되었는가? 설정 파일의 키 매핑도 함께 있는가?
  3. 기본값을 준다면 그 기본값이 운영에서 안전한가(돈·재고에 미치는 영향)? 위험한 값을 조용히 기본값으로 두지 않는가?

**체크포인트**
- 같은 레포에 검증이 붙은 설정 객체와 없는 설정 객체가 섞여 있으면, PR이 어느 쪽 패턴을 따르는지 본다.
- 기본값 없는 환경변수 참조는 기동 시 실패하므로 "필수"가 명확하다. 빈 기본값은 검증이 없으면 조용히 빈 값이 된다.
- 환경변수 이름과 설정 키 이름이 자동으로 이어진다고 가정하지 않는다. 로딩 경로(파일, 환경변수, 프로파일)마다 매핑이 실제로 되는지 본다. 확신이 없으면 confidence를 likely 이하로.
- 환경별 설정 분리를 도입하면 환경별 필수 키 목록이 문서화되는가.
- 기존 검증 없는 설정 객체에 필드를 추가하면서 검증을 안 붙이면 `worsened`, 붙이면 `fixed`.

**심각도 앵커**
- critical: 돈 경로 설정(환불·재고·고객 알림, 외부 쓰기 실행 여부)이 없을 때 서비스가 기동하고, 모든 요청을 종료 상태로 실패시키거나 잘못된 기본값으로 실행한다.
- high: 새 필수 설정에 기동 시 검증이 없고, 누락 시 런타임에 특정 기능이 조용히 꺼지거나 실패한다. 돈 경로 설정에 위험한 기본값.
- medium: 새 환경변수가 예시 파일·설정 문서에 없다. 설정 파일 키 없이 코드에서만 직접 읽는다.
- low: 예시 파일에 용도 설명 누락. 키 이름 규칙 불일치.

**피크 트래픽 관점**: 피크 직전 긴급 배포는 새 설정 키를 들고 온다. 스테이징에 넣은 값이 운영에 빠지면 피크 당일 해당 기능이 전부 실패한다. 기동 실패는 배포 단계에서 바로 드러나니 오히려 안전하다.

**근거**: [12-factor III Config](https://12factor.net/config), 일반 원칙 "fail fast"(Jim Shore, IEEE Software 2004), CWE-1188(안전하지 않은 기본값).

## OPS-04 운영 스위치 (킬 스위치·기능 끄기)

- **적용**: 공통
- **왜 중요한가**: 피크에 외부 의존성이 불안정하거나 로직 결함이 보이면, 재배포 없이 **자동 실행을 멈추고 접수만 받는** 전환이 필요하다. 클라이언트는 문제를 일으키는 프로모션·서드파티 기능을 설정에서 바로 끌 수 있어야 한다. 코드에 기간·동작이 박혀 있으면 끄는 데 배포가 필요하다.
- **판정 질문**:
  1. (서버) 이 PR이 외부 상태를 바꾸는 자동 동작(외부 쓰기, 폴링 스케줄러, 재처리)을 추가·변경할 때 설정 플래그로 끌 수 있는가? 꺼졌을 때 요청은 안전한 보류 상태로 남는가?
  2. (클라이언트) 새 프로모션·카운트다운·배너·서드파티 연동을 콘텐츠 설정으로 켜고 끌 수 있는가? 아니면 코드 수정이 필요한가?
  3. 기간(시작·종료 시각)이 코드에 하드코딩되지 않고 설정·콘텐츠 데이터로 주입되는가?

**체크포인트**
- 스위치는 외부 쓰기 **직전**에 확인되어야 한다. "처리 중" 상태를 저장한 뒤 멈추면 결과 불명 건이 생긴다(안전성 판단은 REL과 함께).
- 재기동 없는 동적 전환이 필요한지는 확인 질문으로 남긴다.
- 스위치 키 자체도 OPS-03 규칙(문서화, 검증)을 따르는가.
- 스위치 상태가 로그·정보 엔드포인트·메트릭에 드러나는가(꺼진 줄 모르고 장애로 오인하는 것 방지).
- 클라이언트 코드의 날짜 리터럴(고정 캠페인 날짜 비교)은 기간 하드코딩 신호다.
- 서드파티 연동 스크립트가 해당 연동을 꺼도 오류 없이 무력화되는가(우아한 저하 자체는 REL, "끌 수 있는가"는 여기).
- 지역·시장별 노출은 설정으로 끌 수 있는가. 파일 복제로만 나뉘어 있으면 끄기가 파일 단위가 된다.
- 필수 설정 누락이 사실상 "항상 꺼짐"으로 동작하는 것은 스위치가 아니라 결함이다(OPS-03).

**심각도 앵커**
- critical: 해당 없음(스위치 부재만으로 금전 손실이 바로 나지는 않는다).
- high: (서버) 외부 상태를 바꾸는 새 자동 동작에 끄는 수단이 없다. (클라이언트) 전 페이지 노출 요소(전역 배너, 카운트다운, 서드파티 연동 스크립트)가 코드에 박혀 끄려면 배포가 필요하다.
- medium: 스위치는 있지만 꺼졌을 때 동작이 정의되지 않았다. 기간이 코드에 하드코딩되어 있다.
- low: 스위치 상태가 관측되지 않는다. 설정 이름이 모호하다.

**피크 트래픽 관점**: 피크 기간에는 변경 동결로 배포가 막히는 경우가 많다. 그때는 "끄는 것"이 유일한 대응 수단이다. 이 기준은 피크 전에 갖춰져야 의미가 있다.

**근거**: Martin Fowler "Feature Toggles"(Pete Hodgson, 2017), Michael Nygard 『Release It!』(circuit breaker·governor 패턴).

## OPS-05 배포 순서·롤백 준비

- **적용**: 공통
- **왜 중요한가**: 스키마와 앱을 함께 되돌려야 하는 변경, 환경 간 마이그레이션 버전 체계 불일치, 수동 반영 후 저장소를 뒤에 맞추는 흐름은 모두 "무엇이 배포됐고 어떻게 되돌리는가"를 흐린다. PR에 그 답이 없으면 사고 때 되돌릴 수 없다.
- **판정 질문**:
  1. (서버) 스키마 변경이 있다면 이전 앱 버전이 새 스키마에서 계속 동작하는가(expand → migrate → contract)? 아니면 롤백 시 앱과 스키마를 함께 되돌려야 하는가? PR 설명에 순서가 있는가?
  2. (서버) 배포 구성(컨테이너, CI, 환경별 설정)을 바꾼다면 스테이징 → 운영 승격 경로와 환경별 설정이 함께 정의되는가?
  3. (클라이언트) PR 설명에 미리보기·스테이징 검증 흔적, 반영 후 기준 브랜치 동기화 계획이 있는가? 대량 변경은 롤백용 스냅샷·복제를 언급하는가?

**체크포인트**
- 컬럼 삭제·이름 변경·기본값 없는 NOT NULL 추가는 이전 앱 버전과 비호환이다 → 롤백 불가. 단계 분리를 요구한다.
- 환경 간 마이그레이션 버전 체계가 다르면 새 파일 번호가 어느 체계를 따르는지, 승격 전략(baseline, repair)을 PR이 설명하는가.
- 운영에서 스키마 전체 삭제(clean)를 허용하는 설정 변경은 SEC/REL과 공동, 운영 리스크로 high.
- 배포 산출물을 추가하면 헬스체크 경로(OPS-02)와 graceful shutdown(진행 중 외부 쓰기 보호)을 설정하는가.
- 레포 프로파일에 정의된 승격 브랜치 순서를 건너뛴 PR → medium.
- 저장소와 실행 환경이 양방향 동기화되는 연동이 있으면, 머지가 곧 반영이 될 수 있다. 연동 여부를 모르면 확인 질문.
- 대량 설정·템플릿 데이터 변경은 실행 환경에서 그사이 바뀐 값을 덮어쓸 위험이 있다. PR이 "운영에서 가져온 최신 기준"인지 밝히는가.
- 템플릿·화면 단위 삭제: 운영에서 그것을 참조하는 콘텐츠가 있으면 기본값으로 떨어진다. 삭제 목록과 참조 확인을 언급하는가(무결성 자체는 REL).
- 판정 입력:
  - PR 대상 실행: PR 본문과 커밋을 보고 위 항목과 앵커대로 판정한다.
  - 브랜치 대상 실행(`context.target.pr`가 null): PR 본문이 아직 없으므로 기록·언급이 없다는 이유로는 감점하지 않는다(검증 흔적, 동기화 계획, 기준 시점, 롤백 스냅샷, 삭제 목록).
  - 브랜치 실행에서 커밋에도 언급이 없으면 `severity: info` finding 하나만 남긴다. 근거는 영향이 가장 큰 변경 1곳만 적고, recommendation에 PR 본문에 적을 내용을 확인 질문으로 쓴다.

**심각도 앵커**
- critical: 해당 없음(롤백 불능 자체는 high까지. 실제 데이터 손실은 REL에서 critical).
- high: 이전 앱 버전과 호환되지 않는 스키마 변경을 단일 배포로 묶고 롤백 계획이 없다. 운영 덮어쓰기 위험이 큰 대량 설정 변경에 기준 시점·스냅샷 언급이 없다(PR 대상 실행). 운영 스키마 clean 허용.
- medium: 마이그레이션 버전 체계 혼선을 늘리는 새 파일. 승격 경로를 건너뛴 PR. 클라이언트 PR에 검증 흔적이 없다(PR 대상 실행).
- low: graceful shutdown 미설정. 배포 메모 누락(클라이언트는 PR 대상 실행만).

**피크 트래픽 관점**: 피크 중 롤백은 "몇 분 안에, 데이터 손실 없이"여야 한다. 스키마와 앱을 함께 되돌려야 하는 변경은 피크 창 전에 끝내야 한다. 피크 직전에는 운영 환경 직접 수정이 잦아 그 시기의 머지·반영이 덮어쓰기 위험이 가장 크다.

**근거**: Martin Fowler "ParallelChange"(expand-contract), Jez Humble·David Farley 『Continuous Delivery』, [12-factor V Build, release, run](https://12factor.net/build-release-run).

## OPS-06 운영자 수동 처리 경로

- **적용**: 서버
- **왜 중요한가**: 결과 불명 건의 재호출 금지, 대기 만료, 최대 확인 횟수 초과는 결국 **사람이 판단해 종결**해야 한다. DB를 직접 고치는 것 말고 방법이 없으면, 직접 UPDATE가 상태 머신·낙관적 락·감사 기록을 모두 우회한다.
- **판정 질문**:
  1. 이 PR이 "자동으로 처리하지 않고 사람에게 넘기는" 상태·분기(최대 횟수 초과, 수동 확인 대상, 결과 불명 장기 체류)를 추가할 때, 운영자가 그 목록을 **조회**하고 **종결·재처리**할 경로(관리자 API, 런북 명령)가 있거나 계획이 문서화되어 있는가?
  2. 수동 처리 경로가 도메인 상태 전이 규칙을 거치고, 누가·언제·왜 바꿨는지 기록하는가?
  3. 재처리 명령이 결과 불명 건에 외부 쓰기를 다시 보낼 수 있는 경로라면, 조회로 확정하는 절차를 강제하는가(안전성 판단은 REL, 경로 존재·감사는 여기)?

**체크포인트**
- 새 관리자·내부 엔드포인트: 인증·인가는 SEC. 여기서는 상태 필터 조회(페이지네이션 포함), 단건 종결(사유 포함), 재확인 트리거가 있는지 본다.
- 수동 종결 시 기록할 것: 처리자, 처리 시각, 사유, 이전 상태. 스키마에 없으면 최소한 로그(OPS-01)로 남기는가.
- "수동 확인 대상" 표시를 상태로 둘지 플래그로 둘지는 ARCH/REL. OPS는 그 표시를 조회할 수 있는지만 본다.
- 런북: 장기 체류 건 처리 절차(외부 시스템에서 실제 결과 확인 → 종결)가 문서에 있는가. 수동 대상 분기를 만들면서 절차를 남기지 않으면 medium.
- 실패 사유를 저장하지 않으면 운영자가 종결 판단을 할 수 없다.

**심각도 앵커**
- critical: 해당 없음.
- high: 자동 처리를 포기하는 분기를 추가했는데, 운영자가 그 건을 찾을 수단(조회·지표·로그 키)도 처리할 수단도 없다. 수동 처리 경로가 도메인 상태 전이를 우회해 DB를 직접 바꾼다.
- medium: 조회는 되지만 종결·재처리 수단이 없다. 감사 기록이 없다. 런북 누락.
- low: 조회 필터·정렬 부족(예: 체류 시간 순 정렬 없음).

**피크 트래픽 관점**: 피크에는 수동 대상 건이 하루 수십~수백 건 생길 수 있다. 하나씩 DB를 고치는 방식은 피크에 실수(이중 환불, 잘못된 종결)를 부른다. 건수 가정은 레포 프로파일 `parameters`에 값이 있으면 그것을, 없으면 가정을 시나리오에 적고 confidence를 likely 이하로.

**근거**: Google SRE Book 14장(Managing Incidents)·Workbook(playbooks), OWASP ASVS V7(로그·감사 기록), [12-factor XII Admin processes](https://12factor.net/admin-processes).

## OPS-07 전역 설정·서드파티 연동 변경 추적

- **적용**: 클라이언트
- **왜 중요한가**: 전역 설정 한 줄이 전 페이지를 바꾼다(서드파티 연동 켜기/끄기, 무료배송 기준, 색·폰트, 카트 동작). 이런 설정 파일은 편집 도구가 저장할 때마다 통째로 다시 쓰는 경우가 많다. 커밋 메시지가 의미 없는 자동 문구뿐이면, 장애 때 "어제 무엇이 바뀌었나"를 답할 수 없다.
- **판정 질문**:
  1. 이 PR이 전역 설정·설정 스키마·공용 레이아웃 데이터를 바꾼다면, 바뀐 키(특히 서드파티 연동 활성 여부, 가격·배송·카트 관련 값)가 PR 설명이나 커밋 메시지에 명시되어 있는가?
  2. 의도하지 않은 대량 변경(편집 도구 저장 부산물: 키 재정렬, 다른 사람이 운영에서 바꾼 값)이 섞여 있지 않은가? 섞였다면 분리되어 있는가?
  3. 커밋 메시지가 레포 관례(요약, 버전, 이슈 키)를 따르는가? 내용 없는 자동 문구 단독은 아닌가?

**체크포인트**
- 서드파티 연동의 활성 플래그가 바뀌었으면 켜고 끈 연동 이름을 PR이 밝히는가.
- 설정 파일의 diff 줄 수가 의도한 변경보다 훨씬 많으면(의도는 1키, diff는 수백 줄) 편집 도구 저장 부산물 의심 → 확인 질문.
- 지역·시장별 오버라이드 설정: 기본 설정만 바꾸고 오버라이드에 같은 키가 있어 그 지역에는 반영되지 않는 경우(동작 정확성은 다른 차원, 추적성 누락은 여기).
- 커밋 메시지는 diff 밖 정보다. 입력에 커밋 목록이 없으면 질문 3은 `not-touched`로 둔다.

**심각도 앵커**
- critical: 해당 없음.
- high: 서드파티 연동·카트 관련 전역 설정을 바꾸면서 PR 설명·커밋 어디에도 변경 내용이 없고, 의도하지 않은 대량 변경이 섞여 무엇이 바뀌었는지 diff로도 구분하기 어렵다.
- medium: 전역 설정 변경이 PR 설명에 없다. 편집 도구 저장 부산물을 분리하지 않았다.
- low: 커밋 메시지 관례 위반(자동 문구 단독, 버전·이슈 키 누락).

**피크 트래픽 관점**: 피크 직전에는 서드파티 연동(증정·번들·팝업) 켜기와 가격·배송 기준 변경이 몰린다. 장애가 나면 첫 질문이 "무엇을 켰나"인데, 그 답이 커밋에 없으면 관리 화면에서 하나씩 확인해야 한다.

**근거**: [Conventional Commits](https://www.conventionalcommits.org/), Chris Beams "How to Write a Git Commit Message", ITIL 변경 관리(변경 기록·추적성).

## OPS-08 프런트 오류 가시성

- **적용**: 클라이언트
- **왜 중요한가**: 카트 추가·빠른 담기·서드파티 연동 스크립트가 오류를 조용히 삼키면, 사용자는 "버튼이 안 눌린다"고 느끼고 이탈한다. 운영자는 아무 신호도 받지 못한다. 세션 분석·오류 수집 도구가 있어도 오류를 삼키면 거기에도 남지 않는다.
- **판정 질문**:
  1. 이 PR이 추가한 네트워크 요청·이벤트 핸들러·서드파티 연동 코드가 실패 시 오류를 **삼키지 않는가**(빈 catch, 아무것도 하지 않는 rejection 처리)? 최소한 콘솔 오류 로그로 남기고 사용자에게 실패를 알리는가?
  2. 구매 흐름(카트 추가, 수량 변경, 바로 구매) 실패 시 사용자에게 번역된 메시지를 보여 주는가?
  3. 전역 오류·미처리 rejection 처리기를 추가·변경한다면 다른 스크립트의 오류 수집을 덮어쓰지 않는가?

**체크포인트**
- 양호 기준선: 응답 상태 확인 → 실패 시 오류 로그, 버튼·UI 상태 복구, 번역 키로 안내.
- 빈 catch는 레포 소유 코드에서만 본다. 벤더가 배포하는 코드·서드파티 생성 코드는 제외한다.
- 응답 상태를 확인하지 않는 카트·주문 API 호출. 재고 부족 같은 4xx를 확인하지 않으면 성공 UI를 보여 준다(동작 오류는 REL, 신호 부재는 여기).
- 디버그 로그 잔재는 low. 운영 오류 신호와 구분한다.
- 서드파티 이벤트 핸들러가 대상 요소가 없을 때(조회 결과 null) 예외를 내는가.
- 사용하지 않는(렌더링되지 않는) 코드의 오류 삼킴은 pre-existing·low로 둔다.

**심각도 앵커**
- critical: 해당 없음(구매 불능 자체는 REL critical).
- high: 카트 추가·결제 진입 경로에서 오류를 삼키고 성공 UI를 보여 준다. 사용자와 운영자 모두 실패를 모른다.
- medium: 비구매 경로의 오류 삼킴. 실패 시 사용자 안내 없음. 전역 오류 처리기가 다른 수집기를 덮어쓴다.
- low: 하드코딩 오류 문구(번역은 A11Y로 `also_affects`). 디버그 로그 잔재.

**피크 트래픽 관점**: 피크에는 재고 소진·API 지연·서드파티 서버 오류가 평시보다 훨씬 잦다. 실패를 삼키는 코드는 평시엔 드러나지 않다가 피크에 "결제가 안 된다" 문의로 터진다.

**근거**: CWE-390(오류 감지 후 조치 없음), CWE-391(확인하지 않은 오류 조건), [WCAG 2.2 SC 3.3.1 Error Identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html).
