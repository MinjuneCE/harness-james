# PERF — 성능·확장성 (피크 트래픽)

- 버전: 2.0.0 (2026-10-13)
- 적용: 모든 레포 (차원·기준 적용은 레포 프로파일의 traits(server·client)와 dimensions가 정한다)
- 보는 것: 이 PR이 **피크 트래픽에서의 용량·지연**을 어떻게 바꾸는지 본다. 서버는 외부 API 호출 예산, 요청 처리 스레드·DB 커넥션 점유, 쿼리·인덱스·폴링 비용, 캐싱·급증 흡수를 본다. 클라이언트는 Core Web Vitals(LCP·INP·CLS)에 영향을 주는 렌더 차단 자원, 자산·이미지 무게, 템플릿·컴포넌트 렌더 비용, 상호작용당 요청 수와 메인 스레드 작업을 본다.
- 보지 않는 것:
  - 타임아웃·재시도·백오프 **정책 자체**와 결과 불명 처리 → `REL`. PERF는 그 정책이 없거나 잘못됐을 때의 **용량 영향**(스레드·커넥션 고갈, 예산 소진)만 본다. 같은 코드 줄이면 정책 문제는 REL, 용량 문제는 PERF에 올리고 `also_affects`로 연결한다.
  - 트랜잭션 경계의 **정합성**(부분 반영, 락 충돌 처리) → `REL`. 트랜잭션이 외부 호출을 감싸 커넥션을 오래 쥐는 문제는 PERF-03.
  - 오래된 캐시로 상태를 잘못 판단하는 위험 → `REL`. PERF는 캐시의 성능 이득과 캐시 부재·무효화 폭주만 본다.
  - 레이트 리밋·CORS·봇 차단의 **남용 방지** 측면 → `SEC`. 레이트 리밋이 정상 피크 트래픽을 받아낼 수 있는지는 PERF-05.
  - 외부 스크립트의 **공급망**(버전 미고정, 무결성 검증) → `SEC`. 같은 스크립트가 렌더를 막는 문제는 PERF-06.
  - 메트릭·알림 **존재 여부** → `OPS`. 적용된 마이그레이션 수정 금지 → `REL`(DDL의 락·스캔 비용만 PERF-04).
  - 사용자 흐름 무결성·외부 위젯 장애 시 우아한 저하 → `REL`. 이미지 대체 텍스트·포커스 → `A11Y`. 벤더 코드 직접 수정 → `ARCH`(크기 증가만 PERF-07).

## 피크 가정 다루기

- 피크 배수, 피크 요청량, 외부 API 예산(회복 속도·버킷 크기), 성능 예산은 레포 프로파일 `parameters`에 값이 있으면 그것을 쓴다. 없으면 가정을 `failure_scenario`에 적고 confidence를 likely 이하로 둔다.
- "평시 OK"는 근거가 아니다. 피크에는 요청 수, 외부 지연, 처리 대기 적체가 **동시에** 커진다.
- 용량은 리틀의 법칙으로 본다. 동시 점유 자원 ≈ 초당 요청 × 요청당 점유 시간. PR이 어느 항을 키우는지 적는다.

## PERF-01 외부 API 호출 예산·스로틀 대응

- **적용**: 서버
- **왜 중요한가**: 외부 플랫폼 API는 대개 앱·계정 단위 예산(호출 수 또는 쿼리 비용, leaky bucket 등)을 둔다. 인스턴스가 여러 개여도 요청 처리·주기 작업·재처리가 모두 **같은 예산 하나**를 나눠 쓴다. 예산을 넘으면 스로틀 응답이 오고, 그것을 일반 오류로 다루면 핵심 흐름이 전면 실패한다. 스로틀이 HTTP 성공 코드 안의 오류 본문으로 오는 API도 있다.
- **판정 질문**:
  1. 이 PR이 요청 1건당, 또는 주기 작업 1회당 외부 API 호출 수나 요청 비용을 늘리는가? 늘린다면 피크 가정에서 예산 조건(아래)을 만족하는가?
  2. 새 쿼리가 큰 페이지 크기·중첩 객체로 요청 비용을 키우거나, 쓰지 않는 필드·객체를 가져오는가?
  3. 대량 호출 경로(폴링·배치·재처리)가 응답의 비용·잔여 예산 정보를 읽어 속도를 조절하는가? 스로틀 응답을 받고도 같은 속도로 계속 치는가?

**체크포인트**
- 예산 조건: (피크 초당 요청 × 요청당 비용) + 주기 작업 초당 비용 + 다른 기능 몫 ≤ 회복 속도 × 여유율. 여유율은 버스트·재시도 몫을 남겨 0.5 안팎으로 본다. 주기 작업 비용 = 대상 건수 × 건당 비용 ÷ 주기.
- 요청 비용은 대개 실행 전 "요청한 비용"으로 판정된다. 큰 컬렉션 필드는 페이지 크기 × 하위 비용이라 한 번에 수백 단위가 될 수 있다.
- 같은 요청 안에서 같은 리소스를 다시 조회하는 경로가 늘었는가? 기존 호출 수를 기준선으로 비교한다.
- 주기 작업의 대상 건수에 상한(페이지 크기·LIMIT)이 있는가? 상한 없는 대상 × 건별 호출은 적체와 함께 커진다.
- 여러 건을 다루는 작업이 묶음 조회를 쓸 수 있는데 건별 호출을 반복하는가.
- 클라이언트 래퍼가 응답의 비용·스로틀 메타데이터를 버리는가? 대량 경로를 추가하면서 그것을 읽지 않으면 해당한다.
- 스로틀 오류 구분 여부. 구분이 없을 때의 **재시도 정책**은 REL 소관이고, PERF는 "스로틀을 모르고 계속 호출해 예산 회복을 막는가"만 본다.
- 인스턴스·스케줄러 수를 늘리는 배포 변경: 예산은 그대로이고 소비자만 는다. 주기 작업이 인스턴스마다 도는가?
- 이미 스로틀 대응이 없는 클라이언트로 새 대량 호출 경로를 추가하면 `worsened`다.

**심각도 앵커**
- critical: 피크 가정에서 예산 조건 좌변이 회복 속도를 넘는 것이 코드로 보인다. 예: 미종료 전체 건을 매 주기 건별로 폴링하고 상한·스로틀 조절이 없어, 핵심 흐름의 신규 요청까지 스로틀로 실패한다.
- high: 요청당 호출 수나 비용을 늘려 여유율을 넘길 수 있다(likely). 대량 호출 경로를 추가하면서 비용·스로틀 정보를 전혀 다루지 않는다. 단일 요청 비용이 예산 대비 큰 비중이다.
- medium: 같은 요청 안에서 불필요한 중복 조회를 추가했다(이미 가진 결과를 다시 조회). 묶음 조회가 가능한데 건별 루프를 돈다(대상 수가 작을 때).
- low: 쓰지 않는 필드·객체를 쿼리에 추가했다.

**피크 트래픽 관점**: 평시 소량이면 어떤 설계도 예산 안에 들어간다. 피크에는 ① 요청 증가 ② 처리 대기 건 증가로 폴링 대상 증가 ③ 외부 지연으로 재처리 증가가 동시에 일어난다. 예산 위험은 요청 접수보다 주기 작업 쪽이 큰 경우가 많다. 피크 배수를 곱한 값으로 조건을 다시 본다.

**근거**: IETF RFC 6585(429 Too Many Requests), Google SRE Book "Handling Overload", AWS Builders' Library "Timeouts, retries, and backoff with jitter", CWE-770(Allocation of Resources Without Limits or Throttling).

## PERF-02 요청 스레드의 동기 외부 호출과 동시성 용량

- **적용**: 서버
- **왜 중요한가**: 요청 처리 스레드(또는 동시 처리 슬롯)는 유한하다. 요청마다 외부 호출이 동기로 여러 번 돌고 타임아웃이 없으면, 외부가 피크에 느려질 때 스레드가 고갈되고 대기 큐를 넘으면 연결이 거부된다. 그러면 헬스체크를 포함한 API 전체가 멈춘다.
- **판정 질문**:
  1. 이 PR이 요청 처리 경로에 **동기 외부 호출을 추가**하거나, 기존 호출을 반복·직렬화하는가?
  2. 요청 경로에 sleep·바쁜 대기·동기 폴링 루프(외부 작업 완료를 요청 안에서 기다림)를 넣는가?
  3. 스레드 모델(스레드 풀 크기, 경량·가상 스레드 전환, 별도 executor)을 바꾼다면 하위 자원(커넥션 풀, 외부 API 예산, 락으로 직렬화된 구간)과의 관계를 설명하는가?

**체크포인트**
- 요청 경로의 외부 호출 수를 기준선과 비교한다. 독립 호출을 이유 없이 순차 실행하는가.
- 외부 비동기 작업의 완료를 요청 안에서 반복 조회하며 기다리는 루프. 이런 대기는 주기 작업·워커로 가야 한다.
- 경량·가상 스레드 전환: 스레드 수 제한이 사라지므로 병목이 커넥션 풀과 외부 API 예산으로 옮겨간다. 락으로 보호된 구간 안의 블로킹 I/O는 런타임에 따라 캐리어 스레드를 붙잡을 수 있다. 이에 대한 설명이 없으면 medium.
- 비동기 처리 도입 시 풀·큐 크기가 무제한이면 PERF-05와 함께 본다.
- 외부 호출 타임아웃 값 결정은 REL. PERF는 "타임아웃 없는 새 호출을 요청 스레드에 추가했다"를 **용량 문제**로 본다(기존에 타임아웃이 없으면 `worsened`).

**심각도 앵커**
- critical: 요청 스레드에서 외부 작업 완료를 무기한 대기한다(타임아웃 없는 폴링·sleep 루프). 외부 지연 시 스레드가 모두 묶여 핵심 API가 전면 정지한다.
- high: 요청 경로에 타임아웃 없는 동기 외부 호출을 1회 이상 추가했다. 경량 스레드를 켜면서 커넥션 풀·외부 예산 병목을 따지지 않았다.
- medium: 요청 경로 호출 수 증가(타임아웃은 있음). 독립 호출 직렬 실행.
- low: 요청 경로에서 무거운 동기 로깅·직렬화 반복.

**피크 트래픽 관점**: 동시 스레드 ≈ 초당 요청 × 요청당 체류 시간. 외부 응답이 평시 0.3s × 4회 = 1.2s면 스레드 200개로 초당 160건을 버틴다. 피크에 응답이 2s로 늘면 8s/건이라 초당 25건에서 고갈된다(예시 값). 이 PR이 체류 시간 항을 늘리는지 본다.

**근거**: Little's Law, Google SRE Book "Addressing Cascading Failures", Michael Nygard "Release It!"(Timeouts, Bulkheads, Blocked Threads), CWE-400(Uncontrolled Resource Consumption).

## PERF-03 DB 커넥션을 쥔 채 외부 호출 (트랜잭션 범위)

- **적용**: 서버
- **왜 중요한가**: 커넥션 풀은 보통 작다(수~수십 개). 정합성을 이유로 서비스 메서드 전체를 트랜잭션으로 감싸면 외부 HTTP 지연 동안 **커넥션을 계속 쥔다**. 피크에 풀이 HTTP 대기로 묶이면 다른 요청은 커넥션 대기 타임아웃까지 기다리다 실패한다. 정합성 부채를 고치려는 PR이 이 기준을 새로 위반하기 가장 쉽다.
- **판정 질문**:
  1. 이 PR이 추가·변경한 트랜잭션 경계(선언형·프로그램형·클래스 단위) 안에서 외부 API 호출(조회·변경·토큰 발급)이 실행되는가?
  2. 비관적 락이나 DB 기반 분산 락을 잡은 채 외부 호출을 하는가?
  3. 주기 작업이 한 트랜잭션 안에서 여러 건을 돌며 건마다 외부 호출을 하는가?

**체크포인트**
- 트랜잭션 선언이 외부 호출을 포함하는 메서드를 감싸는가. 클래스 단위 선언은 모든 공개 메서드에 적용된다.
- 같은 객체 내부 호출로 "새 트랜잭션" 전파 설정이 실제로 적용되지 않는 프록시 기반 패턴. 의도는 짧은 트랜잭션이지만 실제로는 바깥 트랜잭션이 외부 호출을 감싼다.
- 뷰 렌더까지 영속성 세션을 열어 두는 설정을 켜거나 기본값으로 되돌리면 요청 전체가 커넥션을 쥘 수 있다.
- 주기 작업의 권장 형태: 짧은 트랜잭션으로 선점(상태·다음 확인 시각 갱신) → 커밋 → 외부 호출 → 짧은 트랜잭션으로 결과 반영.
- 커넥션 풀 크기·대기 타임아웃 변경 시 DB 최대 커넥션 수 × 인스턴스 수와의 관계를 설명하는가.

**심각도 앵커**
- critical: 핵심 요청 경로 전체를 하나의 트랜잭션으로 감싸 여러 번의 외부 호출 동안 커넥션을 점유하고, 외부 호출 타임아웃도 없다. 외부 지연 시 풀이 고갈되어 핵심 API가 전면 정지한다(likely 이상).
- high: 트랜잭션·비관적 락 안에서 외부 호출 1회. 또는 주기 작업이 배치 전체를 한 트랜잭션으로 돌며 건별 외부 호출을 한다.
- medium: 외부 호출은 트랜잭션 밖이지만 트랜잭션 안의 대량 조회·정렬로 점유가 수백 ms를 넘는다(근거가 코드에 있을 때). 뷰 렌더까지 세션을 여는 설정을 켰다.
- low: 읽기 전용 조회에 불필요한 쓰기 트랜잭션.

**피크 트래픽 관점**: 커넥션 점유 시간 = DB 작업 + 외부 호출 시간. 외부 응답 0.3s면 풀 10개로 초당 30건, 2s로 늘면 초당 5건이 한계다(예시 값). 평시 테스트로는 드러나지 않는다.

**근거**: Martin Kleppmann "Designing Data-Intensive Applications"(트랜잭션), Chris Richardson "Microservices Patterns"(Transactional Outbox), Michael Nygard "Release It!"(Blocked Threads), Little's Law.

## PERF-04 DB 쿼리·인덱스·락·폴링 비용

- **적용**: 서버
- **왜 중요한가**: 작업·이력 테이블은 피크 이후 빠르게 커진다. 주기 작업이 인덱스 없이 상태·시각 조건으로 찾으면 주기마다 풀스캔한다. 상한 없는 조회는 메모리와 커넥션을 함께 잡는다.
- **판정 질문**:
  1. 새 조회 조건의 WHERE·ORDER BY 컬럼에 맞는 인덱스가 마이그레이션에 있는가?
  2. 조회 결과에 상한(LIMIT·페이지)이 있는가? 루프에서 건별 조회(N+1)를 하는가?
  3. 새 DDL이 큰 테이블에 잠금·전체 재작성을 일으키는가? 폴링 주기 × 대상 건수 × 건당 DB 작업이 합리적인가?

**체크포인트**
- "상태 = X 그리고 다음 확인 시각 < 지금" 같은 주기 조회에는 그 순서의 복합 인덱스가 필요하다. 같은 스키마의 다른 환경 마이그레이션에 있는 인덱스가 한 환경에서 빠져 있지 않은지도 본다.
- 전체 조회를 목록으로 받으면서 페이지·상한이 없으면 해당한다.
- 주기 작업 루프 안의 조회·저장 반복, 연관 엔터티 지연 로딩(N+1). 새 연관 테이블을 추가할 때 생기기 쉽다.
- 선점 방식: 대기형 행 잠금 vs 잠긴 행 건너뛰기 vs 버전 조건부 갱신. 다중 인스턴스 락 경합이 커지는 방식이면 해당한다.
- DDL: 인덱스 추가는 대부분 온라인으로 가능하지만 연산·엔진별로 다르다. 컬럼 타입 변경은 테이블 재작성이 생길 수 있다. 확인이 안 되면 confidence를 낮춘다.
- 한 요청에서 같은 엔터티를 여러 번 강제 flush하는 횟수를 늘리는가.
- 인덱스 부재가 기존 상태라도, 그 인덱스가 필요한 주기 조회를 **추가하는 PR**이면 introduced로 본다.

**심각도 앵커**
- critical: (드묾) 폴링 쿼리가 운영 테이블 전체를 매 주기 잠가 핵심 쓰기가 막힌다(예: 상한 없는 잠금 조회).
- high: 주기 실행 쿼리에 인덱스도 결과 상한도 없다. 또는 피크 대상 건수가 많은데 비관적 락을 대기 모드로 잡는다.
- medium: 인덱스 없는 신규 조회. 상한 없는 전체 조회. 루프 안 건별 조회.
- low: 불필요한 flush 추가. 필요 없는 전체 컬럼·엔터티 로딩.

**피크 트래픽 관점**: 미종료 건은 피크에 급증하고 처리가 밀리면 더 쌓인다. 폴링 비용은 대상 건수에 비례한다. 인덱스·상한이 없으면 적체가 쿼리를 느리게 하고, 그것이 다시 적체를 키운다.

**근거**: Markus Winand "Use The Index, Luke", Martin Kleppmann "Designing Data-Intensive Applications", CWE-1049(Excessive Data Query Operations in a Large Data Table), CWE-1073(Non-SQL Invokable Control Element with Excessive Number of Data Resource Accesses).

## PERF-05 캐싱·급증 흡수·백프레셔

- **적용**: 서버
- **왜 중요한가**: 피크 급증을 흡수하는 장치(캐시, 접수/처리 분리, 큐, 동시 실행 상한)가 없으면 외부 지연이 곧바로 API 장애가 된다. 반대로 상한 없는 큐·executor는 메모리 고갈로 끝난다.
- **판정 질문**:
  1. 캐시를 추가·제거·변경할 때, 캐시 미스가 몰리는 경우(동시 만료, 다중 인스턴스)에 외부 호출이 폭주하지 않는가?
  2. 비동기 처리·큐·executor를 도입한다면 **크기 상한**과 넘쳤을 때의 동작(거절·429·지연 처리)이 정의되어 있는가?
  3. 레이트 리밋·동시성 제한을 추가한다면 그 값이 정상 피크를 받아낼 만큼인가(너무 낮아 정상 요청을 버리지 않는가)?

**체크포인트**
- 수명이 긴 자격 증명(액세스 토큰)·설정 캐시: 캐시를 지우거나, 요청마다 발급을 호출하거나, 갱신 경합 보호(단일 갱신·이중 확인)를 없애면 해당한다. 만료 직전 갱신 여유를 근거 없이 바꾸는 것도 본다.
- 다중 인스턴스: 인스턴스마다 캐시를 따로 채운다. 인스턴스 수를 늘리는 PR은 기동 시 발급·조회 폭주를 확인 질문으로 남긴다.
- 정합성 확인용 재조회를 캐시로 대체하는 변경은 REL에 올리고 여기서는 `also_affects`만 한다. PERF는 성능 이득만 본다.
- 접수/처리 분리(접수는 저장 후 즉시 수락 응답, 처리는 워커): 도입 시 워커 동시성 상한을 외부 예산(PERF-01)과 커넥션 풀(PERF-03)에 맞춘다.
- 무제한 스레드를 만드는 executor, 기본 큐 용량이 사실상 무제한인 풀 → 해당.
- 레이트 리밋 값이 하드코딩되어 있고 피크 근거가 없다 → 확인 질문.
- 양호한 기존 캐시를 훼손하는 변경은 introduced다.

**심각도 앵커**
- critical: 자격 증명 캐시를 제거해 요청마다 발급 호출을 추가한다. 피크에 발급 엔드포인트 호출이 요청 수만큼 늘어 발급 실패 → 전 요청 실패(likely).
- high: 상한 없는 executor·큐 도입. 캐시 동시 만료 시 갱신 경합 보호 제거.
- medium: 흡수 장치 없이 동기 처리 단계를 늘린다(PERF-02와 겹치면 PERF-02에만 올림). 레이트 리밋 값이 피크 근거 없이 낮게 고정되었다.
- low: 캐시 TTL·안전 여유를 근거 없이 바꿈.

**피크 트래픽 관점**: 급증은 초당 요청과 외부 지연이 동시에 커지는 형태로 온다. 흡수 장치가 없으면 외부 지연이 그대로 사용자 오류가 되고, 상한 없는 흡수 장치는 장애를 몇 분 늦출 뿐이다.

**근거**: Google SRE Book "Handling Overload"·"Addressing Cascading Failures", AWS Builders' Library "Using load shedding to avoid overload", Michael Nygard "Release It!"(Back Pressure), CWE-770(Allocation of Resources Without Limits or Throttling).

## PERF-06 렌더 차단 자원·서드파티 스크립트

- **적용**: 클라이언트
- **왜 중요한가**: 공통 레이아웃의 head에 들어간 것은 **모든 페이지**의 첫 렌더를 늦춘다(LCP). 렌더 차단 CSS·외부 폰트·서드파티 위젯이 이미 쌓인 화면에 한 줄을 더하면 랜딩·상품 상세 전부가 느려진다. 외부 도메인 장애가 그대로 우리 페이지 장애가 될 수도 있다.
- **판정 질문**:
  1. head나 페이지 상단에 `async`/`defer`/`type="module"` 없는 외부 `<script src>`를 추가하는가?
  2. 렌더 차단 CSS(`<link rel=stylesheet>`, CSS `@import`)·외부 폰트·외부 도메인 자원을 추가하는가? 추가한다면 preconnect·지연 로드·조건부 로드(필요한 화면만)를 하는가?
  3. 전역 서드파티 위젯·임베드를 켜거나, 화면에 서드파티 블록을 추가하는가? 추가에 근거(성능 예산)가 있는가?

**체크포인트**
- 공통 레이아웃에 사본(대체 레이아웃)이 있으면 바뀐 쪽마다 적용한다. 사본 동기화 누락은 ARCH.
- head의 기존 차단 자원 목록과 비교해 추가되는 항목을 센다.
- 페이지 중간 부품 안의 동기 외부 스크립트도 파서를 막는다.
- 전역 부품의 새 인라인 스크립트가 긴 동기 작업을 하는가.
- 폰트: `font-display: swap`(또는 동등)이 있는가. 외부 폰트 추가 시 preconnect가 있는가.
- 마케팅·분석 코드를 head에 직접 붙이는 변경.
- 특정 화면 전용 스크립트를 그 화면에만 로드하도록 한정했는가.
- `preload`는 1–2개만 쓴다. 남용하면 정작 LCP 자원과 대역폭을 다툰다.
- `preload`·`media="print"` 같은 비차단 트릭으로 로드한 외부 CSS는 차단 자원이 아니다. 코드로 확인한다.

**심각도 앵커**
- critical: (드묾) 모든 페이지 head에 느리거나 실패할 수 있는 외부 동기 스크립트를 넣어, 외부 도메인 장애 시 페이지 렌더가 멈춘다(핵심 구매·사용 흐름 전면 장애, likely).
- high: 공통 레이아웃·전역 영역에 렌더 차단 외부 스크립트·외부 CSS를 추가한다. 전 페이지 대상 서드파티 위젯을 켠다.
- medium: 특정 화면에 동기 외부 스크립트 추가. 전역 렌더 차단 로컬 CSS 추가. 외부 폰트에 preconnect·swap 없음. 핵심 화면에 서드파티 블록 추가.
- low: 지연 로드 스크립트지만 조건부 로드가 가능한데 전 페이지에 둠. preload 3개 이상.

**피크 트래픽 관점**: 피크 랜딩은 광고 유입과 첫 방문(캐시 없음) 비율이 높아 렌더 차단 비용을 매번 그대로 낸다. 서드파티 서버도 피크에 느려진다. 동기 로드면 그 지연이 우리 페이지 지연이 된다.

**근거**: [web.dev Core Web Vitals](https://web.dev/articles/vitals) (good: LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1, p75), [Lighthouse render-blocking resources](https://developer.chrome.com/docs/lighthouse/performance/render-blocking-resources), [HTML Living Standard — script 요소](https://html.spec.whatwg.org/multipage/scripting.html#the-script-element).

## PERF-07 자산 무게·이미지 전달 (LCP·CLS)

- **적용**: 클라이언트
- **왜 중요한가**: 배너·히어로 이미지는 대개 LCP 요소다. 정적 자산으로 원본 이미지를 넣어 그대로 내려보내면 이미지 CDN의 크기 조정·포맷 협상·srcset을 못 쓴다. 수 MB짜리 이미지가 모바일에 그대로 간다. 치수가 없으면 CLS가 생긴다.
- **판정 질문**:
  1. 이미지를 정적 자산 폴더에 원본으로 추가하거나, 반응형 변환을 거치지 않은 원본 URL로 렌더하는가?
  2. 새 이미지에 `width`·`height`(또는 aspect-ratio 컨테이너), `srcset`/`sizes`가 있는가? LCP 후보(첫 화면 히어로·상품 메인 이미지)에 `loading="lazy"`를 붙이지 않았고 `fetchpriority="high"`가 있는가? 첫 화면 밖 이미지는 lazy인가?
  3. 전 페이지에 로드되는 CSS/JS 번들을 크게 키우거나, 개발용 비압축 번들을 운영에서 로드하게 바꾸는가?

**체크포인트**
- 새 래스터 이미지 파일과 그 크기. 수십 KB 아이콘은 low, 수백 KB 이상 배너는 medium 이상.
- 이미지 변환 요청에 목표 너비를 지정하는가(없으면 원본 크기). 고정 크기 문자열을 쓰는 구식 변환 API를 새로 쓰는가.
- 공통 이미지 부품이 있는데 우회해 `<img src>`를 직접 쓰는가.
- CSS 배경 이미지 히어로는 srcset을 못 쓴다. `image-set`·`<picture>` 같은 반응형 대체가 있는가.
- 자동재생 히어로 비디오에 `preload="none"`/poster가 있는가.
- 전역 CSS/JS 크기 증가. 수십 KB 증가면 medium. 벤더 번들 직접 수정은 ARCH가 보고 크기 증가만 여기서 본다.
- 주석 안에서만 참조되던 개발용 번들을 실제 로드로 바꾸는 변경. 반대로 주석 안 참조만 편집한 것은 해당하지 않는다.

**심각도 앵커**
- critical: 해당 없음(성능만으로 구매·사용 불능은 아님).
- high: 핵심 화면 첫 화면 LCP 이미지를 대용량 원본(수백 KB~MB)으로 렌더. LCP 이미지에 `loading="lazy"`. 개발용 비압축 번들 전 페이지 로드.
- medium: 첫 화면 밖 이미지를 원본으로 렌더. 치수 없는 새 이미지(CLS). 변환 너비 미지정. 전역 CSS/JS 수십 KB 증가.
- low: 작은 아이콘 이미지 자산 추가. 구식 고정 크기 변환 사용. lazy 누락(첫 화면 밖, 소형).

**피크 트래픽 관점**: 시즌 랜딩은 큰 배너가 여러 장이고 모바일·저속망 비율이 높다. 평시 화면에서 문제없던 이미지 패턴도 랜딩에서는 LCP 4s 이상으로 이어질 수 있다(**추정**, 실측은 판정 범위 밖).

**근거**: [web.dev Core Web Vitals](https://web.dev/articles/vitals), [web.dev Optimize LCP](https://web.dev/articles/optimize-lcp), [web.dev Optimize CLS](https://web.dev/articles/optimize-cls), [MDN Responsive images](https://developer.mozilla.org/en-US/docs/Web/HTML/Responsive_images).

## PERF-08 템플릿·컴포넌트 렌더 비용

- **적용**: 클라이언트
- **왜 중요한가**: 서버 측 템플릿 렌더가 느리면 TTFB가 늘고 LCP가 같이 밀린다. 클라이언트 컴포넌트 렌더가 무거우면 INP가 무너진다. 플랫폼이 서버를 확장해도 **페이지 하나의 렌더 시간**은 템플릿 복잡도에 달려 있다. 템플릿 엔진이 페이지당 반복·조회 한도를 두는 경우, 한도를 넘으면 결과가 **조용히 잘린다**.
- **판정 질문**:
  1. 새 루프가 큰 컬렉션을 상한·페이지네이션 없이 도는가? 루프가 중첩되는가(항목 × 하위 항목 × 부가 데이터)?
  2. 루프 안에서 전역 조회(핸들·ID로 임의 리소스 조회)를 하거나, 페이지당 조회 한도를 넘을 수 있는가?
  3. 루프 안에서 무거운 부품 렌더(숨은 모달 마크업 포함 카드), 동적 include, 큰 문자열 누적을 하는가?

**체크포인트**
- 컬렉션 루프가 페이지네이션 밖에 있는가. 페이지네이션 안의 루프는 정상이다. 페이지 크기 상한을 본다.
- 카드 하나가 숨은 대화상자·변형 선택 마크업까지 렌더하면 카드 수 × 그 비용이다.
- 루프 안 부가 데이터(메타데이터) 접근, 필터·정렬 연산 반복.
- 화면 구성에 섹션·블록을 대량 추가하면 렌더 비용과 HTML 크기가 함께 는다.
- 상호작용마다 다시 렌더되는 부분(검색 제안, 부분 렌더 엔드포인트)에 무거운 로직을 넣으면 PERF-09와 곱해진다.
- 클라이언트 컴포넌트: 입력마다 큰 목록 전체를 다시 그리는가. 메모이제이션·가상화가 필요한 규모인가.
- 구식 include 문법 신규 사용 자체는 ARCH. 루프 안 동적 include는 여기서 본다.

**심각도 앵커**
- critical: 해당 없음.
- high: 컬렉션 전체 × 하위 항목 × 부가 데이터의 3중 루프. 또는 요청마다 렌더되는 부분 렌더 엔드포인트·검색 제안에 큰 루프 추가.
- medium: 상한·페이지네이션 없는 컬렉션 루프 신규(한도에서 잘림 + 비용). 루프 안 전역 조회. 루프 안 무거운 부품 렌더.
- low: 루프 밖으로 뺄 수 있는 계산 반복. 불필요한 문자열 누적.

**피크 트래픽 관점**: 시즌 컬렉션은 항목 수가 평시보다 많고 할인·배지 로직이 카드마다 붙는다. 평시 수십 개 카드에서 괜찮던 루프가 피크 100개 이상 컬렉션에서 렌더 시간과 HTML 크기를 키운다.

**근거**: [web.dev Time to First Byte](https://web.dev/articles/ttfb), [Lighthouse excessive DOM size](https://developer.chrome.com/docs/lighthouse/performance/dom-size), [web.dev Optimize INP](https://web.dev/articles/optimize-inp).

## PERF-09 클라이언트 요청 수·메인 스레드 작업 (INP·CLS)

- **적용**: 클라이언트
- **왜 중요한가**: 장바구니 드로어·빠른 담기·검색 제안은 상호작용마다 서버 API와 부분 렌더 요청을 보낸다. 요청이 많고 직렬이면 클릭 후 반응이 늦어진다(INP). 늦게 삽입되는 배너·위젯은 레이아웃을 민다(CLS). 같은 이벤트에 반응하는 서드파티 스크립트가 있으면 요청이 곱해진다.
- **판정 질문**:
  1. 사용자 동작 한 번(담기, 수량 변경, 옵션 선택, 검색 입력)당 네트워크 요청 수가 늘어나는가? 여러 부분 렌더를 따로 요청하는데 한 요청으로 묶을 수 있는가?
  2. 입력 이벤트에 debounce가 있는가? `setInterval`·재귀 `setTimeout` 폴링을 추가하는가?
  3. 늦게 삽입되는 요소(공지 배너, 카운트다운, 위젯 컨테이너)에 자리를 미리 잡는가? 이벤트 핸들러가 긴 동기 작업(대량 DOM 조작, 큰 파싱 루프)을 하는가?

**체크포인트**
- 커스텀 스크립트·인라인 스크립트의 새 fetch를 기존 기준선과 비교한다.
- 상태 변경 후 부분 렌더를 하나씩 따로 받는 코드.
- 카드 hover·노출만으로 미리 요청하는(prefetch) 변경은 목록 카드 수만큼 요청이 생긴다 → high.
- 내장 검색 동작을 우회하는 커스텀 입력 핸들러가 키 입력마다 요청하는가.
- 1초 tick 타이머는 정상. tick 안에서 fetch·대량 DOM 갱신을 하면 해당.
- 관찰자·스크롤 핸들러에서 레이아웃 읽기/쓰기 반복(강제 리플로우), passive가 아닌 스크롤 리스너.
- 늦게 채우는 컨테이너에 `min-height` 등 자리 확보가 있는가. 이미지 치수는 PERF-07.
- `alert()` 같은 동기 대화상자는 INP를 망친다(오류 경로에만 있으면 low).

**심각도 앵커**
- critical: 상태 변경 한 번이 자기 자신을 다시 트리거하는 이벤트 루프(변경 이벤트 리스너가 다시 변경 API를 호출). 무한 요청으로 장바구니·핵심 흐름이 사용 불능이 되고 서버 남용 방지에 걸린다(likely).
- high: 목록 카드마다 자동 요청(prefetch). 입력마다 debounce 없는 요청. 상호작용당 부분 렌더 요청 3회 이상 증가.
- medium: 묶을 수 있는 요청 분리. 주기 폴링 추가(분 단위 이상). 늦게 삽입되는 전역 배너에 자리 미확보.
- low: 결과를 쓰지 않는 중복 조회. 오류 경로 `alert`.

**피크 트래픽 관점**: 고정 한도가 공개되지 않은 API도 남용 방지 대상이고, 피크에는 동시 사용자가 몰려 응답이 느려진다. 상호작용당 요청 수가 클수록 피크에 체감 지연·실패가 커진다. 같은 이벤트에 반응하는 서드파티 리스너와 겹치면 요청이 곱해진다.

**근거**: [web.dev Optimize INP](https://web.dev/articles/optimize-inp), [web.dev Optimize CLS](https://web.dev/articles/optimize-cls), [web.dev Optimize long tasks](https://web.dev/articles/optimize-long-tasks), CWE-400(Uncontrolled Resource Consumption).
