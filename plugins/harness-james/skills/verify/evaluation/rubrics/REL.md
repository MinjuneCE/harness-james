# REL — 신뢰성·데이터 정합성

- 버전: 2.0.0 (2026-10-13)
- 적용: 모든 레포 (차원·기준 적용은 레포 프로파일의 traits(server·client)와 dimensions가 정한다)
- 보는 것: 외부 상태를 바꾸는 호출의 안전성(결과가 불확실하면 재실행하지 않기), 멱등성, 상태 전이의 런타임 안전성, 외부 호출 실패 처리(타임아웃·재시도·백오프), 트랜잭션 경계, 동시성 제어, 마이그레이션 안전성, 복구·재처리 경로. 클라이언트는 구매·제출 흐름 무결성, 서드파티 장애 시 우아한 저하, 저장된 설정 스키마 호환성과 렌더 오류.
- 보지 않는 것:
  - 처리량·스레드 풀·커넥션 풀·외부 API 호출 예산의 **용량** 측면, 동기 호출이 피크에서 버티는지 → **PERF** (타임아웃·재시도 **정책 자체**는 REL)
  - 상태 전이 규칙을 도메인이 소유하는지, 외부 값 매핑을 보수적으로 했는지(구조) → **ARCH-02/03** (그 결과 런타임에서 중복 실행·잘못된 확정이 나면 REL)
  - 로그·메트릭·알림·운영자 수동 처리 절차의 **가시성** → **OPS** (복구 경로가 존재하는지, 안전한지는 REL)
  - 가격·프로모션 노출의 정확성, UI의 접근성 → **A11Y**
  - 인증·레이트 리밋의 남용 방지 → **SEC**

## REL-01 불확실 결과 재실행 금지·선영속화

- **적용**: 서버
- **왜 중요한가**: 외부 시스템에서 돈·재고·알림을 움직이는 호출(취소·환불·결제·발송)이 실제로 처리됐는데 응답만 잃은 상태(타임아웃, 5xx, 429, 연결 끊김, 응답 누락)에서 같은 호출을 다시 보내면 부수 효과가 두 번 난다. 호출 전에 "처리 중" 상태를 영속화하지 않으면, 프로세스가 죽은 뒤 초기 상태로 남은 건을 누군가 다시 실행한다.
- **판정 질문**
  - 외부 상태를 바꾸는 호출을 보내기 **전에** "처리 중" 상태가 커밋되는가?
  - 결과 불명(예외, 타임아웃, 비동기 작업 미완료, 완료 후 미확인)인 건에 같은 호출을 다시 보내는 경로(재시도 라이브러리, catch 후 재호출, 스케줄러 재실행, 재요청 시 재처리)가 생기는가?
  - 외부가 돌려준 작업 ID·참조값이 후속 조회 **전에** 저장되는가? 호출 직전에 외부 상태로 전제 조건을 다시 확인하는가?

**체크포인트**
- 순서: 상태 전이 저장(커밋) → 외부 호출 → 결과 저장. 순서가 바뀌거나 저장이 트랜잭션에 묶여 호출 뒤에 커밋되면 위반(REL-04와 함께 본다).
- 작업 ID 저장이 후속 조회보다 먼저다. 조회가 실패해도 ID는 남아야 한다.
- 호출 직전 재조회를 제거하거나 캐시된 스냅샷으로 대체하면 위반이다.
- 변경 호출부를 전수로 센다. 새 호출부(복구 스케줄러, 관리자 재시도 API, 재요청 처리)는 다음 중 하나를 증명해야 한다.
  - 대상이 "처리 중"에 들어간 적 없는 건이다(상태 조건부 전이가 성공해야 진입).
  - 외부 조회로 이전 호출이 **실행되지 않았음**을 확정했다.
- 방어 코드(선영속화·ID 저장·직전 재조회)를 지우는 diff는 같은 PR에서 다른 위치로 옮겼는지 확인한 뒤 판정한다.
- 조회와 변경 호출이 같은 API 클라이언트를 공유하면, 클라이언트에 일괄 재시도를 걸 때 변경 호출도 재시도된다.
- 레이트 리밋 거절 예외: 외부 API가 한도를 **실행 전에** 검사한다고 문서로 보장하고 응답에 결과 데이터가 없으면 미실행으로 볼 수 있다. 그래도 레포 원칙이 429를 불확실로 정했다면, 원칙 개정 근거 없이 재시도 대상으로 분류하면 high다. critical로 보지 않는다.

**심각도 앵커**
- critical: 결과 불명 건에 변경 호출을 다시 보내는 경로 추가. "처리 중" 선영속화 제거·후순위화. 호출 직전 재조회 제거. 조회·변경 공유 클라이언트에 변경 호출까지 적용되는 재시도 추가
- high: 작업 ID 저장을 후속 조회 뒤로 옮김(조회 실패 시 ID 유실). 결과 불명을 실패(종료)로 확정해 조회 없이 끝냄(실제 처리된 건을 실패로 기록 → 수동 재처리 중복 위험). 레이트 리밋 거절 재시도를 근거 없이 도입
- medium: 새 변경 호출부가 상태 조건부 전이 외 추가 확인이 없음(기존 경로와 동등 수준이면 info)
- low: 결과 분류 로그에 작업 ID·오류 코드 누락(OPS로 `also_affects`)

**피크 트래픽 관점**: 피크에는 429·5xx·지연이 늘어 결과 불명 건이 평시보다 훨씬 많아진다. "처리 중에 멈춘 건이 많다"는 압박으로 일괄 재전송 스크립트·재시도 설정이 들어오기 쉽다. 이 기준은 그런 PR을 항상 critical로 막는다.

**근거**: RFC 9110 9.2.2(멱등 메서드와 자동 재시도), Kleppmann *Designing Data-Intensive Applications* 8장·11장, Nygard *Release It!*(Integration Points), Transactional Outbox 패턴, CWE-754

## REL-02 외부 호출 실패 분류·타임아웃·재시도

- **적용**: 서버
- **왜 중요한가**: 타임아웃이 없으면 외부 지연 시 요청 스레드가 무기한 묶이고 결과 불명 건이 쌓인다. 실패를 잘못 분류하면 안전하게 재시도할 수 있는 건(인증 토큰 발급 실패, 조회 실패)이 "처리 중"에 갇히고, 위험한 건(변경 호출 결과 불명)이 실패로 확정되기도 한다.
- **판정 질문**
  - 새로 만들거나 바꾼 외부 호출 클라이언트(토큰·API·작업 조회·웹훅)에 연결·응답 타임아웃이 설정되는가?
  - 재시도·백오프가 **조회·멱등 호출에만** 적용되고 상한(횟수·총 시간)과 지터가 있는가? 429에서 `Retry-After`나 API가 알려주는 잔여 한도·회복 속도를 존중하는가?
  - 실패를 "보내지 않았음(안전)"과 "보냈는지 모름(불확실)"으로 구분하는가?

**체크포인트**
- HTTP 클라이언트 라이브러리는 기본값이 타임아웃 없음인 경우가 많다. 기본 생성자·기본 빌더로 만든 새 클라이언트는 위반으로 본다. 타임아웃이 설정·주입 팩토리에서 오는지 확인한다.
- 타임아웃 값은 레포 프로파일 `parameters`에 있으면 그것을 쓴다. 없으면 가정을 시나리오에 적고 confidence를 likely 이하로. 응답 타임아웃이 변경 호출의 정상 응답 시간보다 짧으면 결과 불명이 늘어난다. 값의 용량 영향은 PERF.
- 실패 분류 기대값:

  | 상황 | 기대 분류 |
  |---|---|
  | 호출 전 설정·검증 실패 | 실패(미전송) |
  | 4xx(429 제외) | 실패(요청 자체 거절) |
  | 429 / 5xx / 타임아웃 / 연결 끊김 | 불확실 |
  | 200이지만 본문에 최상위 오류 | 불확실(한도 거절 코드만 별도 검토, REL-01) |
  | 응답·작업 ID 누락 | 불확실 |
  | 요청 전송 전 단계(토큰 발급 등)의 예외 | 미전송으로 분리 가능 |

- 미전송 분리: 요청을 만들기 전에 나는 예외만 "미전송"으로 분리하면 `fixed`다. 전송 후 예외까지 같은 분기에 넣으면 REL-01 critical.
- 조회 실패를 삼켜 "없음"으로 바꾸면 404 오응답과 상태 방치가 생긴다.
- 서킷 브레이커가 열렸을 때 변경 호출을 "보류"로 두는 것은 안전하다(보내지 않았음). 열림을 불확실로 기록하면 불필요한 복구 대상이 생긴다 → low.
- 인증 실패(401) 시 토큰 무효화·재발급 1회는 안전한 재시도다(실행 전 거절로 본다 — 추정).
- 인스턴스 메모리 캐시 토큰은 인스턴스마다 발급된다. 발급 한도가 있는 외부 시스템이면 확인한다.
- 외부 API 버전 고정: 지원 기간이 끝난 버전이 조용히 다른 버전으로 대체되는 정책이 있으면, 만료 일정과 필드 변경을 확인했는지 본다(필드 계약은 REL-06).

**심각도 앵커**
- critical: (변경 호출 재시도는 REL-01에 올린다)
- high: 새 외부 호출 클라이언트에 타임아웃 없음. 기존 타임아웃 제거. 무한·무상한 재시도(조회라도). 불확실 실패를 "미전송"으로 오분류해 안전 재시도 경로로 보냄(실제로 보낸 변경 호출이면 REL-01로 올라감)
- medium: 재시도에 백오프·지터 없음, 429에서 `Retry-After`·잔여 한도 무시. 조회 실패를 삼켜 "없음"으로 바꿈
- low: 서킷 열림을 불확실로 기록, 실패 코드 문자열이 기존 관례와 다름

**피크 트래픽 관점**: 피크에는 같은 외부 API 한도 버킷을 조회와 변경 호출이 함께 쓴다. 백오프 없는 조회 재시도는 버킷을 더 빨리 비워 변경 호출까지 거절되게 만든다. 타임아웃이 없으면 외부 지연이 요청 스레드를 묶어 API 전체가 멈춘다(용량 판단은 PERF, 타임아웃 존재 여부는 REL).

**근거**: RFC 9110(10.2.3 `Retry-After`), RFC 6585(429), Google *Site Reliability Engineering* 22장(Addressing Cascading Failures), Nygard *Release It!*(Timeouts, Circuit Breaker), CWE-400, CWE-703

## REL-03 멱등성

- **적용**: 서버
- **왜 중요한가**: 사용자가 버튼을 연타하거나 클라이언트가 재시도하면 같은 대상에 요청이 여러 번 온다. 중복 방지가 애플리케이션 조회에만 있으면 동시 요청 두 건이 모두 실행까지 간다. 반대로 키 범위가 너무 넓으면 실패한 대상을 영원히 다시 처리할 수 없다.
- **판정 질문**
  - 중복 방지가 DB 유니크 제약으로 최종 보장되는가? 이 제약을 바꾸거나(복합 키, 조건부 유니크) 지우는가?
  - 유니크 위반이 오류가 아니라 "기존 요청 반환"으로 처리되는가? 변경 가능한 엔터티의 버전 컬럼(낙관적 락)이 유지되는가?
  - 재요청 허용 범위를 바꾸는 변경(실패·거절 건 재요청, 입력 변경)이 기존 건의 작업 ID·결과 불명 상태를 고려하는가?

**체크포인트**
- "조회 → 없으면 저장"만으로는 동시 요청을 막지 못한다. 유니크 위반을 잡아 기존 건을 재조회·반환하는 흐름이 유지되는지 본다. 예외 변환 계층을 바꿔도 이 동작이 남아야 한다.
- 키 범위 변경:
  - 새 행을 허용하려고 유니크 키를 (대상 ID, 시도 번호) 등으로 바꾸면 동시 재요청 두 건이 각자 행을 만든다. "활성 요청은 대상당 1건" 보장(활성 상태 컬럼 + 유니크, 또는 비관적 잠금)이 함께 와야 한다.
  - 기존 실패 행을 재개하는 것은 실패 원인이 "미전송"일 때만 안전하다. 원인(오류 코드)을 저장하지 않는 스키마에서는 원인 저장이 먼저 와야 한다.
- 버전 컬럼 제거, 원시 타입·래퍼 타입 변경 시 동작 변화를 확인한다.
- 동시 요청의 두 번째 응답이 중간 상태를 돌려줄 수 있다. 응답 규약이 정해지기 전에는 info.
- 멱등성 키 헤더를 도입하면 키 저장·만료·요청 본문 비교가 있는지 본다. 키가 대상 ID 유니크 제약을 대체하면 안 된다(제약은 유지).

**심각도 앵커**
- critical: 대상 ID 유니크 제약 제거·완화로 같은 대상에 활성 요청 2건이 생기고 둘 다 실행 경로에 진입 가능. 결과 불명·작업 ID 있는 기존 건을 재요청으로 재실행
- high: 유니크 위반을 500·오류로 바꿈. 버전 컬럼 제거. 실패 건 재개 조건에 원인 구분 없음(미전송 vs 불확실)
- medium: 재요청 시 입력을 덮어써 감사 정보 유실, 멱등성 키를 받기만 하고 저장하지 않음
- low: 동시 요청 응답 상태 불일치를 문서화하지 않음

**피크 트래픽 관점**: 응답 지연이 길어지면 클라이언트·사용자 재시도가 늘어 같은 대상의 동시 요청이 평시보다 잦다. 유니크 제약 + 재조회 반환이 이를 흡수한다. 이 경로를 "조회 후 없으면 저장"만으로 바꾸는 PR은 평시 테스트를 통과해도 피크에서 중복 실행을 만든다.

**근거**: RFC 9110 9.2.2, IETF draft *The Idempotency-Key HTTP Header Field*, Kleppmann *DDIA* 7장(Preventing Lost Updates, Write Skew), CWE-362

## REL-04 트랜잭션 경계·동시성 제어

- **적용**: 서버
- **왜 중요한가**: 외부 호출을 DB 트랜잭션 안에 넣으면, 호출 후 롤백 시 DB는 이전 상태인데 외부는 이미 바뀐 상태가 된다. 다중 인스턴스에서 스케줄러·요청 스레드가 같은 건을 집으면 외부 변경이 중복된다. 단계별 커밋이 의도된 설계라면 그것을 하나로 묶는 변경이 선영속화(REL-01)를 깨뜨린다.
- **판정 질문**
  - 새 트랜잭션 경계가 외부 호출(변경·조회·토큰)을 감싸는가? 특히 "처리 중" 저장과 변경 호출이 한 트랜잭션에 들어가는가?
  - 같은 건을 동시에 두 처리기(요청 스레드·스케줄러·다른 인스턴스)가 집을 수 있는가? 잠금(분산 잠금, `SELECT … FOR UPDATE SKIP LOCKED`, 상태 조건부 UPDATE + 영향 행 수 확인, 낙관적 락)이 **변경 호출 전에** 단일 처리기를 보장하는가?
  - 낙관적 락 충돌이 어디서 나고 어떻게 처리되는가?

**체크포인트**
- 외부 호출을 트랜잭션 밖에 두는 표준 형태: (1) 짧은 트랜잭션으로 상태 전이·커밋 → (2) 트랜잭션 밖 외부 호출 → (3) 짧은 트랜잭션으로 결과 반영. 트랜잭션 전파 설정을 바꾸면 단계별 커밋 의미가 바뀐다.
- 요청 단위 영속성 컨텍스트가 열려 있는지에 따라 커밋 시점이 달라진다. 설정을 확인한다.
- 단일 처리기 보장:
  - 스케줄러 메서드 단위 분산 잠금은 "동시에 한 인스턴스"만 보장한다. 사용자 요청 경로와의 경합은 따로 막아야 한다.
  - 행 단위 선점은 상태 전이 저장이 버전 충돌을 감지한다. 충돌한 쪽이 **변경 호출 전에** 중단되는지 본다. 충돌을 catch해 계속 진행하게 바꾸면 위반이다.
  - `SKIP LOCKED` 조회는 트랜잭션이 커밋되면 잠금이 풀린다. 조회 트랜잭션과 "처리 중" 전이가 같은 커밋인지 본다.
  - 프로세스 로컬 잠금(뮤텍스·동기화 블록)은 다중 인스턴스에서 아무것도 보장하지 않는다.
- 재요청이 처리를 재개하도록 바뀌면(REL-03) 요청 경로와 스케줄러가 경합하기 시작한다.
- 낙관적 락 충돌 처리: "충돌 = 다른 처리기가 진행 중 → 현재 상태 반환"이면 정상. "충돌 → 재시도 → 변경 호출 재전송"이면 REL-01 critical.

**심각도 앵커**
- critical: "처리 중" 저장과 변경 호출을 한 트랜잭션에 넣어, 호출 후 예외·롤백 시 DB가 이전 상태로 돌아감(재실행 가능). 다중 인스턴스·스케줄러가 같은 건을 잠금 없이 집어 변경 호출이 두 번 나갈 수 있음
- high: 외부 호출을 긴 트랜잭션·행 잠금 안에서 수행(잠금 보유 중 외부 지연). 낙관적 락 충돌을 삼키고 진행. 스케줄러 잠금이 프로세스 로컬뿐
- medium: 부분 반영 가능성(관련 필드를 별도 커밋으로 나눠 중간 실패 시 불일치)이 문서화·복구 경로 없이 생김. 충돌 시 500 그대로
- low: 트랜잭션 경계 의도(단계별 커밋 등)를 주석·설계 문서에 적지 않음

**피크 트래픽 관점**: 피크 대비로 인스턴스를 늘리면 평시 단일 인스턴스에서 드러나지 않던 스케줄러 중복 실행이 처음 드러난다. 다중 인스턴스 배포 여부가 불확실하면, 스케줄러를 추가하는 PR은 단일 인스턴스를 가정하더라도 분산 잠금이 있어야 한다(없으면 high, 실제 변경 호출 재실행 경로면 critical).

**근거**: Kleppmann *DDIA* 7장·8장(Fencing tokens), Garcia-Molina & Salem *Sagas*(1987), Transactional Outbox 패턴, CWE-362, CWE-667

## REL-05 미종료 상태 복구·재처리 경로

- **적용**: 서버
- **왜 중요한가**: 중간 상태(접수·대기·처리 중)에 멈춘 건은 사용자에게 "처리 중"으로 남고 아무도 확정하지 않는다. 복구 로직은 결과 불명 건을 다루므로 잘못 만들면 이중 실행 경로가 된다(REL-01). 너무 공격적으로 돌면 외부 API 한도를 소진한다(PERF).
- **판정 질문**
  - 새 복구·폴링 로직이 "처리 중"은 조회만으로 확정하고, 외부에서 완료가 확인될 때만 완료로 전이하며, 일시 오류는 상태를 유지하고 다음 확인으로 넘기는가?
  - 확인 주기·최대 횟수·만료 정책이 있고, 최대 횟수를 넘긴 건이 종료되거나 수동 처리 대상으로 표시되는가?
  - 대상 선정이 "상태 + 다음 확인 시각" 기준으로 제한되고, 한 번에 집는 건수에 상한이 있는가?

**체크포인트**
- 대상 선정 쿼리: 미종료 상태 AND 다음 확인 시각 ≤ 현재, 건수 상한. 맞는 인덱스가 있는지 본다(쿼리 비용은 PERF).
- 상태별 처리:
  - 외부 전제 조건 대기 → 외부 재조회 → 조건 충족이면 정상 실행 규칙(직전 재조회 포함)으로. 상태 조건부 전이에 성공한 처리기만 변경 호출.
  - 처리 중 + 작업 ID → 작업 조회 → 완료면 외부 대상 상태로 최종 확인. 작업은 완료인데 대상이 바뀌지 않았으면 근거 없이 실패로 확정하지 않는다(수동 처리 대상).
  - 처리 중 + 작업 ID 없음 → 대상 상태 조회만. 재전송은 REL-01 규칙을 따른다.
  - 접수 후 방치 → 재판정.
- 시각·횟수 기록은 도메인 메서드로(ARCH-02), 시계는 주입(ARCH-01).
- 수동 처리 경로(운영자 재처리 API·스크립트)가 REL-01·REL-03 규칙을 같은 유스케이스로 거치는지. 알림·대시보드는 OPS.
- 웹훅을 보조로 쓰면 중복·순서 역전 전달에 멱등한지(같은 상태 재적용이 무해한지).

**심각도 앵커**
- critical: 복구 로직이 "처리 중" 건에 변경 호출 재전송(REL-01에도 별도 finding) 또는 외부 확인 없이 완료로 확정(실제로는 처리 안 됐는데 완료 표시)
- high: 일시 오류(5xx/429/타임아웃)에서 상태를 종료로 바꿈. 최대 횟수·만료 없이 무한 재확인. 작업 완료 + 대상 미변경을 근거 없이 실패 확정
- medium: 한 번에 집는 건수 상한 없음, 다음 확인 시각 갱신 누락(같은 건 매 주기 재조회), 웹훅 재전달에 비멱등
- low: 재확인 전이 기록에 이전/새 상태·횟수 누락(OPS로 `also_affects`)

**피크 트래픽 관점**: 피크 중 결과 불명·대기 건이 급증하면 복구 스케줄러가 매 주기 많은 건을 조회해 같은 한도 버킷을 쓰는 신규 요청까지 거절되게 만든다. 배치 상한·백오프·다음 확인 시각 분산이 있는지 본다(부하 수치는 PERF, 존재 여부는 REL).

**근거**: Google *Site Reliability Engineering* 22장, Kleppmann *DDIA* 11장, Hohpe & Woolf *Enterprise Integration Patterns*(Idempotent Receiver, Guaranteed Delivery)

## REL-06 외부 상태 변경 계약과 돈·재고 정확성

- **적용**: 서버
- **왜 중요한가**: 외부 변경 호출의 인자 하나(환불 여부·환불 수단, 재고 복원, 고객 알림, 사유 코드, 메모)가 모든 처리 건의 돈·재고·고객 커뮤니케이션을 결정한다. 잘못 바꾸면 환불 없는 취소나 재고 이중 복원이 전 건에 적용된다. 외부 API 버전을 올려 필드 의미·필수 여부가 바뀌면 조용히 다르게 동작한다.
- **판정 질문**
  - 변경 호출의 인자 값, 정책 설정 값, 요청 문서(쿼리·스키마)의 필드가 바뀌는가? 바뀐 값이 스펙·운영 결정과 일치하는가?
  - 완료 판정이 "외부에 실제로 반영됨"을 근거로 하는가(최종 상태 확인 유지)?
  - API 버전·필드 변경 시 폐기·제거 필드, 필수 인자 변경을 공식 변경 내역으로 확인했는가?

**체크포인트**
- 현재 코드의 요청 형식을 외부 API의 공식 계약(필수 인자, 반환 필드, 오류 필드)과 대조한다. 코드가 문서보다 엄격한 것은 문제가 아니다.
- 인자 값 변경 영향:

  | 인자 종류 | 영향 | 변경 시 확인 |
  |---|---|---|
  | 환불 여부·환불 수단 | 끄면 처리만 되고 환불 안 됨 | 운영 결정 근거, 다른 환불 경로 |
  | 재고 복원 | 미복원·이중 복원 | 묶음 상품 구성품 재고, 재고 연동 시스템 |
  | 고객 알림 | 재전송·복구 시 중복 알림, 끄면 고객이 처리 사실을 모름 | 복구 경로에서도 같은 값 |
  | 사유 코드(enum) | 외부 리포트·사기 분석 | 매핑 표, 원문 문자열 직접 전달 금지 |
  | 자유 메모 | 사용자 입력 전달 | 길이·개인정보(SEC로 `also_affects`) |

- 정책 값 미설정 가드(미설정이면 호출하지 않음)를 제거하고 코드 기본값을 넣으면 운영 결정을 코드가 대신한다(ARCH-04 + 여기서 돈 영향).
- 완료 조건을 느슨하게(비동기 작업 완료만으로) 바꾸면 위반이다. 대상 상태로 최종 확인해야 한다. 환불 거래 상태까지 확인하지 않는 한계가 있으면 문서화돼 있는지 본다.
- 결과 선택 필드에서 사용자 오류 목록을 빼면 거절 원인을 잃는다.
- 외부 enum 값 추가는 보수적 매핑(ARCH-03)으로 흡수돼야 한다.

**심각도 앵커**
- critical: 환불을 근거 없이 끄거나 환불 인자를 빼서 환불 없는 처리가 전 건에 적용. 외부 최종 상태 확인 없이 완료 확정. 정책 미설정 가드 제거 + 코드 기본값으로 운영 결정 없이 실제 변경이 나감
- high: 재고 복원·고객 알림 값 변경이 운영 결정·PR 근거 없이 들어옴. API 버전을 올리면서 제거·변경된 필드를 그대로 사용(조용한 null → 불확실 증가 또는 잘못된 판정). 사유 코드에 원문 문자열을 넘겨 enum 오류(→ 4xx 실패 대량)
- medium: 메모 형식 변경(운영자가 검색하던 정보 유실), 결과 선택 필드에서 사용자 오류 목록 제거
- low: 정책 값 변경을 운영 로그·PR 본문에 남기지 않음(OPS로 `also_affects`)

**피크 트래픽 관점**: 피크 직후 처리가 몰리면 정책 값 하나의 실수가 대량의 돈·재고 오류로 번진다. 피크 중 "알림이 너무 많다"는 이유로 알림을 끄는 핫픽스가 들어오기 쉽고, 이는 고객이 환불 사실을 모르게 만든다. 값 변경은 항상 high 이상으로 보고 운영 결정 근거를 요구한다.

**근거**: Fowler *Tolerant Reader*, Kleppmann *DDIA* 4장(Encoding and Evolution), Semantic Versioning 2.0.0, CWE-20

## REL-07 스키마 마이그레이션 안전성

- **적용**: 서버
- **왜 중요한가**: 마이그레이션 도구는 적용된 파일의 체크섬을 검증한다. 적용된 파일을 고치면 그 버전이 적용된 환경에서 기동이 실패하거나 스키마가 환경마다 갈라진다. 무중단 배포 중에는 구버전·신버전 애플리케이션이 같은 스키마를 함께 쓰므로 파괴적 변경이 장애가 된다.
- **판정 질문**
  - 이미 적용됐을 수 있는 마이그레이션 파일을 수정·삭제·이름 변경하는가?
  - 새 마이그레이션이 구버전 애플리케이션과 호환되는가(컬럼 삭제·이름 변경·타입 축소·기본값 없는 NOT NULL 추가 금지, 확장 → 이행 → 축소 순서)?
  - 유니크 제약·버전 컬럼처럼 정합성을 보장하는 제약을 바꾸는가? 버전 번호가 다른 환경의 이력과 충돌하지 않는가?

**체크포인트**
- 환경별 이력이 다를 수 있다(같은 버전 번호에 다른 내용). 각 환경에 실제로 무엇이 적용됐는지는 저장소만으로 확인할 수 없다. 이력 정리 PR은 baseline·새 버전 이행·repair 방법을 PR 본문에 적었는지 본다.
- 자릿수가 다른 버전 명명(`1`과 `0001`)이 같은 버전으로 해석될 수 있다. 새 파일 명명은 기존 관례를 따른다(어기면 low).
- ORM 스키마 검증 모드: 엔터티 매핑을 바꾸면서 마이그레이션이 없으면 기동 실패. 반대로 마이그레이션만 있고 엔터티 미반영이면(새 nullable 컬럼) 검증이 잡지 못하기도 한다.
- 컬럼 추가는 nullable 또는 기본값을 두고 추가 → 애플리케이션 배포 → 필요하면 NOT NULL 전환을 별도 버전으로.
- 되돌리기 기능이 없는 도구가 많다. 보상 마이그레이션 계획을 PR 본문에 적었는지 본다(OPS로 `also_affects`).
- 운영 데이터 변경(`DELETE`·`TRUNCATE`·대량 `UPDATE`)이 스키마 마이그레이션에 섞이면 따로 본다.
- 대용량 테이블의 온라인 DDL 잠금 시간은 PERF.
- 기존 결함을 고치려고 적용된 파일을 다시 수정하는 PR은, 어떤 환경에도 아직 적용되지 않았다는 근거가 확인되면 downgraded(info)다.

**심각도 앵커**
- critical: 대상 ID 유니크 제약 삭제·완화(REL-03 critical과 같은 문제면 REL-03에 올리고 여기에는 `also_affects`). 운영 데이터 삭제가 들어간 마이그레이션
- high: 적용된 마이그레이션 파일 수정·삭제. 구버전과 비호환인 컬럼 삭제·이름 변경·타입 변경. 기본값 없는 NOT NULL 컬럼 추가
- medium: 다른 환경 이력과 충돌하는 버전 번호, 버전 컬럼 정의 변경, 엔터티·마이그레이션 불일치
- low: 파일 명명 관례 위반, 되돌리기 계획 없음

**피크 트래픽 관점**: 시즌 중 배포는 롤링·무중단이 전제다. 비호환 DDL은 배포 중 구 인스턴스의 처리를 실패시킨다. "처리 중" 저장 직후 실패가 나면 결과 불명 건이 생긴다(REL-01·REL-05 부담 증가).

**근거**: Ambler & Sadalage *Refactoring Databases*, Fowler *Parallel Change*(expand/contract), Kleppmann *DDIA* 4장, 12-factor XII(Admin processes)

## REL-08 구매·제출 흐름 무결성과 우아한 저하

- **적용**: 클라이언트
- **왜 중요한가**: 장바구니 담기·수량 변경·결제 진입 같은 핵심 흐름이 깨지면 매출이 바로 멈춘다. 같은 페이지·같은 장바구니를 여러 서드파티 스크립트가 다루므로 하나의 장애·지연이 흐름 전체를 막지 않아야 한다.
- **판정 질문**
  - 장바구니·주문 변경 API 호출이 오류 응답(422 재고 부족·품절, 4xx/5xx, 네트워크 오류)을 처리하고, 실패 시 버튼·UI를 원상 복구하며 사용자에게 알리는가?
  - 빠른 연속 조작(수량 연타, 담기 연타, 다른 탭에서 변경)에서 요청 순서 역전·중복 담기가 생기지 않는가?
  - 서드파티 스크립트가 로드 실패·지연·예외일 때도 담기와 결제 진입이 동작하는가?

**체크포인트**
- 오류 계약: 재고 초과 시 가능한 수량만 담고 오류를 돌려주는 API가 있다. 성공(`ok`)만 가정하고 바로 결제로 가면 일부만 담긴 상태로 결제에 진입한다. 응답 본문의 오류 필드를 확인하는지 본다.
- 기존 처리 패턴 재사용: 레포에 요청 직렬화(요청 중 버튼 비활성), 오류 표시, 실패 이벤트 발행을 하는 공용 컴포넌트가 있으면 새 코드는 그것을 쓴다. 독자 요청 코드는 ARCH와 함께 여기서 오류 처리·이벤트 발행을 확인한다.
- 오류 처리 코드(`ok` 검사, 422 분기, `catch`, 버튼 비활성)를 지우는 diff는 같은 PR에서 동등한 처리로 옮겼는지 확인한다.
- 새 담기 경로가 추가되는지 기존 경로를 전수로 비교한다. 같은 기능의 변형(카드·퀵애드·모달)이 담는 방식이 다르면 필수 옵션 누락 담기가 생긴다.
- 컬렉션 항목 식별자는 항목마다 유일해야 한다. 상품·variant ID처럼 유일하지 않은 키로 바꾸면, 같은 상품이 속성만 다른 두 줄(증정·묶음·옵션)로 있을 때 다른 줄이 수정·삭제된다 → high.
- 기본 선택 항목: "선택 가능한 첫 항목"을 "첫 항목"으로 바꾸면 품절 항목이 기본값이 될 수 있다. 실제 담기 ID가 바뀌면 medium, 표시 가격·이미지만 바뀌면 low. 다른 화면이 담을 때 상품을 다시 불러오면 표시만 바뀌는 경우도 있다.
- 같은 장바구니를 바꾸는 서드파티(증정·묶음 등)와 갱신 이벤트로 결합돼 있으면, 이벤트 이름·리스너를 바꾸는 PR은 연결이 유지되는지 본다. 서드파티가 관리하는 줄을 테마·앱 코드가 직접 바꾸면 재추가 루프나 금액 오류가 생길 수 있다(추정).
- 우아한 저하:
  - 서드파티에 의존하는 버튼은 서드파티가 없을 때 기본 담기 폼이 남는지 본다.
  - 전역 객체 메서드 호출에 존재 확인(타입 검사·옵셔널 체이닝)이 있는지 본다.
  - 외부 모듈 스크립트 로드 실패가 인라인 스크립트 예외로 번지지 않는지 본다.
- 결제 진입: 결제 URL 직접 이동이 폼 제출 검증(장바구니 속성·메모·약관 동의)을 우회하는지 본다. 약관 동의 체크를 끄는 변경은 결제 차단 해제다(법무 영향은 A11Y/SEC로 `also_affects`).
- 부분 렌더링 갱신: 서버가 돌려주는 조각 HTML을 파싱하는 셀렉터가 바뀐 마크업과 맞는지 본다.

**심각도 앵커**
- critical: 담기·수량 변경·결제 진입이 특정 조건(서드파티 실패, 특정 지역·마켓, 특정 줄 존재)에서 전면 불가. 오류 응답을 성공으로 간주해 담기 실패 상태로 결제 진입이 기본 동작이 됨. 서드파티 전역 객체 부재 시 예외로 장바구니 컴포넌트 초기화 중단
- high: 오류 처리 누락으로 UI가 로딩 상태에 멈추거나(버튼 비활성 고정) 화면 수량과 실제가 다름. 연타 시 중복 담기(직렬화·버튼 비활성 없음). 약관 동의·장바구니 검증 우회. 서드파티와의 장바구니 이벤트 연결 끊김. 항목 식별자가 유일하지 않아 다른 줄이 수정·삭제됨
- medium: 오류를 `alert`·콘솔에만 남김, 네트워크 실패 시 재시도 안내 없음, 독자 요청 경로가 공용 갱신 이벤트를 발행하지 않아 다른 컴포넌트가 갱신 안 됨. 기본 선택이 품절 항목으로 바뀌어 담기 ID가 바뀜
- low: 실패 시 포커스·라이브 영역 미처리(A11Y로 `also_affects`), 사용하지 않는 담기 경로 잔존, 기본 선택 변경으로 표시만 바뀜

**피크 트래픽 관점**: 피크에는 품절·재고 부족 오류가 평시보다 훨씬 많고 서드파티 서버가 느려지거나 실패한다. 평시 테스트에서 성공 경로만 확인한 담기 코드는 피크에 "버튼이 안 눌림"으로 나타난다.

**근거**: Progressive Enhancement 원칙, WCAG 2.2 SC 3.3.1(Error Identification)·4.1.3(Status Messages), Nygard *Release It!*(Integration Points, Fail Fast), CWE-703, CWE-362

## REL-09 저장된 설정 스키마 호환성과 렌더 안전성

- **적용**: 클라이언트
- **왜 중요한가**: 템플릿·페이지 구성 파일은 컴포넌트의 설정 키와 블록 타입을 키로 값을 저장한다. 스키마에서 키를 지우거나 이름을 바꾸면 그 컴포넌트를 쓰는 모든 템플릿에서 값이 더는 쓰이지 않는다. 사실상 콘텐츠가 유실되고 에디터에서 다시 입력해야 한다. 템플릿 렌더 오류(없는 부분 템플릿, null 접근)는 페이지 일부를 깨뜨린다.
- **판정 질문**
  - 컴포넌트 스키마에서 설정 키·블록 타입을 삭제·이름 변경하거나, 설정 값의 타입을 바꾸거나, 블록 수 상한을 줄이거나, 기본 프리셋을 바꾸는가? 그 컴포넌트를 참조하는 템플릿 수와 해당 키를 실제로 쓰는 템플릿 수는?
  - 컴포넌트·부분 템플릿 파일을 삭제·이름 변경할 때 참조(구성 파일의 타입, include 문, 레이아웃 그룹, 부분 렌더링 요청 ID, 동적 include 대상)가 남지 않는가?
  - 새 템플릿 코드가 비어 있는 메타데이터·빈 리스트에 안전한가? 동적 include 대상이 모두 존재하는가? 상속·오버라이드 구성 파일의 부모가 존재하는가?

**체크포인트**
- 참조 수는 구성 파일을 실제로 파싱해 센다(주석 헤더가 있으면 벗기고 파싱). grep 결과는 근사치로만 쓴다.
- 영향 범위 기준: "다수 템플릿" 문턱값은 레포 프로파일 `parameters`에 있으면 그것을, 없으면 10개 파일을 가정하고 시나리오에 적는다.
- 안전한 변경: 설정 추가(기본값 포함), 라벨·설명 변경, 새 블록 타입 추가. 이름 변경이 필요하면 새 키 추가 + 코드에서 구 키 폴백 + 템플릿 일괄 이관을 같은 PR에서 처리한다.
- 숨은 위험:
  - 설정 값 타입 변경(텍스트 → 서식 텍스트, 이미지 → URL 등)은 저장된 값 형식이 달라 렌더가 깨진다(추정).
  - 블록 수 상한 축소는 기존 템플릿이 상한을 넘으면 에디터 저장 오류가 난다(추정).
  - 설정 키는 컴포넌트 안에서 유일해야 한다.
  - 플랫폼의 템플릿당 컴포넌트 수·블록 수 상한에 근접한 템플릿에 추가하면 저장이 거부될 수 있다.
- 삭제 안전성: 정적 참조가 없어도 사용 중일 수 있는 것(부분 렌더링 API로 이름을 불러 쓰는 컴포넌트, 메타데이터·설정값 기반 동적 include 대상, 외부 앱이 관리하는 파일)을 확인한다. 주석 안의 사용 예시는 참조가 아니다. 동적 대상 값이 저장소 밖에 있으면 `possible`로 적고 확인 질문으로 남긴다.
- 변수로 대상을 정하는 동적 include를 새로 추가하면, 대상 목록과 존재 여부를 확인한다(누락 시 렌더 오류).
- null 안전성: 깊은 속성 체인은 값이 없으면 빈 출력인 템플릿 언어가 많지만, `first`·인덱스 접근·분할 후 반복·포함 검사는 빈 값 처리를 확인한다.
- 지역·마켓별 오버라이드 구성 파일의 부모 템플릿을 삭제·이름 변경하면 오버라이드가 고아가 된다.
- 전역 설정 스키마의 키 변경은 저장된 전역 설정 값(오버라이드 포함)을 끊는다. 위와 같은 기준을 적용한다.

**심각도 앵커**
- critical: 장바구니·구매 폼을 렌더하는 컴포넌트의 스키마·파일 변경으로 장바구니·구매 버튼이 렌더되지 않음(REL-08 critical과 같은 문제면 REL-08에 올리고 `also_affects`). 모든 페이지의 레이아웃 그룹이 렌더 오류
- high: 다수 템플릿이 쓰는 설정 키·블록 타입 삭제·이름 변경·타입 변경(이관 없음). 참조가 남은 컴포넌트·부분 템플릿 삭제. 부모 템플릿 삭제로 오버라이드 파일 고아화
- medium: 소수 템플릿의 키 삭제·변경, 블록 수 상한 축소, 동적 include 대상 삭제·이름 변경(대상 값 미확인), null 가능 체인에 `first`·인덱스 접근 추가, 템플릿이 플랫폼 상한에 근접
- low: 프리셋 변경(신규 추가 시 기본값만 영향), 참조 0인 키 정리, 라벨 없는 설정

**피크 트래픽 관점**: 피크 직전에는 캠페인 컴포넌트 스키마를 고치고 템플릿 수십 개를 동시에 교체한다. 피크 중 에디터에서 콘텐츠가 사라진 걸 발견하면 복구 수단은 구성 파일 재입력뿐이다. 시즌에는 "다수 템플릿" 문턱값을 낮추는 것을 권장한다(레포 프로파일 `parameters`).

**근거**: Kleppmann *DDIA* 4장(schema evolution, forward/backward compatibility), Fowler *Parallel Change*, Fowler *Tolerant Reader*, CWE-476
