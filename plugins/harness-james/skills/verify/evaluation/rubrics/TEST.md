# TEST — 테스트 적정성

- 버전: 2.0.0 (2026-10-13)
- 적용: 모든 레포 (차원·기준 적용은 레포 프로파일의 traits(server·client)와 dimensions가 정한다)
- 보는 것: 이 PR이 바꾼 로직에 맞는 검증이 함께 왔는지 본다. 범위는 분기·실패 경로·경계값, 테스트 계층 선택, 실제 외부 호출 격리, 시간 제어와 결정성, 동시성·멱등성, 기존 테스트 약화, 정적 검증 도구의 신규 오류, 사람이 하는 QA의 기록이다.
- 보지 않는 것:
  - 테스트 대상 코드 자체의 결함. 예: 결과 불명 상태에서 외부 변경 호출을 다시 보내는 버그는 REL, 인증 누락은 SEC. 여기서는 "그 분기를 검증하는 테스트가 있는가"만 본다.
  - 테스트 코드의 토큰·시크릿 출력 → SEC
  - CI·배포 파이프라인 유무, 미리보기·스테이징 운영 절차 → OPS. 여기서는 PR에 QA 시나리오가 **적혀 있는지**만 본다.
  - 정적 검증 도구 오프펜스 중 성능 계열(렌더 차단 스크립트, 자산 크기, 이미지 크기 미지정) → PERF, 누락 참조 → REL, 번역 키 누락·불일치 → A11Y-08, 위생(사용하지 않는 파일, 폐기 예정 문법) → ARCH. TEST-07은 문법·스키마 유효성 계열만 본다.
  - 테스트 실행 결과. 파이프라인은 테스트를 실행하지 않는다(framework.md 8장). 모든 판정은 diff와 레포의 정적 맥락으로만 한다.

## TEST-01 바뀐 분기·실패 경로·경계값 테스트

- **적용**: 공통
- **왜 중요한가**: 돈 경로의 분기는 각각 다른 결과로 이어진다. 실행, 보류, 거절, 영구 실패가 갈린다. 테스트 없이 바뀐 분기는 운영에서 처음 실행된다. 피크 때만 나는 스로틀·5xx 분기는 특히 그렇다.
- **판정 질문**:
  - 이 PR이 추가·변경한 프로덕션 코드의 각 분기(조건문·switch case·예외 경로)에 그 분기를 직접 통과하는 테스트가 있는가? 이번 PR에서 추가된 것이든 기존 것이든 된다.
  - 실패 경로(외부 오류·타임아웃·잘못된 응답·설정 누락)와 경계값(새 enum 값, 매핑의 default)이 정상 경로와 함께 검증되는가?
  - 테스트가 결과 상태뿐 아니라 **부작용**(외부 호출 횟수, 저장 순서, 호출하지 않아야 할 의존성에 대한 "호출 안 됨" 단언)도 확인하는가?

**체크포인트**
- 외부 시스템의 결과를 내부 상태로 바꾸는 매핑(성공·진행 중·거절·실패·결과 불명)을 바꾸면, 바뀐 결과 종류마다 상태 전이 테스트가 있어야 한다.
- 결과 불명(타임아웃·5xx·스로틀·응답 누락) 분기는 **외부 변경 호출이 다시 나가지 않음**(호출 횟수 정확히 1회)과 보류 상태 유지를 함께 검증해야 한다.
- HTTP 실패 매핑은 4xx(거절·영구 실패), 스로틀(429), 5xx·전송 예외·응답 본문 오류(결과 불명)를 구분해 각각 테스트한다.
- 외부 상태값을 내부 enum으로 바꾸는 매핑에서 **현재 default로 떨어지는 값**이 경계값이다. 값을 추가하거나 매핑을 바꾸면 바뀐 값과 default 경로 둘 다 테스트한다.
- 판정 규칙의 평가 순서를 바꾸면 순서에 따라 결과가 달라지는 조합(예: 이미 취소됨 + 이미 출고됨)을 검증한다.
- 토큰·자격증명 경로: 발급 실패, 만료값 누락·0, 동시 갱신.
- 웹 계층: 새 응답 코드·검증 규칙은 각 오류 코드(400/401/403/404/409/500) 케이스를 둔다. 특정 입력이 500을 내는 결함을 고치는 PR이면 그 입력의 테스트가 있어야 한다.
- 복구·폴링 PR: 대상 선정 조건, 조회로만 확정하는지, 식별자 없는 결과 불명 건에 재호출하지 않는지, 최대 횟수·만료를 검증한다.
- 인증·인가 PR: 인증 실패, 다른 사용자 자원(소유자 불일치), 비회원 요청의 거부 경로를 테스트한다.
- 클라이언트 코드에 자동 테스트 체계가 있으면 같은 원칙을 쓴다. 상태 변경 UI의 실패 응답·로딩·빈 데이터 분기가 대상이다.
- 기존 부채: 바뀌지 않은 코드의 테스트 공백은 지적하지 않는다. PR이 미검증 코드를 건드렸는데 바뀐 분기에 테스트가 없으면 `introduced`(새 분기) 또는 `worsened`(기존 미검증 분기를 더 복잡하게 함)다.

**심각도 앵커**
- critical: 사용하지 않음. 테스트 누락만으로 금전 손실이 나지는 않는다. 손실 자체는 REL·SEC가 잡는다.
- high: 외부 변경 실행·결과 불명 복구·인증 같은 핵심 구조에서 **새로 추가되거나 동작이 바뀐 분기에 테스트가 0개**다. 예: 외부 결과 매핑을 바꿨는데 매핑 테스트가 없음, 복구 스케줄러를 추가했는데 재호출 안 함 검증이 없음, 소유자 검증을 추가했는데 불일치 거부 테스트가 없음.
- medium: 정상 경로만 테스트하고 이 PR이 추가한 실패 경로(4xx/429/5xx/타임아웃/설정 누락)나 경계값(새 enum, default)이 빠짐. 또는 상태 전이·요청 접수 분기 변경에 테스트가 0개.
- low: 부작용 검증 누락(호출 안 됨·호출 횟수 미확인), 조합 케이스 일부 누락.

**피크 트래픽 관점**: 스로틀·5xx·연결 지연은 평시엔 드물고 피크에 몰린다. 이 분기를 건드린 PR에서 정상 경로만 테스트되었다면 medium 이상으로 본다. 재시도·백오프를 추가한 PR이면 "최대 횟수에서 멈춤"과 "결과 불명에서 변경 호출 재전송 안 함"을 둘 다 검증해야 한다. 이 검증이 없으면 high다.

**근거**: OWASP ASVS v4 V1.1(보안 검증 요구의 테스트 가능성), Google Testing Blog "Code Coverage Best Practices"(변경 코드 커버리지), Martin Fowler "TestCoverage". 실패 경로 테스트는 Michael Nygard *Release It!* 안정성 패턴.

## TEST-02 테스트 계층 적합성

- **적용**: 공통
- **왜 중요한가**: 계층이 틀리면 테스트가 있어도 검증이 안 된다. 영속성을 mock해서 유니크 제약을 "검증"하거나, ORM 자동 스키마 생성으로 테스트 DB를 만들어 마이그레이션 오류를 놓치는 경우가 그렇다.
- **판정 질문**:
  - 새·변경 테스트가 대상 계층에 맞는 수단을 쓰는가? 도메인은 순수 단위, 웹은 웹 계층 슬라이스, 영속성은 운영과 같은 DB 엔진(컨테이너 등) + 실제 마이그레이션, 외부 API 어댑터는 HTTP 대역 서버로 계약 검증.
  - 영속성 테스트가 실제 마이그레이션을 적용하는가? 마이그레이션 비활성화, ORM 자동 스키마 생성, 다른 엔진의 인메모리 DB 같은 우회가 없어야 한다.
  - 어댑터 테스트가 외부 요청 본문(변수·operation)과 응답 형태를 계약으로 검증하는가? 아니면 클라이언트를 통째로 mock해서 매핑만 보는가?

**체크포인트**
- 도메인 테스트에 프레임워크 컨텍스트·mock 라이브러리가 필요 없어야 한다. 레포의 기존 도메인 테스트 패턴을 기준으로 본다.
- 새 마이그레이션을 추가하는 PR은 그 스키마를 쓰는 영속성 테스트를 추가하거나 갱신해야 한다. 컬럼·인덱스·유니크 제약이 실제로 작동하는지가 대상이다.
- 테스트 설정에서 마이그레이션 끄기, 자동 스키마 생성, 운영과 다른 DB 엔진을 쓰면 위반이다.
- 외부 API 어댑터: HTTP 대역 서버로 요청·응답을 검증하고, 응답 픽스처는 실제 API 형태(데이터·사용자 오류·비용 메타데이터 등)를 따른다. 어댑터를 하위 클라이언트 mock만으로 테스트하는 것은 low다(매핑은 검증되지만 요청 계약은 안 됨).
- 웹: 컨트롤러 변경을 전체 애플리케이션 컨텍스트로만 검증하면 DB·외부 설정이 필요해 결국 skip되거나 실패한다. 슬라이스 테스트를 쓴다.
- 서비스: 포트(인터페이스)를 대역으로 둔다. 어댑터 구체 클래스를 mock하면 경계를 우회한 것이다. ARCH가 아니라 테스트 설계 문제로 low다.
- 레포가 옮겨 간 패키지 구조와 다른 옛 위치에 새 테스트를 두면 low다.
- 클라이언트: 컴포넌트 렌더 테스트, 상태 로직 단위 테스트, 네트워크 대역(요청 가로채기) 중 대상에 맞는 수단을 쓴다. 실제 브라우저 전체 흐름이 필요한 것을 단위 테스트로 흉내 내지 않는다.

**심각도 앵커**
- critical: 사용하지 않음.
- high: 마이그레이션을 추가·변경한 PR에서 영속성 테스트가 마이그레이션을 끄거나 자동 스키마 생성을 쓴다. 마이그레이션 오류가 테스트를 통과해 배포 시 기동 실패로 이어질 수 있다.
- medium: 새 영속성 쿼리·제약이 실제 DB 없이 mock으로만 검증됨. 새 외부 API 호출(쿼리·변경)에 HTTP 계약 테스트가 없음. 컨트롤러 변경을 슬라이스 없이 전체 컨텍스트로만 검증.
- low: 어댑터를 클라이언트 mock으로만 검증, 옛 위치에 테스트 추가, 계층과 맞지 않는 무거운 컨텍스트 사용.

**피크 트래픽 관점**: 해당 없음. 계층 선택은 트래픽과 무관하다.

**근거**: Martin Fowler "The Practical Test Pyramid", "IntegrationTest", "ContractTest". 12-factor X(개발·운영 환경 일치). Testcontainers 프로젝트 문서(운영과 같은 엔진으로 테스트).

## TEST-03 실제 외부 호출 격리

- **적용**: 공통
- **왜 중요한가**: 기본 테스트 실행이 실제 외부 시스템을 부르면 세 가지 문제가 생긴다. 테스트가 네트워크와 외부 데이터에 묶여 비결정적이 되고, 운영 API 한도를 소모하며, 상태를 바꾸는 호출이라면 **실제 주문·결제를 취소·환불·생성한다.**
- **판정 질문**:
  - 실제 외부 시스템을 호출하는 새·변경 테스트가 통합 테스트로 표시(태그·별도 디렉터리·별도 태스크)되어 기본 테스트 실행에서 제외되는가?
  - 이 PR이 기존 통합 테스트 표시나 기본 실행의 제외 설정을 지우는가?
  - 실제 외부 호출 테스트가 상태를 바꾸는 호출을 하는가? 한다면 전용 개발 환경인지 확인하는 가드가 있는가?

**체크포인트**
- "실제 호출 테스트"의 판별: 외부 클라이언트를 대역 없이 주입하고, 접속 설정을 가짜 값으로 덮어쓰지 않으며, 환경 변수·로컬 자격증명 파일에서 읽는다. 이름의 "Integration"·"IT" 접미사는 보조 신호다.
- 통합 표시는 클래스(파일) 단위로 둔다. 기본 테스트 태스크가 그 표시를 실제로 제외하는지 빌드 설정까지 확인한다. 표시만 있고 제외 설정이 없으면 격리되지 않은 것이다. 제외 설정을 추가하는 PR은 `fixed`, 제거하는 PR은 high다.
- 테스트 코드에 실제 운영 호스트·실제 주문·고객 식별자를 하드코딩하지 않는다. 가짜 호스트(test-·example·fake 계열 이름)나 HTTP 대역을 쓴다.
- 상태를 바꾸는 호출을 실제로 보내는 테스트는 통합 표시만으로는 부족하다. 실행 전 대상이 개발 환경인지 가드(전용 환경 변수, 허용 호스트 목록, 테스트 표시가 붙은 대상만 조작)를 둔다. 가드가 없으면 high다.
- 클라이언트 E2E·브라우저 자동화도 같다. 운영 사이트를 대상으로 결제·폼 제출까지 가는 흐름은 구조적으로 막혀 있어야 한다.
- 기존 부채: 이미 격리되지 않은 통합 테스트는 `pre-existing`이다. PR이 그 파일을 건드리고도 격리하지 않으면 `pre-existing`, 격리하면 `fixed`다.

**심각도 앵커**
- critical: 기본 테스트 실행에서 제외되지 않는 상태로 **취소·환불·결제 같은 상태를 바꾸는 실제 호출**을 하는 테스트를 추가한다. 테스트 한 번 실행에 자격증명이 가리키는 환경의 실데이터가 바뀐다(금전 손실).
- high: 실제 조회 호출 테스트를 격리 없이 추가. 기존 통합 표시 제거. 기본 실행의 제외 설정 제거. 개발 환경 가드 없는 상태 변경 통합 테스트(격리는 됨).
- medium: 테스트 코드에 실제 운영 호스트·실데이터 식별자를 하드코딩. 통합 테스트가 특정 실데이터의 상태에 의존(그 데이터가 바뀌면 깨짐).
- low: 통합 테스트 결과를 "null 아님" 수준으로만 확인(외부 계약 검증 가치 낮음).

**피크 트래픽 관점**: 피크 기간에 누군가 로컬이나 CI에서 테스트를 돌리면 통합 테스트가 운영 자격증명으로 외부 API 한도를 함께 소모한다. 토큰 발급도 반복된다. 프로파일이 피크 기간을 정의하면(시즌 모드) TEST-03 위반은 같은 심각도라도 사람이 보도록 임계값 30을 권장한다.

**근거**: Martin Fowler "TestDouble", "UnitTest"(solitary vs sociable). 12-factor III(설정은 환경에), X(환경 분리). OWASP ASVS v4 V14.1(빌드·배포 파이프라인의 환경 분리).

## TEST-04 시간 제어와 결정성

- **적용**: 공통
- **왜 중요한가**: 결제 대기 만료, 다음 확인 시각, 토큰 만료처럼 시간에 기대는 규칙은 시스템 시계를 직접 읽으면 테스트로 고정할 수 없다. 실시간 대기 기반 테스트는 느리고 간헐적으로 실패한다(flaky). flaky 테스트는 결국 무시되고 회귀를 놓친다.
- **판정 질문**:
  - 이 PR이 추가한 시간 의존 로직(만료·주기·경과 시간 비교·타임스탬프 기록)이 주입 가능한 시간 소스(clock)를 쓰는가?
  - 새 테스트가 sleep·실시간 대기·실행 순서·공유 정적 상태·랜덤·시스템 시간대에 의존하는가?

**체크포인트**
- 새 시간 의존 로직은 주입받은 시간 소스에서 현재 시각을 읽어야 한다. 레포에 이미 있는 시간 소스 주입·가변 테스트 시계 패턴을 기준으로 본다.
- **비교·판단에 쓰이는** 현재 시각 직접 호출은 medium이다(만료·다음 확인 시각 계산, 대기 시간 초과 판정). **기록용**은 low다(요청 시각·완료 시각 기록). 판정 에이전트는 값이 조건문·스케줄 쿼리에 쓰이는지 확인한다.
- 시간대: DB·서버·테스트의 시간대가 다를 수 있다. 시간 비교 테스트가 실행 환경 기본 시간대에 기대면 개발자 PC와 CI 결과가 달라진다. 시스템 기본 시간대·시간대 없는 현재 시각 사용은 medium이다.
- 비동기·스케줄러 테스트: sleep 대신 직접 메서드 호출, 래치·조건 대기(polling assertion), 고정 시계를 쓴다. 클라이언트는 가짜 타이머를 쓴다.
- 결정성: 테스트 간 공유 상태 금지(정적 가변 필드, 정리하지 않는 DB 행·저장소). 각 테스트 앞에서 상태를 비운다. 테스트 실행 순서에 기대지 않는다. 단언은 랜덤 UUID나 현재 시각과 정확히 같은 값을 비교하지 않는다.
- 기존 부채: 바뀌지 않은 코드의 직접 시각 호출은 지적하지 않는다.

**심각도 앵커**
- critical: 사용하지 않음.
- high: 폴링·만료 로직(결제 대기 만료, 재확인 주기, 최대 경과 시간)을 주입 가능한 시간 소스 없이 구현해 **경계(만료 직전·직후)를 테스트할 수 없음.** 이 로직이 만료 시 실행·거절 같은 돈 결정을 할 때다.
- medium: 비교·판단용 현재 시각에 시간 소스 주입이 없음. 새 테스트의 sleep·실시간 대기. 실행 환경 기본 시간대 의존. 테스트 간 공유 가변 상태.
- low: 기록용 타임스탬프의 직접 호출. 단언이 시간 근사치를 느슨하게 비교.

**피크 트래픽 관점**: 피크에는 재확인 대상 건이 몰려 스케줄러 주기·백오프 경계가 실제로 자주 닿는다. 그 경계를 고정 시계로 검증하지 않은 폴링 PR은 시즌 모드에서 medium을 high로 올려 판단한다.

**근거**: Martin Fowler "Eradicating Non-Determinism in Tests". Google Testing Blog "Flaky Tests at Google and How We Mitigate Them". Kent Beck *Test-Driven Development* (테스트 독립성).

## TEST-05 동시성·멱등성 테스트

- **적용**: 서버
- **왜 중요한가**: 같은 대상에 대한 중복 실행은 대개 DB 유니크 제약과 낙관적 락으로만 막힌다. 복구 스케줄러·다중 인스턴스가 생기면 "같은 건을 두 실행자가 집는" 경합이 새로 생기고, 이것이 곧 외부 변경 호출 중복(이중 환불)이다. 경합은 단위 테스트로는 재현되지 않는다.
- **판정 질문**:
  - 이 PR이 멱등성 키·유니크 제약·낙관적 락·선점(claim) 로직을 추가·변경했다면, 운영과 같은 DB 엔진에서 **2개 이상 스레드**로 같은 대상을 동시에 처리하는 테스트가 있는가?
  - 테스트가 "행이 1개"뿐 아니라 "외부 호출이 1회"까지 확인하는가?

**체크포인트**
- 기준 패턴: 스레드 풀 2개 이상 + 래치로 동시 출발시키고, 각 결과가 같은 식별자로 수렴하는지 확인한다.
- 유니크 제약 위반 → 기존 건 반환 경로를 바꾸면 mock 단위 테스트와 실제 DB 동시 테스트를 둘 다 갱신한다.
- 스케줄러·선점 로직: 두 실행자가 같은 보류 건을 동시에 집을 때 외부 변경 호출이 **정확히 1회**인지 검증한다(대역 + 원자적 카운터, 또는 호출 횟수 단언). 잠금 방식(행 잠금 + 잠긴 행 건너뛰기, 조건부 UPDATE, 버전 컬럼)은 운영과 같은 DB에서 검증해야 한다. 다른 엔진·mock으로는 잠금 의미가 재현되지 않는다.
- 낙관적 락 충돌 처리를 추가하면 충돌 재현 테스트를 둔다. 같은 엔터티를 두 번 로드해 각각 저장하는 방식이다.
- 동시성 테스트도 결정적이어야 한다(TEST-04). sleep으로 경합을 "기대"하지 말고 래치로 출발을 맞춘다. 결과 대기에는 타임아웃을 둔다.
- 클라이언트의 동시 갱신(연타·중복 요청)은 REL에서 코드로 본다.

**심각도 앵커**
- critical: 사용하지 않음.
- high: 복구·폴링·재시도 PR이 "같은 건 동시 처리 시 외부 변경 호출 1회"를 검증하는 테스트 없이 선점·잠금 로직을 추가. 멱등성 키나 유니크 제약을 바꾸면서 동시 요청 테스트를 갱신·추가하지 않음.
- medium: 동시성 테스트가 mock·다른 DB 엔진으로만 작성되어 운영 DB의 잠금 의미를 검증하지 못함. 행 수만 보고 외부 호출 횟수는 안 봄.
- low: 동시성 테스트가 타임아웃 없는 대기·sleep 사용.

**피크 트래픽 관점**: 피크에는 사용자가 버튼을 연타하고 프론트·연동 시스템 재시도가 겹친다. 그래서 같은 대상 동시 요청이 평시보다 훨씬 자주 생긴다. 멱등성 경로를 바꾼 PR의 동시성 테스트 누락은 시즌 모드에서 반드시 사람이 보게 한다.

**근거**: CWE-362(Race Condition), CWE-367(TOCTOU). Martin Kleppmann *Designing Data-Intensive Applications* 7장(트랜잭션·격리 수준). Brian Goetz *Java Concurrency in Practice* 12장(동시성 테스트).

## TEST-06 기존 테스트 무력화·약화 금지

- **적용**: 공통
- **왜 중요한가**: 실패하는 테스트를 지우거나 끄거나 단언을 느슨하게 하면 회귀 방지가 조용히 사라진다. CI가 약한 레포에서는 이런 변경을 막을 장치가 리뷰뿐이다.
- **판정 질문**:
  - 이 PR이 테스트 메서드·파일을 삭제하거나, skip·disabled 표시·항상 거짓인 가정·조건부 실행으로 끄거나, 단언을 약화하는가? 약화의 예: 값 동등 → null 아님, 호출 횟수 단언 삭제, 예외 타입 단언 제거, 스냅샷 일괄 갱신.
  - 삭제·약화가 있다면 그 동작이 의도적으로 바뀌었고, 새 동작을 검증하는 테스트로 대체되었는가?

**체크포인트**
- 상태 전이 불변식(종료 상태에서 전이 거부, 처리 전 완료 거부), 멱등성(동시 요청·중복 식별자 거부), 결과 불명 시 재호출 안 함을 지키는 테스트의 삭제·약화는 high다. 정책이 스펙·결정 기록으로 바뀐 경우는 예외지만, 그 근거 링크와 대체 테스트가 있어야 한다.
- 실제 DB가 필요한 영속성 테스트를 무조건 skip하게 바꾸거나 끄면 high다. 마이그레이션 오류를 숨긴다.
- mock 반환값을 바꿔 테스트를 "통과시키기"만 했는지 본다. 예: 거절 분기 테스트의 입력을 허용 상태로 바꿔 사실상 정상 경로를 검증하게 됨.
- 정적 검증 도구 설정으로 체크를 끄거나 제외 범위를 넓히는 변경은 TEST-07에서 본다.

**심각도 앵커**
- critical: 사용하지 않음.
- high: 상태 전이·멱등성·결과 불명 재호출 금지 같은 핵심 불변식을 검증하는 테스트를 대체 없이 삭제·비활성화·약화. 영속성 테스트 전체 비활성화.
- medium: 그 밖의 테스트를 대체 없이 삭제·비활성화. 단언을 약화.
- low: 이유와 추적 티켓이 적힌 일시 비활성화에 복구 계획이 있음.

**피크 트래픽 관점**: 피크 직전 핫픽스 PR에서 "테스트가 막아서" 끄는 경우가 생기기 쉽다. 시즌 모드에서는 TEST-06 finding이 1건이라도 사람이 보게 임계값 30을 쓴다.

## TEST-07 정적 검증 도구 신규 오류

- **적용**: 공통
- **왜 중요한가**: 자동 테스트가 없거나 얇은 레포에서는 린터·타입 체커·템플릿/스키마 검증기가 유일한 정적 관문이다. 템플릿 문법 오류는 해당 화면 렌더 오류를 내고, 설정 스키마·JSON 오류는 편집기 저장·배포를 막는다.

- 신규 판정 키는 (체크, 파일, 메시지)로 본다. 줄 번호는 PR이 위쪽 줄을 바꾸면 밀리므로 키에서 뺀다.
- 생성 도구·외부 편집기가 만든 파일의 신규 오프펜스는 info로 둔다. 직접 수정 여부는 ARCH가 본다.
- 도구 설정으로 체크를 끄거나 경로를 제외하면 medium이다. 기존 부채를 숨기려고 제외하려면 PR에 목록과 이유를 적어야 한다.
- 기존 부채: base에 이미 있던 오프펜스는 PR이 그 줄을 건드려도 남아 있으면 `pre-existing`, 고쳤으면 `fixed`다.

**심각도 앵커**
- critical: 사용하지 않음. 구매 불능 같은 결과는 REL이 critical로 잡는다.
- high: 신규 템플릿 문법 오류가 카트·구매 폼·전역 레이아웃처럼 모든 구매 흐름이나 전 페이지가 거치는 핵심 구조 파일에 생김.
- medium: 그 밖의 파일에서 TEST-07 소관 error 신규 오프펜스. 설정·억제 주석으로 체크를 끄거나 범위를 줄임.
- low: TEST-07 소관 warning 신규 오프펜스.

**피크 트래픽 관점**: 피크 중에는 프로모션 화면·템플릿이 하루에도 여러 번 바뀐다. 문법 오류가 섞인 프로모션 화면이 라이브에 나가면 랜딩 페이지 전체에 렌더 오류가 노출된다. 시즌 모드에서는 프로모션 구조 파일의 신규 문법 오류도 high로 본다.

**근거**: OWASP ASVS v4 V14.2(빌드 시 정적 분석). Google *Software Engineering at Google* 20장(Static Analysis). CWE-1164(Irrelevant Code)·CWE-710(코딩 표준 미준수) 계열.

## TEST-08 수동 QA 시나리오·미리보기 근거

- **적용**: 클라이언트
- **왜 중요한가**: 화면 변경의 실제 검증은 미리보기·스테이징 환경에서 사람이 한다. 시장(국가·통화), 서드파티 스크립트, 언어, 디바이스 조합이 많아 "무엇을 어디서 확인했는지"가 PR에 없으면 리뷰어가 검증 범위를 알 수 없다.
- **판정 질문**:
  - PR 설명이나 커밋 메시지에 미리보기 링크(또는 미리보기 환경 식별자)와 확인한 시나리오가 있는가?
  - 시나리오가 변경 영향에 맞는 축을 다루는가? 축은 시장·디바이스·언어·서드파티 연동·키보드/스크린리더 중 해당하는 것이다.

**체크포인트**
- 판정 입력: PR 본문(`context.target.pr.body`)과 커밋 메시지.
  - PR 대상 실행: 둘 다 보고 아래 앵커대로 판정한다.
  - 브랜치 대상 실행(`context.target.pr`가 null): PR 본문이 아직 없으므로 감점하지 않는다. 커밋 메시지에도 미리보기·시나리오 근거가 없으면 `severity: info` finding 하나만 남긴다. 근거는 영향이 가장 큰 변경 1곳만 적고, recommendation에 PR 본문에 적을 미리보기 식별자와 시나리오(아래 기준)를 리뷰어 확인 질문으로 쓴다.
  - QA 기록을 커밋 본문이 아니라 PR 본문에 남기는 팀이 많다. 커밋 메시지만으로 감점하면 모든 브랜치 실행이 같은 이유로 감점된다.
- 변경 영향별 최소 시나리오:
  - 카트·구매 폼 변경: 담기 → 수량 변경 → 삭제 → 체크아웃 진입(제출 전까지), 증정품·번들처럼 특수 품목 포함, 모바일·데스크톱.
  - 시장·국가 분기·프로모션 변경: 영향 시장별 가격·통화·약관 노출, 국가 전환 후 재확인.
  - 전역 레이아웃·공통 스크립트 변경: 주요 페이지 유형 공통 로드, 서드파티 스크립트 동작, 콘솔 오류 없음.
  - 번역 문자열 추가: 지원 언어 중 최소 1개 비기본 locale 확인.
  - 접근성 관련 변경: 키보드만으로 조작, 스크린리더 1회.
- 링크가 미리보기가 아닌 라이브 환경을 가리키면 "미리보기 검증 없이 라이브 편집"이다. OPS 소관이므로 `also_affects: ["OPS"]`로 둔다.
- 커밋 메시지 형식·티켓 번호 규칙은 OPS(변경 추적성) 소관이라 여기서 감점하지 않는다.
- PR 템플릿·QA 체크리스트가 레포에 없는 것은 PR별 판정과 무관하다. 과거 커밋은 판정 대상이 아니다.

**심각도 앵커**
- critical: 사용하지 않음.
- high: 사용하지 않음. QA 기록 부재만으로 high 피해가 확정되지 않는다.
- medium: 카트·구매 폼·시장 분기·프로모션 구조를 바꾼 PR에 QA 시나리오와 미리보기 근거가 **둘 다** 없음.
- low: 시나리오는 있으나 영향 축(시장·디바이스·언어·서드파티) 중 하나 이상 누락. 또는 그 밖의 구조 변경에 QA 기록이 없음.

**피크 트래픽 관점**: 피크 프로모션 PR은 시장별 금액·약관·카운트다운이 핵심이다. 시즌 모드에서는 프로모션·시장 분기 변경의 "시장별 확인 기록 없음"을 medium으로 본다. 다른 시나리오가 있어도 마찬가지다.

**근거**: ISTQB Foundation Level Syllabus(탐색적·경험 기반 테스트, 테스트 근거 기록). WCAG 2.2 평가 방법론(WCAG-EM) 수동 확인 절차. Google *Software Engineering at Google* 9장(Code Review: 리뷰어에게 검증 맥락 제공).

## TEST-09 테스트 가독성

- **적용**: 공통
- **왜 중요한가**: 정책은 바뀐다. 테스트 이름이 시나리오를 말해야 정책이 바뀔 때 어떤 테스트를 고쳐야 할지 보인다.
- **판정 질문**:
  - 새 테스트 이름이 "조건 → 기대 결과"를 말하는가? (`test1`, `testCancel`, `shouldWork`는 아니다)
  - 한 테스트가 여러 시나리오를 섞지 않고, given/when/then 구조가 읽히는가?

**체크포인트**
- 이름 스타일(영어 문장형, 한국어 문장형 등)은 레포 관례를 따른다. 여러 스타일이 공존해도 되지만 같은 테스트 파일 안에서는 한 스타일로 쓴다.
- 상태 매핑 경계값에는 파라미터 테스트를 권장한다. 케이스별 표시 이름("입력 → 기대")을 둔다.
- 픽스처: 반복되는 입력 생성은 헬퍼로 모은다. 매직 값(식별자 리터럴)에는 의미 있는 이름을 쓴다.
- 테스트의 진단 출력(표준 출력 print)은 가독성 문제다. 그 출력에 토큰이 있으면 SEC 소관이다.

**심각도 앵커**
- critical / high / medium: 사용하지 않음.
- low: 시나리오를 알 수 없는 이름, 한 테스트에 여러 시나리오, 같은 파일 안 스타일 혼용.

**피크 트래픽 관점**: 해당 없음.

**근거**: Gerard Meszaros *xUnit Test Patterns*(Obscure Test, Four-Phase Test). Robert C. Martin *Clean Code* 9장(Clean Tests). Martin Fowler "GivenWhenThen".
